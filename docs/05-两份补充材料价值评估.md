## 1. 结论

**两份都有帮助，但用途不同：附件 A 适合补充产品交互和交付细节；附件 B 适合扩充开源组件研究清单。相对于现有 v0.2，它们带来的核心需求增量有限，均不适合直接作为开发依据。**

| 判断维度 | 附件 A：web app工作台.md | 附件 B：pasted-text.txt |
|---|---|---|
| 最有用的部分 | 今日经营状态、旧素材复用提醒、渠道交接包字段 | 公众号排版、热点输入、人工审核的具体开源参照 |
| 与现有需求的重合 | 高：IP、资产、选题、正式作品、版本、审核和反馈已覆盖 | 高：八阶段蓝图大体重复现有经营链路 |
| 相对新增价值 | 主要是已有功能的页面和模板细化 | 主要是组件候选和交互例子，组件线索比 A 更有用 |
| 主要问题 | 人工复盘、未来自动发布、混合状态链、先审核后生成渠道稿 | 海外渠道、自动发布/抓数据、自动固化复盘结论、MCP 示例被当作完整远程方案 |
| 开源信息可靠性 | 所列项目可访问；“均超过 50 Star”不能覆盖参考仓库 | 所列项目可访问且均超过 50 Star；部分数字和适配判断需要修正 |
| 建议用途 | 作为交互设计及导出模板的补充参考 | 作为组件调研候选清单和原型参考 |

真正值得吸收的是具体交互、交付细节和有针对性的组件线索。用户已确定的 Hermes 底座选择已进入技术文档；其余建议尚未整体并入 PRD。当前 v0.2.1 在版本绑定、人工记录、审核权限、数据口径、AI 复盘和验收条件上更具体。

### 3.2 可以保留作说明，但不产生新需求

“作品不能只留在聊天框”“来源、上下文、个人判断要一起保存”“向量库不是全部记忆”“人保留最终判断”等观点与本项目一致。它们适合帮助新成员理解产品，但 v0.2 已用独立对象、版本、引用、审核和 Learning 采纳表达，不需要再增加平行的一套资产体系。

选题评分的 R/A/P/F/U 维度可以用作讨论材料，但 0.30、0.25 等权重没有验证依据。它也没有定义归一化、缺失值、历史反馈可比性、制作成本和重复风险。当前 PRD §6 的解释维度更完整，首版不应直接采用这条总分公式。

### 3.3 技术组合的参考价值有限

附件列出多种前后端、队列、检索、编排、鉴权和观测产品，说明了可能需要的技术类别，但没有完成具体选型。它不能证明项目需要同时引入 Temporal、向量索引、独立搜索服务、复杂身份系统或多 Agent 编排框架。

用户已确定从 Easel-For-Hermes 开发，因此技术方案已改为沿用其 React/TypeScript/Vite 前端、Python/FastAPI 后端和 Hermes CLI，替代此前新建 Fastify/Node 后端的建议。PostgreSQL 业务事务层、正式作品版本和受控 Worker 作为待补能力；附件里列出的其他框架不因此自动成为依赖。

- “市面上 99% 的工具都是玩具”“全球目前最火”等说法没有调查方法或对照样本，不能写进立项论证。

## 5. 使用材料前必须修正的内容

以下属于与已确认范围冲突，或会破坏经营数据、版本和审核可信度的问题。

| 问题 | 出现位置 | 对本项目的影响 | 正确处理 |
|---|---|---|---|
| 将人工复盘作为首版终点 | A：MVP 和首个版本说明 | 缺少用户明确要求的 AI 复盘成果 | 人填原始记录，AI 生成可编辑报告、证据、局限与下一轮建议，沿用 R-044～R-047。 |
| 将自动发布放到 P2，或第二阶段接入 Postiz/MultiPost | A：优先级；B：排发整合和实施路线 | 用户已排除的能力被重新写回路线图 | 各阶段均采用人工发布；工作台只安排提醒并导出已审核内容包。 |
| 邮件、独立站、X、LinkedIn 等作为输出渠道 | A、B | 扩大到中国社交媒体以外 | 当前渠道允许列表保持中国社交媒体。研究资料来自何处与成品发布渠道分别判断。 |
| 自动抓取自己账号的发布指标 | A：P2；B：架构图的 API 抓取 | 改变人工记录边界，增加平台凭据和采集依赖 | 自己作品的经营观测由人通过表单或手动 CSV 导入；公开研究输入不能伪装成已确认经营记录。 |
| Agent 写真实发布/反馈记录 | A：record_publish_result、publish_records:write；B：log_feedback_metrics | AI 输出可能变成“真实观测”，污染下一轮复盘 | Agent 可读授权记录、生成研究和复盘；真实记录写入仅限人的界面/确认导入路径。 |
| 先审核，再生成渠道版本 | A：创作流程第 8 步 | 母稿的审批无法覆盖改写后新增的标题、事实和附件 | 先生成渠道稿并核查，再由人审核该渠道的最终交付快照。审核后可做确定性打包，不做未经复审的改写。 |

### 6.4 推荐研究顺序

1. **Easel-For-Hermes：按已选基准开展改造。** 本轮已核对指定提交的核心文件，后续先验证实际工程与 Hermes 路径，再补作品、审核和人工记录。具体顺序见 06。
2. **doocs/md：针对公众号交付缺口验证。** 用包含标题、列表、表格、图片说明和引用的样稿，检查导出、人工粘贴及审核快照对应关系；保留工作台的结构化文档为事实源。
3. **TrendRadar：有输入需求时研究。** 验证来源链接、事件时间、采集时间、去重和失效信息能否进入来源契约；上游热度只作为选题证据之一。
4. **social-media-agent / Agent-Reach：有具体缺口再参考。** 分别用于审核交互与输入研究，不能改变所选底座或产品权限边界。

Postiz、Brightbean、MultiPost 和专项发布器暂不进入集成清单；ShenNongMi、获客工作台也没有显示出比当前方案更直接的核心复用价值。

以下 EV 编号属于本评估的建议追踪，不是已新增的 R/AC 需求编号；建议阶段不改变现有首版验收范围。

| 评估项 | 来源 | 建议落点 | 可验证的结果 | 处理级别 |
|---|---|---|---|---|
| EV-01 今日积压提示 | A | R-020 / AC-020；今日页 | 显示待补证、待审核、待登记等真实待办及停留时间；点击可到具体对象；导出不被统计为发布 | 已有页面细化候选 |

短期优先补交接模板和页面原型，再验证公众号导出方式。八 Agent 编排、固定选题权重、独立知识图谱、全功能发布平台，不进入这份建议清单。

首轮试用可沿用附件 A 的收敛思路：一个 IP、一个栏目、少量真实网页/笔记 → 一个素材包与简报 → 公众号和小红书渠道稿 → 人审、导出 → 人工发布和补录 → AI 复盘 → 下一轮建议。这是先验证一条路径，不代表删除 v0.2 其他首版需求；开发演练数据必须与真实经营记录区分。
