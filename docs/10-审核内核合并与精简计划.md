## 0. 已确认基准与真实状态

### 0.1 当前产品与架构决定

| 决定 | 开发约束 |
|---|---|
| Multica 是源码底座 | 复用 Next.js/React/TypeScript、Go API、PostgreSQL、Task/Run、daemon；增加原生内容模块，插件可选 |
| 一个品牌一个工作空间 | 空间内支持多个账号、人设、项目和 SOP 配置；跨空间权限边界继续有效 |
| 公共与账号专属资料 | 品牌公共资料可供本空间账号使用；账号专属素材、经历、记忆按任务授权读取 |
| 账号人设提示词 | 人设是账号设置字段，各账号独立保存；任务沿用账号配置，不建独立人设库或绑定关系 |
| 运营参数在使用时配置 | 账号角色、内容侧重点、运营目标可自定义，不写死某个品牌或官方/人设/素人的固定枚举 |
| SOP 用受约束的步骤模板 | 支持输入、交付物、执行角色、Skill、确认节点与依赖约束下的增删/排序；不建设任意连线流程画布 |
| 最终人工审核必须执行 | Web/API/Agent 走同一后端门禁；SOP 编辑或自动预检开关不能绕过 |
| AI 风险允许人类处置 | 保留原始报告及逐项处理；人工继续不意味着 AI 通过或风险事实被推翻 |
| 检测失败/未完成单列 | 允许经人类说明并最终审核后继续交付，但不能把未完成改写成检查通过 |
| 人工发布和真实记录、AI 复盘 | 本模块只判定已审核内容包是否可交付，不调用社媒平台发布，也不代填真实经营数据 |
| 浏览器为主要测试入口 | 日常不同时调试 Electron；先便于本机定位问题，后补远程服务与本机 daemon 的连接、断线恢复测试 |

研究后、正文创作前的一次人工研究结论确认仍保留在默认 SOP；它确认表达意图、材料及未解决问题，不等于所有内容都必须有外部事实依据。最终人工审核是另一个不可跳过的交付节点。

## 1. 合并目标与责任边界

合并能力、规则语义和接口，不拼接两份 SKILL.md，不硬合并上游 Git 历史，不要求另建一套账号/数据库/任务平台。`content-publishing-gate` 仅作为审核模块的逻辑名称，首版直接集成 Multica 派生工程；独立服务、独立仓库或新的 Python/Node 主后端不是前置条件。

本模块负责：

1. 按内容性质识别需要核查的主张、适用场景与依据缺口。
2. 对目标中国平台、商业属性及品牌规范进行风险预检。
3. 检查编辑一致性、渠道必备字段和明确声明的风格约束。
4. 形成可定位、可追溯、可人工处置的结构化报告及改稿建议。
5. 由 Go 领域服务校验最终版本、人工审批和已审核内容包交付条件。

本模块不负责正文生产全流程、视频剪辑、平台登录/发布、广告投放、自动经营数据抓取、完整 RAG 或独立项目管理。可以给出修改建议，但采用建议必须创建内容新版本，不能覆盖当前正文和旧报告。风险判断不构成法律结论或平台过审保证。

## 4. 四层审核职责与权限

保留四层职责划分，但 L1～L3 提供检查结果，L4 是 App 的确定性状态校验。禁止把所有层的风险严重度直接当作审批权。

| 层 | 负责内容 | 执行方式 | 输出 |
|---|---|---|---|
| L1 主张与依据 | 可核查事实、引用、工况、范围、时效与必要的媒体证据 | 结构化提取＋语义审查＋资料关联校验 | Finding、证据状态、未检查项或不适用 |
| L2 风险 | 平台、商业表达、误导、权利/授权等适用风险 | 按场景加载规则并结合语境判断 | 风险发现、来源、程度、建议和不确定性 |
| L3 编辑与渠道 | 标题正文一致、占位符、必备字段、明确品牌风格 | 确定性校验＋按需语义检查 | 质量建议、字段问题或内部规范冲突 |
| L4 交付就绪 | 版本、附件、授权、人类审批和处置完整性 | Go 领域服务 | 是否可取得“已审核交付包”及阻断原因 |

风险 Finding 使用 `info/low/medium/high/blocker`；`pass` 不作为单个 Finding 的严重度。上游等级映射必须保存原值，映射写进台账。AI 给出的 blocker 是待人工处理的风险发现，不自动成为永远不可覆盖的系统硬阻断。

系统硬阻断包括：缺少有效人工批准、版本/哈希不匹配、对象越权、所需交付文件实际缺失、请求身份伪造或应处置的问题未作处置。这些完整性与权限约束不能用风险接受理由绕过。

## 5. 内容性质与规则装载

### 5.1 不把所有表达事实化

先识别具体片段的表达性质：事实陈述、个人经验、观点、假设、虚构/创意等可混合存在。

- 产品性能、数字、比较、认证、价格等事实主张按相应条件检查，不靠少数关键词直接判错。
- 个人经验关注是否忠于用户提供的经历及是否被扩大为普遍结论，不要求每段经历都附第三方证明。
- 观点检查论据和表达是否混淆；创意检查表达、自洽及真假边界；其中嵌入的具体事实仍单独核查。
- 没有需核验的事实主张时，L1 可记录分类和不适用理由，不为凑报告强行生成缺证问题。

### 5.2 按任务装载

```text
最小检查契约
+ 目标平台及交付类型规则
+ 实际涉及的领域/商业场景规则
+ 有权限的品牌公共规范
+ 本次任务获授权的账号资料、规则和案例
+ 必要的人设与账号平台配置版本
```

中国平台使用应用允许列表；不因上游包含 TikTok 等描述自动扩展范围。官方号、人设号、素人号只是可配置角色，不能仅凭角色名字判断有无商业属性。规则应区分内容实际场景与用户声明，缺信息记录待核验，不默默伪造配置。

核心规则目录只是分类组织，不要求每次完整加载四份长文；L4 在后端执行，无需让模型“模拟通过审批”。案例按需检索，保存来源、日期、限制和来源类别；普通创作者讨论不能当作平台官方规则。

### 5.3 规则更新与版本

静态规则包显式升级、固定版本与内容哈希；不在运行中自动更新 main。每次报告保存原始来源、规则快照和执行版本。新增规则不重写旧报告；必要时标记相关内容需复查，并发起新运行。来源失效与检查器故障分开处理，不能把链接失效当作内容已违规。

## 6. 统一数据契约

所有下述字段与 schema 是待实施契约，不是已创建接口。来源归属从认证主体和已授权对象校验，不能信任请求自报的 workspace、actor 或人工标记。

### 6.1 ReviewInputSnapshot

至少包含：workspace_id、account_id、work_id、channel_variant_id、content_revision_id、content_hash、资产 ID/哈希清单、account_config_revision_id、persona_prompt 的实际输入快照或哈希（可空）、sop_revision_id、step_id、审核范围、输入授权摘要、商业/内容场景及对应版本。

一次报告固定一个目标账号和渠道交付快照；批量操作拆成多个子报告，按授权形成汇总，不能以一个渠道通过代表所有账号通过。不得把其他账号的专属案例混入汇总解释。对外调用只传对象引用或受控输入，不接受任意本机绝对路径。

### 6.2 Claim 与 Evidence

Claim 保存稳定 ID、表达性质、主张类型、文本位置、原文、适用范围、来源引用和待核验信息。Evidence 保存来源快照/Asset、定位、可访问范围、支持/反驳/上下文关系、时间与局限。

文本定位需指定 block_id、范围和偏移编码约定；Python 字符位置与 JavaScript UTF-16 偏移不能直接混用。视频定位使用 Asset 哈希和时间码。改稿后旧定位失效须重新检查，不能仍高亮错误段落却沿用旧结论。

### 6.3 RuleDefinition

规则保存稳定 rule_id、layer、name、source_kind、适用平台/场景/表达性质、触发逻辑、需要的证据类型、风险程度、建议动作、来源登记 ID、核验时间、规则版本及上游路径/提交。

触发逻辑必须区分确定性检查与语义判断。YAML/JSON 不自动变成可执行规则：需要 schema、受控操作符及执行器；禁止从上传规则运行任意代码或无限制正则。缺来源、某词命中或商业场景不能一概直接升级为系统硬阻断。

### 6.4 Finding 与人工处置

Finding 保存 finding_id、run_id、rule_id、原始上游规则/等级、归一化严重度、位置、原文、原因、证据、未知项、建议及检测来源。模型结论与后续处置分开存储，禁止通过覆盖原报告改变风险等级历史。

人工处置使用独立追加记录：finding_id、actor、权限与原生确认来源、action、理由、证据引用、时间和适用内容版本。action 可表达修改后复检、补充资料、判为误报或接受风险继续；接受风险不代表声明内容合法或平台一定通过。人类处置不能由 Agent 凭据或通用插件桥接伪造。

### 6.5 PrecheckRun 与 Report

至少保存以下四组独立信息：

| 组 | 字段/状态示例 |
|---|---|
| 执行状态 | queued、running、completed、failed、cancelled、skipped，以及错误和重试 attempt |
| 覆盖状态 | 每个必查面的 reviewed/pending/not_applicable、未完成原因、资料及媒体清单 |
| 风险评估 | assessed/not_assessed、最高风险、findings、limitations、原始模型结果引用 |
| 版本与追溯 | 输入快照哈希、规则/Skill/schema/执行器版本、时间、parent_run、幂等键 |

应用 schema 须强化上游约束：证据引用、规则版本、覆盖结构有明确类型；成功执行不等于已完整覆盖；未完成或必要面缺失不得写为“AI 检查通过”。上游 schema 仅是输入参考，不用提示词代替服务端一致性校验。

### 6.6 HumanReviewDecision 与 DeliveryReadiness

人工批准绑定冻结的 DeliverySnapshot 哈希，含正文、附件、账号和实质性交付配置；保存审批者、人类确认来源、处置记录及所看的 AI 报告版本或未完成状态。

DeliveryReadiness 只由服务端计算 `can_export_approved_package`、reason_codes、approval_id、snapshot_hash 和风险/未完成提示。模型不得提交 `can_publish=true` 作为控制字段；本项目没有平台自动发布能力。

## 7. 处置与交付状态机

| 当前情况 | 后端与界面行为 |
|---|---|
| AI 未发现问题 | 仍待最终人工审核，不自动批准 |
| 有风险发现未处置 | 标为待人工处理；保留原始风险，不允许直接取得已审核包 |
| 人工逐项说明误报或接受风险 | 保留原报告、处置与理由；仍需对确定交付版本完成最终人工审核 |
| 检测失败、未检查或覆盖不足 | 显示未完成；人类明确说明并选择人工继续后可进入最终人工审核，不伪造 AI 通过 |
| 无有效人工批准 | can_export_approved_package=false；不能靠关闭开关或改 SOP 通过 |
| 人工已批准、快照/权限/附件有效、应处置项已处理 | 可交付；继续显示接受风险或 AI 未完成提示 |
| 批准后内容/附件/账号或实质配置变更 | 新快照需重新人工审核，旧批准只对旧快照有效 |
| 配置变更、切换或取消后的迟到结果 | 归入原运行，不覆盖当前版本、人工决定或新报告 |

区分风险处置、AI 覆盖和人工审批，不强制把它们压成一个 BLOCK/WARN/PASS。人类可以接受风险，但不能跳过身份校验、明确确认、必备交付文件或篡改历史。哪些低级建议允许批量确认由后续交互细化；任何方式均须保留可追溯处置。

排期草案可在制作中创建；冻结的已审核交接包和到期交付使用上述门禁。用户可继续编辑与人工整理，不因审核故障锁住整个工作区。导出/交接不代表已发布，发布与真实结果由人登记。

## 8. 自动执行与 Skill 装配

### 8.1 两个独立控制面

1. 内置依赖与自动调度：A 已固定收录。App 的 SOP 执行器负责何时加载、选择执行器、准备授权输入、调用和保存报告。
2. 最终人工审批与交付门禁：始终由 Go 服务执行，不由 Skill 文本或可选插件决定，不能被自动预检开关关闭。

已确认每个新建品牌空间的自动预检默认开启，在渠道稿提审时触发；关闭后保留手动检查。平时保存不自动调用模型，内容变化使旧报告过期。首版所有账号统一使用品牌级开关，不提供账号级覆盖。上述为已确认设计，尚未实现；任何开关设置都不能取消人工审核。

### 8.2 后端编排

```text
验证主体、对象和输入授权
→ 固定账号/人设/SOP/内容及规则版本
→ 创建 PrecheckRun 与上游 Task/Run 关联
→ 按场景加载必要规则与选定 Skill
→ 运行确定性预筛和独立语义分析
→ 校验覆盖、证据、schema 和输出版本
→ 按根因聚合发现并保存不可变报告
→ 原生页面完成人工处置及最终审核
→ Go 服务校验并导出已审核内容包
```

禁用自动检测时仍形成可识别的 skipped/未检查状态；模型或工具失败必须保留错误。无可用 AI 时人工经营继续可用，正式交付仍须最终人审。复用上游任务队列，不新增第二套相互竞争的 Agent 调度状态机。

### 8.3 运行边界

不绑定 Codex、Claude、Hermes 等单一执行器；已启用路径按任务能力装配同一审核输入/输出契约。上游说明出现 OpenClaw 不代表本项目保留其运行依赖；实际交付移除相关发现、安装、执行和兼容入口。原始 vendor 作为来源证据保留，运行时只启用允许组件。

浏览器不能直接调用本机文件/CLI。后端或已授权 daemon 在受控目录执行工具；网络、搜索和付费通道按配置启用，不因内置了相关代码自动运行。Python 工具、ffmpeg/ffprobe 及视觉/音频能力均需预检，不能满足时如实报告未检查范围。

## 9. 规则去重与精简

按同一输入快照、位置/Claim、根因和适用场景聚合发现，保留全部原规则、证据、平台差异与最高风险。不同平台处罚语义、不同权利问题或不同账号授权不能为了减少数量被错误合并。

建议 namespace 延用 INPUT、EVIDENCE、RISK、RIGHTS、EDITORIAL、CHANNEL、DELIVERY 等稳定前缀；原编号保存在 upstream_trace。实际 rule_id 清单由盘点和测试确定，不先凭数量机械迁移。

- 词面命中只生成候选，零命中也不等于语义安全。
- 证据缺口引出的同根因问题可聚合，但证据不足和独立的版权/商业规则不强行合并。
- 主观“吸睛、情绪、爆款”建议默认只作信息性提示；明确的品牌内部标准另行标注，不能冒充官方规则。
- 低质量、无适用范围或不可追溯断言先隔离为未核验材料；不要以静态断言强制阻断。
- L4 权限/版本/人审完整性校验只由应用维护一份，不复制到多个 Agent 中作独立裁决。

改写建议保留表达意图，不补造测试、数字、认证、案例或来源。必要时建议补披露/条件、收窄主张或删除不支持的部分；没有已知测试，不能生成“在本次测试中……”等暗示真实实验的句子。建议被采用后创建新版本并复检。

## 10. 模板、账号与私有规则

品牌 Profile、PersonaRevision、AccountConfigRevision 和任务授权分别管理，不将一个扁平 profile.md 当作全部品牌/账号的事实源。模板只是创建候选配置的辅助；由用户在 App 使用时设定角色、目标、内容方向和规范，AI 推断不自动固化为正式档案。

B 的 profile、my-rules、expressions 和词库模板可作为配置交互参考，实际迁移逐文件登记。品牌自定义规则不替换公共来源真实性，账号白名单只处理已确认场景，不能跨账号扩散。风险接受是本次内容/版本的人类决定，不自动永久降低规则门槛。

运营者手工录入处罚、反馈或误报案例，AI 可提出规则/表达候选；采纳后才成为后续可用的品牌或账号记忆。不得原样接入自动向共享 data/ 目录写长期规则的路径。

## 11. 最小运行包与依赖

运行包保留精简 Skill 入口、选用的 schema、规则、必要模板与工具适配、来源元数据和必需许可证。完整上游说明和回归夹具可随源码维护，不必全部随运行包发送给模型。

不要混淆三个集合：完整研究/维护源码、实际发行依赖、单次任务上下文。维护源码可以比发行包大；发行包包含多个平台规则，单次审核仍只装载相关部分。更新固定版本后再生成发行清单，不靠启动时联网下载。

首版媒体边界已确认：文字、图文文案和视频脚本在工作台内创作；图片与视频成片在外部制作后放入已授权的本地工作/素材文件夹，由工作台登记引用，作为正式作品附件支持预览、版本绑定及人工终审，替换附件后重新审核。首版不要求内置排版、剪辑、媒体生成或成片自动审核；AI 必须区分文字已检查与媒体未检查，不能以脚本检查代替成片审核。若启用视频，分别记录抽帧范围、音轨/转写覆盖和缺口，不把证据包准备完成写成全片审核通过。参考上游能力不自动扩展视频制作、广告投放或海外平台范围。

## 12. 浏览器优先开发与测试

已确认以浏览器为主要入口，日常无需同时调试 Electron；先便于定位问题，再补远程服务与本机 daemon 的连接、断线恢复。

建议首个联调环境为当前 Windows 本机 Web＋Go API＋独立开发数据库/附件，真实 Agent 联调时增加本机 daemon。用户确认了浏览器优先和后续远程测试顺序；数据库使用原生服务还是容器、具体端口和启动脚本仍属于实施选择，本轮未部署。Windows 客户端登录不自动等同 WSL 登录。

| 测试层 | 内容 | 运行条件 |
|---|---|---|
| 静态/合同 | schema、规则结构、映射、配置版本、归属与重复 ID | 无真实 Agent 调用 |
| 领域/数据库 | 权限、人工处置、批准事务、哈希、幂等、恢复、并发变更 | 独立测试数据库及样例附件 |
| 浏览器 | 自动开关、手动检查、报告高亮、覆盖缺口、处置、最终审核与导出 | Web/API；可控的 demo 执行器 |
| 真实 Agent | 输入装配、实际语义审核、工具能力、报告落库与隔离 | 显式选择客户端和测试资料；记录版本/执行证据 |
| 远程集成 | 配对、任务归属、断线重连、离线/重启、重复与迟到结果 | 后续远程测试服务＋本机 daemon |
| 桌面专项 | Electron IPC、原生对话框、桌面生命周期 | 仅涉及桌面交付或对应改动时执行，不是日常内容模块前置 |

开发服务可保持运行；前端用开发模式更新，后端/daemon 只重启受影响组件，不能假设 Go 已配置热重载。统一启动/状态/停止脚本需在 T-01 实测，停止默认保留数据，不能复用或误停日常实例。普通测试不得自动消耗本机 Agent 额度。

### 12.1 评估集

至少建立 30 条有区分度的样例，数量不是质量替代：

- 事实来源缺失、不支持、过期、超出工况或存在矛盾。
- 正常个人经验、观点、假设和创意不会因没有外部引用统一误报。
- 有/无商业属性及平台差异，词面误报和没有关键词的语义问题。
- 证据未读、规则缺失、工具失败、模型失败、媒体覆盖不足。
- 同根因去重及不同平台/权利问题应保留差异。
- AI blocker 经具名逐项处置后可由人类批准交付，原风险仍保留。
- 检测失败经人类继续后可审批，检测状态仍是 failed/未完成。
- 未经人审、伪造人类身份、版本变化、缺附件时均不能取得已审核包。
- 空间越权、账号专属资料泄漏、相同提示词意外扩大授权。
- 开关关闭仍有人审，SOP 删除/重排不能绕过最终审核。
- 修改版本、重复回传、取消后迟到、断线恢复与规则更新。

确定性测试断言执行/覆盖状态、必需规则及来源、去重、有效人审和 can_export_approved_package；不要断言 can_publish 或把排期草案当作真实发布。模型评估另行比较误报、漏报、依据忠实度和修改是否保意，记录样本、模型、提示版本及人工标注；schema 通过不等于判断准确。

## 13. 分阶段实施与验收出口

| 阶段 | 输出 | 出口 |
|---|---|---|
| P-01 盘点 | 固定 A/B 来源、文件与许可台账、能力/规则映射 | 未知来源和未迁移项清楚，原 vendor 保持可追溯 |
| P-02 数据与门禁 | 输入/报告/覆盖/处置/批准 schema、Go 事务与授权 | 不运行 AI 也能用夹具证明人工必审及版本边界 |
| P-03 文本预检接入 | 精简 Skill、按需规则、任务装配、去重、原始报告保存 | 成功/失败/取消/重复的输出均能进入正确状态 |
| P-04 原生界面 | 开关、手动触发、报告与处置、最终审核和导出 | 浏览器完成两条路径：AI 完成与 AI 未完成后人工继续 |
| P-05 回归与真实调用 | 至少 30 样例、选定执行器实测、升级/恢复证据 | 当前实现通过对应合同、数据库、浏览器和真实路径检查 |
| P-06 增强 | 经选择的媒体审核、更多规则及远程联调 | 每项能力单独报告覆盖和边界，不扩大已通过声明 |

按阶段组织改动，是否建立 Git 提交遵循实际用户授权；附件里的提交清单不构成自动提交/推送授权。文档修改不执行上述阶段。

完成定义为“Multica 中可调用、可追溯、可人工处置的原生审核能力”，不是必须交付独立 content-publishing-gate 产品。必须有精简入口、数据契约、版本化规则、唯一后端交付门禁、授权和回归证据、来源归属台账及实际支持矩阵。
