# Loretide · 模块边界与变更回归约束

日期：2026-09-13
状态：开发约束；应用尚未实施，自动边界检查与回归测试尚未建立。

## 1. 目标与实现形式

采用模块化单体：同一 Web/Go 应用内部划分明确业务模块，沿用 Multica 基础能力。首版不为每个功能单独部署微服务，也不把每个模块包装成插件。

目标是把修改的影响限制在所属模块，用公开接口和自动验证识别对调用方的影响；不能承诺修改 A 永远不影响 B。授权、公共类型、数据库迁移和公共 UI 的变化本来就可能影响多个模块，必须显式识别并扩大对应回归范围。

“放在不同文件夹”不等于模块化。需要同时落实接口、数据所有权、依赖方向、配置与状态归属，以及可执行的边界测试。

## 2. 模块职责与数据所有权

保留原模块 ID 以便追踪需求；ip-profile 只是历史编号，实际是账号配置，不代表独立人设库。

| 模块 | 独占维护的数据/行为 | 公开给调用者的能力 |
|---|---|---|
| workspace-core | 品牌空间、身份授权、账号归属、公共审计基础 | 校验操作主体、品牌/账号/资源访问 |
| ip-profile（账号配置） | 账号 persona_prompt、平台表达要求、配置版本与范围偏好 | 获取确定的账号配置、提交合法设置变更 |
| source-inbox | 登记来源、本地文件引用、哈希/缺失状态、解析输入 | 登记/读取授权来源、查询文件状态 |
| knowledge-base | 知识卡、引用、素材包、检索与必用/排除约束 | 搜索授权资料、返回来源明确的素材包 |
| topic-planning | 选题、理由、创作简报 | 保存选题决定、输出版本化简报 |
| work-editor | 正文、候选修改、内容版本与附件引用清单 | 读取确定版本、保存草稿、提交候选/采用新版本 |
| agent-workflow | SOP/步骤、运行快照、状态、重试/取消与结果路由 | 启动/恢复运行、查询进度、接收候选产物 |
| review-delivery | AI 原报告、风险处置、人工批准、交付包与手动发布记录 | 请求预检、人工处置/批准、校验并导出、登记发布事实 |
| feedback-learning | 人工指标、AI 复盘、待采纳/已采纳经营结论 | 读取观测、保存复盘候选、人类采纳/撤回 |
| project-collab | 项目、任务组织、日历关联 | 组织已有业务对象，不直接修改其正文或批准状态 |
| agent-gateway | 外部 Agent/MCP 接入协议与调用来源识别 | 调用受限的应用用例，不直接写业务表 |

review-delivery 内部将预检、最终审批和交付导出分为独立组件；规则调整不得改写已批准状态。API适配器、Codex等执行器只产生结果，人工身份与批准权限由服务端用例校验。

## 3. 允许的依赖方向

- UI 页面 → 所属模块客户端/公开用例 → 领域服务 → 所属存储/工具适配器。
- HTTP/MCP/daemon 回传入口调用同一应用用例，不能在 handler 或 Skill 中复制审核与授权规则。
- 研究/创作编排调用资料、账号配置、作品接口；这些模块不反向依赖流程引擎。
- 审核读取作品与文件的确定快照；编辑器不依赖审核服务。内容变化产生新版本，原批准仍属于旧快照，交付时重新检查有效性。
- 复盘读取明确的发布/指标输入，输出建议；选题读取已发布的经营结论查询接口。使用发布记录/知识查询端口或编排层组装，避免选题、复盘互相导入实现。
- 项目看板显示来自其他模块的状态，不成为其他模块运行的强制前置。
- 可选插件依赖公开接口；核心模块不得依赖插件。浏览器核心业务不得导入 Electron IPC。

Go 用消费方所需的小接口和集中依赖装配避免 import cycle；前端按模块公开导出限制深层导入。不要求把上游所有目录一次重构，约束先覆盖新增内容模块及其上游适配入口。

## 4. 禁止的跨模块访问

1. 禁止直接调用另一个模块的私有实现、数据库 repository、内部 sqlc query 或私有前端 store。公开接口变更必须检查所有消费者。
2. 禁止模块直接更新其他模块拥有的表；跨模块用例由应用层协调。确需同库事务时传递受控事务上下文，通过各自接口操作，不向调用者暴露原始 SQL 能力。
3. 禁止“为了复用”把业务规则都堆到 utils/shared/common 或一个全局状态库。共享层只保存稳定的基础类型、校验工具和通用 UI 原语。
4. 禁止前端页面直接拼接 Codex/模型参数或解析原始 AI 报告；归一化与 schema 校验在执行适配器/报告入口，页面只消费领域契约。
5. 禁止改变公共字段含义、删除字段或复用枚举值而不迁移调用者和历史数据。兼容变更优先新增可选字段，破坏性变化需明确版本与迁移路径。
6. 禁止全局缓存省略 workspace/account/config revision 等必要键，禁止用共享提示词或跨模块回调隐式扩大权限。

数据迁移仍遵守上游无新增外键/级联、并发索引独立迁移约束。模块化不是数据库物理隔离，也不能取代运行时沙箱。

## 5. 防止改 A 破坏 B/C/D 的验证层

| 层 | 检查内容 | 触发范围 |
|---|---|---|
| 依赖边界检查 | 禁止路径导入、循环依赖、核心依赖插件/桌面、跨模块私有访问 | 每次新增模块/导入或修改公开出口 |
| 模块行为测试 | 模块公开用例的成功、失败、权限与状态转换 | 修改所属模块时 |
| 消费者契约测试 | 所有调用方仍接受输入/输出、错误码和状态语义 | 公开接口/报告schema/公共类型变更时 |
| 数据迁移测试 | 旧版本数据可读、迁移可重跑或按设计恢复、历史状态不伪改 | schema/持久化格式变更时 |
| 关键流程冒烟 | 账号设置 → 素材 → 创作 → 人审 → 交付/记录 → 复盘 | 每次集成；按已实现阶段覆盖，不能假报未实现环节通过 |
| 真实执行集成 | Codex/搜索/文件权限等真实环境行为 | 相应适配器、隔离或外部协议改变时；不因每次文案修改调用模型 |

Go 编译能发现直接 import cycle，但不能发现所有越界；需约束包依赖和私有存储入口。TypeScript typecheck 不能验证运行时 JSON/旧数据，因此须有 schema 与消费者契约测试。工具可沿用已有 lint/test/build，再增加项目内边界检查，不预先声称某个命令已存在或已通过。

## 6. 变更影响示例

| 修改 | 主要模块 | 必须额外检查 |
|---|---|---|
| 调整账号人设提示词字段 | 账号配置 | 旧运行快照可读、启动界面读取、账号间隔离 |
| 修改素材搜索/排序 | 知识库 | 必用排除、权限过滤、选题/研究的素材包契约 |
| 增加预检规则 | 审核预检 | 报告 schema、处置页面、失败状态、原报告留存；最终人审不能被规则自动绕过 |
| 更换 Codex 接入方式 | 执行适配器 | 超时/取消/重传、输出契约、无令牌复制、运行资料范围；编辑器无需理解新协议 |
| 修改导出格式 | 交付 | 批准快照校验、文件变化/缺失、不得自动写已发布；复盘输入格式保持稳定 |
| 修改公共权限服务 | workspace-core | 所有内容模块的权限负例与关键流程，不能只测该服务 |

每次任务/PR 写明“所属模块、公开契约是否变更、消费者、迁移、已运行检查与未覆盖项”。发现新依赖时先更新影响表，再扩大检查；回归不是无差别运行所有真实模型。

## 7. 纳入现有任务的方式

- LT-001～002：核对新增模块位置、上游公开入口与工具能力，不进行大规模上游重构。
- LT-009～010：首个品牌/权限功能落地时建立依赖边界清单；业务代码不能通过全局共享 store/SQL 绕过权限。
- LT-011～016：每项交付所属数据接口和消费者契约检查；共享配置变更纳入影响分析。
- LT-017～024：文件访问、来源与检索分别通过公开用例衔接，不让页面直接读本机路径。
- 后续 EP 阶段细拆时必须包含本阶段的依赖边界/契约回归任务，公开接口冻结前不得并行修改多个消费者。

自动边界检查的初次落地见任务 ARCH-01/02；它们是功能实现前的新增工程任务，不将本文编写标成检查已通过。
