## 2. 开发者应能直接回答的问题

1. 谁对哪个品牌/账号/作品版本做了什么，实际成功还是失败？
2. 请求在哪个组件或 SOP 步骤失败、耗时在哪里，失败是否影响最终交付？
3. 当时使用哪些配置、素材引用、执行器和工具，哪些输入已经不可复现？
4. 修改后怎样重现旧故障、验证修复并检查相关功能未被破坏？

开发面板可只对有权限的开发/拥有者开放；普通运营界面仍能查看有权访问对象的操作记录和可理解错误。不能因为“开发模式”而允许跨品牌查看私有内容。

## 4. 两种日志分开存储、关联查看

### 操作/审计记录

覆盖账号设置、人设提示词修改（记录版本而非全文）、素材登记/重新关联、创作开始/取消/重试、素材要求与范围选择、作品编辑/采用、风险处置、最终审核、导出、手动发布/指标记录和复盘采纳等动作。

字段至少包括 event_id、发生/接收时间、actor_kind/id、workspace/account、对象类型/ID/版本、action、outcome、reason_code、operation_id、trace_id、run/attempt/step引用。成功和失败不可混淆；数据库关键变更与审计/outbox一致提交，不能业务已失败却记成功。

最终批准与真实记录审计采用追加记录，不允许普通诊断清理改写/删除。更正通过新事件表示。没有请求上下文的后台任务也有系统身份与关联 ID。

### 技术日志

结构化字段：时间、severity、component、operation、error_code、safe_message、trace/span、run/step/attempt、duration、retryable、result_class、client/build/config版本。堆栈仅向授权诊断视图显示，统一截断/脱敏。原始模型 stdout/stderr 须经适配器过滤，不直接作为可公开日志。

日志不得包含登录令牌、Cookie、Authorization、API key、连接密码或默认复制私有正文；文件路径/URL查询参数/用户输入也须按字段策略脱敏。调试日志与审计保留期分别配置；普通日志滚动清理不能删除仍需保留的审批证据。

## 5. 错误、追踪与指标合同

统一错误包含稳定 code、用户可读说明、组件/步骤、retryable、trace_id 和允许的下一动作。区分授权、输入冲突、文件缺失/变更、数据库不可用、网络/搜索、客户端认证/额度、超时/取消、输出 schema 与内部异常；不把权限失败全部变成“网络错误”。

operation_id 表示一次用户意图；一次网络请求有 request_id/trace，多个请求和重试归同操作但保留不同 attempt。跨 HTTP、队列、WebSocket、daemon、工具调用和结果回写显式传递父子关系；不接受客户端提供的 ID 作为身份授权。断线重连和重复投递保留 event_id/序号以去重和识别缺口。

使用供应商无关的 OpenTelemetry 追踪接口/上下文作为实施方向，具体 SDK 版本与现有 slog/前端诊断的适配在任务中核验；不要求先部署外部采集平台。外部模型服务无法提供内部 span 时，只展示本系统调用边界及耗时，不虚构对方内部过程。

指标覆盖请求错误率/延迟分布、队列等待、步骤耗时、重试/取消、日志丢弃和最后心跳。分位数样本不足要显示样本量，指标标签只用有限组件/动作/结果枚举，不把用户ID、完整URL或trace作为高基数字段。阈值和保留容量为可配置值，首次实现记录默认值及依据。

## 6. 输入快照与安全复现

保存账号配置版本、实际 persona_prompt 的受控业务引用、SOP/Skill/规则/执行器版本、source_scope、必用/排除ID、授权清单、素材哈希、模型参数、预算/超时和产物引用。私有正文保存在原业务存储，不在日志里重复。快照遵循账号权限，权限撤销后复现不能越权读取。

文件仍由操作人手动管理，不新增自动媒体副本、扫描或监听。旧文件缺失、覆盖或执行器不可用时显示复现缺口，不能承诺完全重放。

“复现”默认通过固定夹具/模拟执行器产生独立测试运行，不能自动重做审核通过、发布登记、长期记忆采纳等人工动作。真实模型重跑是显式选择，重新校验权限、工具和预算，生成新尝试；不能把点击查看旧日志变成付费执行。

## 7. 模拟与故障集

初期即支持固定种子/可控时钟、可保存场景和实际运行记录，覆盖：正常、慢响应、超时、取消、断线/重连、重复/迟到消息、文件缺失/改变、授权拒绝、数据库写失败、模型认证/额度/输出格式错误及搜索失败。

故障注入仅测试实例和模拟执行器可用，带明显 test/demo 标识，不可写生产审批/发布/指标数据。测试隔离不靠前端按钮；后端拒绝在非测试运行注入故障。回归样例关联原故障和模块，能在 CI 无真实模型条件下稳定重现。

## 8. 故障隔离与诊断自身健康

诊断不得成为所有业务模块的反向依赖。通过小的日志/追踪接口注入，无须业务模块知道面板实现；读模型只订阅/读取授权事件，不直接修改领域数据。缺省技术日志 sink 失败不能导致所有普通操作失败，使用有界缓冲并报告 dropped/error 指标。

必须区分技术日志失败与关键审计失败：最终批准、真实记录等需审计一致性的业务写入，在对应事务失败时明确失败，不能绕过审计继续宣称成功。日志存储满、面板掉线、时钟偏差、分页过期和流式消息丢失均需测试和状态提示。
