# Contributing to Loretide / AI 开发协作

> **本文件是摘要，不是权威。** 协作规则的权威来源是文档仓库（分支 `main`）的 `CONTRIBUTING.md`；本文件只是它在应用仓库一侧的摘要，供开发者就近查阅。本摘要对应的 CONTRIBUTING 提交为 `7926540cc`。两者冲突时以 `CONTRIBUTING.md` 为准，并以更新本摘要的方式消除冲突，不要反向修改 CONTRIBUTING。

本规范适用于所有人类与 AI 开发者。同一私有 GitHub 仓库的 main 保存项目文档，app-main 保存应用代码；应用 PR 必须以 app-main 为目标。没有明确代码仓库和基线提交的代码任务不得标记 ready。

## 领取与状态

1. 只领取带 ready 标签、无负责人、依赖已关闭的 Issue。
2. 主任务主动派发任务时，先在 GitHub 上完成预占再派发：移除 ready、添加 in-progress、设置负责人，并评论唯一执行者标识与实际线程 ID。派发早于预占会让同一 Issue 被第二个执行者按第 1 条合法领走。
3. 先评论执行者名称、工具、分支和开始时间；设置负责人并将 ready 改为 in-progress，然后重新读取 Issue 确认。共用 GitHub 账号时，评论中的执行者名称才用于区分 AI。
4. GitHub 标签/负责人操作不是原子抢锁。若发现其他执行者已领取或无法确定唯一所有者，停止修改，由主任务裁定。无写权限者仅申请领取，等待主任务确认。
5. 一个 Issue 一个执行者、一个独立分支/worktree。禁止同时改同一工作目录。
6. 阻塞时标记 blocked，记录复现、依赖和最小缺项；不要弱化测试或自行扩大范围。
7. 完成后创建 Draft PR，在描述写 Related to #编号（待审阶段不使用自动关闭关键字），添加 review-needed，移除 in-progress。
8. 主任务审查代码、证据及范围后决定补改或合并；合并并完成验收后由主任务关闭 Issue。执行者不自行合并、关闭 Issue。

## 每张 ready 任务必须具备

- 目标和不做事项；明确修改模块/文件及禁止范围。
- 代码仓库 URL、基线提交、分支要求；独立工作目录。
- 前置依赖、运行环境、独立测试数据库及端口要求。
- 可执行验收步骤、预期结果、浏览器证据（由用户手动验证产生；禁止 computer use / 自动点击验收）要求。
- 数据保护、回滚方式、交付文件要求。

## 开发约束

阅读 AGENTS.md、应用 CLAUDE.md、docs/11、docs/12、docs/13 和 docs/design/README.md。历史建议服从最新确认；TODO不代表无代码，已有代码不代表已验收。

UI完整复用Multica组件、布局、字体和颜色/字号token。真实AI执行器保持禁用，除非后续专门任务明确通过安全验收并授权启用。不得读取、复制或上传模型客户端登录凭据。

保留未提交修改；禁止reset/clean、整目录覆盖、真实发布或未经授权删除数据。测试使用独立合成数据，不得将清理型测试连接到开发业务库。各执行者独立数据库和端口；共享服务重启/故障注入必须由主任务排定互斥时间窗口。

## 交付

PR包含问题与修复行为、修改模块、实际测试结果、浏览器证据（由用户手动验证产生；禁止 computer use / 自动点击验收）、未覆盖项和回滚方法。记录写入records/并关联对应任务。禁止将密钥、数据库dump、运行日志原文、依赖目录或私人素材提交仓库。

GitHub负责任务与审查留痕，不自动唤醒AI。主任务通过各AI工具派发Issue链接并接收交付；后台轮询仅在实际配置后才能称为持续监控。
