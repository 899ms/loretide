# Spec Kit 交付流程

## 这份文件是什么

**一条已经跑通的流水线的操作规范。** 2026-09-13～14 期间，features 002、005～009 共 6 个特性按同一条流程从规格走到合并，这份文件把其中稳定下来的部分固定为仓库内规范。

它**不重复**以下三份文件，冲突时以它们为准：

| 权威来源 | 管什么 |
|---|---|
| [`.specify/memory/constitution.md`](../../.specify/memory/constitution.md) | 十条原则与停止条件。本文件的每一步都要过它的门，但不复述它 |
| [`ai-collaboration.md`](ai-collaboration.md) | 领取、预占、唯一执行者、独立分支/库/端口、Issue 状态流转。本文件只讲**规格到合并之间**那一段 |
| [`diagnostics-onboarding-contract.md`](diagnostics-onboarding-contract.md) | 新 content 模块必须接入哪些诊断面。本文件不重复清单，只在「实施」一步指向它 |

`README.md` 的测试政策（不写不跑 UI 单测、手动 UI 验收模板）同样是前提，本文件不复述。

## 三条铁律

这三条不是建议，是判定交付真假的标准。**任何一条被违反，交付无效，无论其余部分多完整。**

### 1. 跳过不算通过

一条 `SKIP` 的用例，在交付记录里记「按策略未执行」或「环境未配置，未执行」，**绝不记为 PASS**。

这条最容易在数据库背书用例上出事：`LORETIDE_DIAG_TEST_DATABASE_URL` 没设时整包退出码仍是 0，而 16 条用例一条都没跑。**退出码不是证据，用例名与 PASS/SKIP 计数才是**，所以带 DB 的包一律用 `-v` 跑并报出三个数字。

同类陷阱已在本仓出现过一次并被记录：`server/internal/handler/handler_test.go` 的 `TestMain` 在数据库连不上时执行 `os.Exit(0)`——**整个包以退出码 0「通过」而实际一个用例都没跑**。

### 2. 桩测试不代表目标平台

一条在 Linux 容器里绿的用例，不证明它在 Windows 上绿；一条用假可执行文件跑通的用例，不证明真实 CLI 能跑通。

实例：`internal/daemon` 三包在 Linux 上整理到 0 失败之后，同一提交在 Windows 上仍有 98 条红（PATH 上有真实 CLI、Windows 路径进 JSON 被转义等）。**「在我这台机器上全绿」是一句需要限定平台才成立的话**，交付记录里要写清楚跑的是哪个平台、哪个环境。

### 3. 模拟不代替真实

16 个模拟场景全绿，只满足 D13-V12 三条子句里的一条。真实执行器按 constitution 原则 IX 保持禁用，因此相关证据一律记「未执行（constitution 原则 IX）」——**不写「N/A」、不留空、不用「暂不适用」代替**，这三种写法都会在汇总时被当成没有问题。

**不存在一个可以在真实执行器未跑的情况下达成的「全绿」状态。** 任何汇总口径若能显示这样的全绿，是那个口径错了。

## 流程

```text
specify ─→ clarify ─→ plan ─→ tasks ─→ analyze ─→ Draft PR（规格）─→ 主任务审查合并
                                                                          │
                                                                          ▼
                    实施分支从 app-main 起 ─→ 先写测试确认失败 ─→ 实施 ─→ 验证
                                                                          │
                                                                          ▼
                              Draft PR（实现）─→ 主任务审查合并 ─→ 对照表与文档仓库回写
```

### 1. specify

产出 `specs/<NNN>-<short-name>/spec.md`。

- **Current State 一节以代码为准。** 逐条核实并给出文件与行号；与既有文档冲突时**写代码是什么样，并把文档的错处单列出来**。特性 008 就是这样发现对照表 §5 有三条描述与代码不符的。
- 不确定处标 `[NEEDS CLARIFICATION]`，**最多 3 条**，按影响排序（范围 > 安全 > 体验 > 技术细节）。
- **写完立即提交并推送**（`docs(spec): initial spec draft`）。主任务以分支出现为信号开始读，不必等 clarify 结束。

### 2. clarify

- 问题**一次性全部贴在会话里**，每条带选项表与**推荐值**，不自问自答。
- **推荐值即暂定值，写进 Clarifications 与对应 FR，不阻塞后续阶段。** 主任务裁决与推荐值不同时，改动范围应当局限在一条 FR 与它对应的任务——如果不是，说明那条 FR 写得不够独立。
- 裁决回写后，spec 内不应再有「暂定」字样。

### 3. plan

产出 `plan.md`、`research.md`、`data-model.md`、`contracts/`、`quickstart.md`。

- **`plan.md` 的 Source Code 清单是实施阶段的改动白名单**，见第 7 步。
- `research.md` 记决策、理由与**被拒绝的更简方案**。写不出被拒绝方案的决策，通常是还没想清楚。
- Constitution Check 逐条判定，N/A 也要写明为什么 N/A。

### 4. tasks

产出 `tasks.md`。

- 每行匹配 `^- \[ \] T\d{3}( \[P\])?( \[US\d\])? `，编号连续、无重号、无缺号。**不要用 `T008a` 这类编号**，它不匹配模板约定。
- 每条任务标注它覆盖的 FR / SC。**没有任务覆盖的 FR 或 SC 是 analyze 会抓的覆盖缺口。**
- 「先写的测试」明确标注**先写、且要确认它红**。

### 5. analyze

只读，产出报告。**HIGH 及以上自行整改**，整改后在 PR 正文贴整改后的最终表并标注每条的状态。

最值得抓的一类问题：**FR 对外承诺了实现做不到的事**。特性 009 的 FR-011 原文写「任何记录最多被实际派发一次」，而 data-model 诚实地记了「已派发、标记前崩溃」这个关不掉的窗口——两份产物互相矛盾，且矛盾方向是对外超额承诺。这类必须在规格阶段改掉。

### 6. Draft PR（规格）

base `app-main`，标题 `docs(spec): <NNN> <短描述>`。正文含 Current State 的关键发现、Clarifications 裁决表、analyze 最终表、未验证项（**纯规格 PR 通常是「未运行任何构建、测试或脚本」**）。

主任务审查合并后才进入实施。

### 7. 实施

- **分支从 `app-main` 新起**，不在规格分支上继续。
- **按 `tasks.md` 顺序执行**；标了「先写」的测试先写，**并确认它确实失败**（编译不过也算失败，但要说明）。
- **改动限 `plan.md` 的 Source Code 清单。** 需要动清单外的文件时——例如共享测试夹具——**照做但在 PR 正文单列出来并说明为什么另一条路更差**。特性 009 动了 `store_integration_test.go` 的迁移范围，替代方案是复制一份会漂移的夹具。
- 规格未覆盖的决定**停下来问**，不要自行扩范围。

### 8. 规格被事实推翻时

**在实现 PR 内修正规格，并在正文单列一节「规格修正」。**

不是所有规格都会被推翻，但被推翻时**改规格，不要遮掉**。两个真实例子：

- 特性 009 的规格写「`SKIP LOCKED` 与租约缺一不可」。变异验证删掉 `SKIP LOCKED` 后**全部用例依旧绿**——真相是租约单独保证正确性，`SKIP LOCKED` 只买不阻塞。这是一处真实的测试缺口，补了针对性用例关掉，同时把 `contracts/` 与 `research.md` 里那句话改成变异实际证明的说法。
- 特性 009 的 data-model 列了 `workspace_id` 列，但 `DispatchItem` 四个字段里没有东西能填它。加字段与删列两条路都偏离规格，选了偏离更小的一条，并把选择与理由写回 data-model，标注「实施期修正」。

**判断标准**：规格与实现不一致时，谁对就改谁；两边都说得通时改规格更小的那一处；**任何一种情况下都不允许让文档停留在已知错误的状态**。

### 9. tasks.md 回勾

**默认回勾。** 每个实施任务交付后勾 `[x]`。

**真正没执行的项保留 `[ ]` 并在行末注明原因。** 一条任务里有子项没真跑，整条不勾——特性 009 的 T021 就因为 `pnpm typecheck` 全部命中 turbo 缓存（本特性未改任何 TypeScript，那不是一次真实的类型检查）而保留未勾。

按 constitution 原则 X：**勾选只表示该实施任务已交付，不表示已合并，也不表示主任务已验收。**

### 10. PR 正文交付格式

实现 PR 必须含以下各节，缺一节视为交付不完整：

| 节 | 内容 |
|---|---|
| **改动与用途** | 逐文件一行，说清这个文件为什么必须改 |
| **实际命令与退出码** | 表格：命令、退出码、结果。带 DB 或带平台差异的包**必须给 PASS / SKIP / FAIL 三个计数**（铁律 1） |
| **变异验证** | 删掉规则、确认对应用例变红、随后还原，逐条列出变红的用例数。**「写完看绿」不算验证** |
| **未验证项** | 按策略未跑的、跳过的、没条件跑的，逐条写清楚。宁可多写一条，也不要让读者以为跑过 |
| **UI 影响** | 无改动写「无」；有改动按 `README.md` 的模板列出受影响界面 |
| **手动 UI Todo** | 同上，`README.md` 的模板 |
| **回滚** | 具体命令；涉及迁移时写明 `.down.sql` 需要另跑，并说明是否实测过可逆 |

### 11. 回写

合并后回写 [`diagnostics-acceptance-mapping.md`](diagnostics-acceptance-mapping.md)：

- 引用**实际**运行结果，不是预期结果；
- 计数按第 2 节各行**重新统计**，不要只改总数；
- **只有真的通过才改状态。** 一条子句在当前政策下不可能通过（例如真实执行器实测），就明写它不可能通过并保留不闭合，不要因为其余子句都绿了就把整条标为满足。

文档仓库（分支 `main`）的卡片勾选与检查点判定**不在本仓完成**，由主任务执行（constitution 原则 X）。

### 12. 新端点必须有路由存在性用例

handler 用例经 `httptest` 直接调用处理函数，**证明不了端点已挂到 `router.go`**。2026-09-15 的 LT-011 / LT-012 交付了 8 个账号端点、handler 用例全绿、两次审查通过，合入后浏览器一个都打不到——它们从未注册。规则：凡新增 HTTP 端点，同一 PR 必须包含一条经真实 router 的用例（至少断言路径已注册、且未登录/非成员经中间件被拒）；PR 正文「验证」表要单列这一条。审查方在合并前 `grep` 一次 `router.go` 里的处理函数名，零命中就退回。

### 13. 上游 Multica 代码：默认不碰，SOP 需要时可以改，但要单列提出来

「不碰上游代码」不是绝对约束（用户 2026-09-15 明确）。规则：

- **默认不碰。** 风格、现代化、顺手修都不构成理由；`go-modern-guidelines` 等 skill 永远不是改上游的依据。
- **SOP 需求确实需要时可以改**（例如接线、扩一个字段、放开一个校验），条件是：最小侵入；放在**独立提交**里，提交信息以 `upstream:` 开头；PR 正文单列一节「**上游改动**」，写明改了哪个文件、为什么 SOP 没它不成立、有没有不碰上游的替代及为何不选、回滚方式；能加测试自证「其余行为逐字节不变」的必须加。
- 审查方按这一节单独审：理由不成立就退回，改成不碰上游的做法。
- 与上游未来合并的冲突风险由这一节承担记录，便于日后 rebase 时定位。

## 变异验证怎么做

删掉一条规则 → 跑测试 → 确认对应用例变红 → **立即还原**。每处独立做，不要同时改两处。

**一处变异没变红，说明那条规则没有被任何用例保护**，不是变异写错了。正确反应是补用例，不是换一个更容易红的变异。

## 常见失败模式

| 症状 | 实际问题 |
|---|---|
| 整包退出码 0，但没人看用例数 | 铁律 1。带 DB 的包用 `-v` 跑并报三个计数 |
| 「本地全绿」 | 铁律 2。写清楚是哪个平台、哪个环境 |
| 模拟场景全绿就标 V12 通过 | 铁律 3 |
| FR 承诺了实现做不到的事 | analyze 该抓而没抓。规格阶段改掉 |
| 规格与实现不一致，留着不管 | 第 8 步。改规格或改实现，不允许停在已知错误 |
| 改了清单外的文件不说 | 第 7 步。照做，但单列说明 |
| handler 用例全绿但浏览器打不到 | 第 12 步。端点没挂到 router；要路由存在性用例 |
| 改了上游文件却混在功能提交里没说 | 第 13 步。独立提交 + PR 正文「上游改动」一节 |
| 变异不变红就换个变异 | 补用例，不要换变异 |
