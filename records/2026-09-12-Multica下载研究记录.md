## 结论与纠正

- 基础平台可复用，适合先以任务模板、Skill 与插件面板制作个人内容原型；完整作品/审核/人工指标/AI 复盘闭环需要新增业务模块，不是单纯换皮。
- 直接派生 Multica 应沿用 Go + Next.js，需重写之前 FastAPI/Vite 的工程映射。用户本次允许下载研究，并不等于已完成底座迁移或自动批准部署。
- 当前许可证是带附加条件的 Multica License。内部使用、对外托管、商业分发与品牌修改的条件不同；报告提供指定提交原文，不将其称为普通 Apache-2.0。
- Codex 原生 app-server 调用路径存在，但 Multica 的任务环境还会链接认证文件，Windows 链接失败可回退复制；不能声称原样采用它就满足本项目“不复制登录凭据”的约束。
- 有工作区 API 授权不等于有文件系统沙箱；各目标 Agent 的默认权限仍需改造与验收。
- 独立 Gemini CLI 和完整 API 工作流执行器不能算已具备。当前模型 API 包服务于辅助调用，Issue revision 不能替代不可变作品版本。

## 追加对话：为什么界面只有 Skill，没有插件

用户问：“Multica 上有插件吗，我只看到 skill”。

再次读取固定提交 3551e72e76d2c276e550b668303646d1280fb1e2，沿 Web settings 页面 → SettingsPage → PluginsTab 核对真实挂载，确认插件入口受 plugins_v1 开关控制，前后端回退均为 false。后端注释说明插件目录/管理 API 仍用于内部试用；开关开启后 owner/admin 可管理，其他成员只读。SDK README 的 Settings → Plugins 路径遗漏了这一开放条件，之前研究建议未充分体现该限制，已修正。

核对官方 Skills 页面，确认 Skill 是 SKILL.md 加可选脚本、模板及参考材料；当前文档导航没有 Plugins。没有核验用户运行实例的版本与开关，不能断言其账号为何不可见，也不把源码实现称为已普遍开放的插件市场。
