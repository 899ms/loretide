## 用户要求

用户明确将“隔离空间、不绑定单一 AI 供应商”作为核心架构，要求 Pi、OpenCode、Codex、Claude Code 或 API 均能切换驱动工作台。

## 本轮决定与影响

1. 保留 Easel-For-Hermes 代码基准，推翻此前 Hermes 固定默认的限制：Hermes 仅为可选适配器，其他执行路径无需经它中转，核心启动不依赖其安装。OpenClaw 仍完全移除。
2. 拆分业务服务、空间授权与上下文、通用执行接口、Agent 适配器和 API 执行器。API 执行器通过模型协议适配器与受限工具循环完成任务；不能把模型接口直接当成完整 Agent。
3. Pi、OpenCode、Codex、Claude Code、API 均为交付目标；之前已要求的 Gemini 与 Hermes 保留为可选路径。逐路径记录开发/验收状态，不声称目前已经兼容。
4. 将首版从固定个人工作区扩为可创建、切换的个人隔离空间，每个空间独立 IP、资产、经营记忆与执行配置。该范围按用户最新“隔离空间”要求作实施细化；空间内多 IP 与团队协作仍后续开发。
5. 明确无缝切换指业务资产与工作流连续：以版本化上下文、阶段成果与交接摘要接续，不能保证不同客户端内部会话或推理状态直接迁移。
6. 空间隔离约束适用于全部执行器，覆盖数据库、文件/进程、工具、会话、缓存、事件、连接授权与子进程；客户端不满足策略时阻止任务。具体 Windows 隔离机制仍须 T-01 选定并验收。
7. 沿用人工发布、人工真实记录、AI 复盘及正式作品版本等业务约束。

## 后续澄清：代码底座与 Agent 运行时

用户问：“现在是不是以 Pi、OpenCode、Codex 还是 Claude Code 或者 Hermes 为运行时作为底座？”

答复依据：本轮重新读取 07 的核心决定及 03 的架构目标。代码底座仍是 Easel-For-Hermes 的 React/TypeScript/Vite 与 Python/FastAPI 工程；业务工作流、隔离空间和正式作品存储由工作台管理。Pi、OpenCode、Codex、Claude Code、Gemini、Hermes 是可选择的 Agent 执行器，不选其中一个作为不可替换的核心。具体任务实际通过选定执行器运行；直连 API 则使用工作台 API 执行器的受限工具循环。

这要求从现有代码中抽取并改造 Hermes 耦合，并非上游代码已天然满足。当前没有选定必须安装的 Agent 运行时，也没有完成运行时接入。本次只是澄清已确认架构，未改变产品范围或新增应用文件；相关设计文件及用途见上文关联表。

## 后续对照：是否与 Multica 一样

用户问：“和 multica 一样吗？”本轮重新阅读 Multica 官方运行时文档及安全模型。结论为：可替换 Agent、本地 daemon 领取任务并回传结果的架构思路一致；代码底座、内容经营领域与具体隔离实现不能等同。

纠正此前可能引起误解的“安全调用方案”表述：由本地客户端管理登录不等于任务拥有文件系统沙箱。Multica 官方明确默认继承 daemon 用户权限，不保证文件系统隔离；独立运行目录、状态和 API 令牌也不能替代操作系统边界。Windows 上主动启用 Codex 原生沙箱有文档所述例外，不能泛化至所有执行器。

已将这一边界与一手来源补入 [07 核心架构](../docs/07-隔离工作空间与可替换AI执行架构.md)的“与 Multica 的关系”，本记录保存对话详情与更正理由。未修改应用代码，未执行任何 Agent 或安全测试；原文档检查数量是此前快照，本次仅核对追加内容。

来源：[Multica 运行时](https://multica.ai/docs/daemon-runtimes)、[Multica 安全模型](https://multica.ai/docs/security-model)。

## 术语说明：本机 daemon

用户问：“本机 daemon 是什么？”此处指运行在用户电脑后台的执行服务，可在产品中称为“本地执行助手”。它连接工作台，领取授权任务，准备受限上下文，启动用户选择的 Agent 客户端，并回传进度、结果及失败状态。它自身不是 AI 模型，不负责创作推理，也不天然等于安全沙箱。

例如：用户在网页发起正文创作 → 本地执行助手领取任务 → 启动所选 Codex/Pi 等客户端 → 客户端通过其配置的模型完成任务 → 助手将候选结果交回工作台入库。前提是相关适配器已经实现且客户端可用；当前项目尚未实现此流程。

若工作台部署在远程服务器，本机执行助手负责连接用户电脑上的 Agent；电脑关机、休眠或服务未运行时，本机任务不可执行。若工作台后端也运行在同一台电脑，可由其 Worker 承担该职责，不必为了这个名称再单独安装一个产品。它可以随应用启动，也可作为后台服务运行，具体打包与自启动方式尚未确定。

本次只解释现有架构术语，未安装后台服务、开启自启动或修改系统配置。关联文件仍为上文的 07 核心架构与 03 技术设计，本记录保存问题和说明。

## 后续对照：Orca 与截图中的用量面板

用户提供 Orca 仓库链接与用量截图，询问是否一样。本轮读取 Orca 仓库 README、用量说明及运行方式文档。截图可见 Codex、Claude、Gemini 账号/用量状态，但不据此验证本机客户端登录、实际额度或安全配置。

结论：在统一承载并选择本地 CLI Agent 这一层，与本项目的可替换执行器设计属于同类模式；本项目并未更换为 Orca 代码底座。Orca 官方 README 描述 Codex、Claude Code、OpenCode、Pi 并行运行及独立 Git worktree；本项目管理内容空间、素材、作品版本、审核与反馈，并额外定义自己的 API 执行契约。

Orca 本地桌面模式让 Agent、终端和界面在同一台电脑运行；远程模式还可由独立运行主机管理进程。本项目所称“本地执行助手”是这类本机执行管理职责，可以合入本地后端，无须因为 daemon 名称而强制单独安装产品。

截图对应账号与用量显示这一产品层。Orca 文档称显示本地用量状态、限额窗口及重置时间，并提供未知/加载/未登录等状态；其更新受本地状态刷新影响。该文档描述不等于对全部实现源码的审计。本项目可以设计同类面板，但用量读取、窗口口径与账号管理须逐客户端实现；不能用 API 成本估算冒充订阅剩余额度，也不能把模型选择等同于账号切换。此问不自动授权读取登录文件、切换账号或兑换额度。

普通 Git worktree 是代码目录与分支的分离，不能单独证明系统级文件/进程隔离。Orca 文档另有按工作空间配置 VM/容器环境的模式，不能据截图推断当前模式。项目的隔离验收仍按 07 执行。

本次仅追加本记录，用于保存对照结论与截图含义；07 核心架构和 03 技术方案继续作为开发要求，未新增已实现能力。

来源：[Orca 仓库](https://github.com/stablyai/orca)、[用量与限额](https://www.onorca.dev/docs/agents/usage-tracking)、[运行方式](https://www.onorca.dev/docs/ways-to-run)。

## 逐步核对：两者是否都是领取任务、启动 Agent、回传结果

用户引用“领取任务和授权素材 → 启动所选 Agent → 将进度和结果交回工作台”，要求确认 Multica 与 Orca 是否都沿此路径。

本轮核对结论：在接收任务、调用 Agent、展示/保存输出这一抽象层面相同；不能把两者的实际调度协议都描述成 daemon 从服务器领取队列任务。

- Multica 官方明确采用 daemon 连接服务端、领取 run、启动本机工具并回报结果，直接对应上述三步。
- Orca 的典型本地会话由用户在工作树中选择 Agent，Orca 启动 CLI 并显示终端输出，结合终端状态序列与 hooks 跟踪生命周期；不要求每次先向独立服务器领取任务。其远程 server 模式由运行主机持有终端与 Agent 进程，客户端展示和控制。
- “授权素材”是本项目要落实的输入权限约束，不意味着两款产品默认只能访问提供的材料。“回传结果”也不意味着自动成为本项目带版本、引用和审核状态的正式作品；结构化校验与入库由本项目额外实现。

新增读取的 Orca 会话文档还描述了默认全自主启动参数，不能把 worktree 分离称为操作系统安全边界。本次仅核对文档，不运行这些参数或更改本机设置。

本次只补充本记录；03/07 中本项目的任务账本、上下文授权和候选产物契约保持不变。来源：[Multica daemon 与运行时](https://multica.ai/docs/daemon-runtimes)、[Orca 会话生命周期](https://www.onorca.dev/docs/model/agents-sessions)、[Orca 运行方式](https://www.onorca.dev/docs/ways-to-run)。

## 推荐选择：内容经营工作台采用哪种执行路径

用户问：“哪种更适合我？”本轮重新核对项目 03/07 契约以及 Multica 运行时、Orca 会话官方文档。建议以 Multica 式的任务调度和执行回传为主，参考 Orca 的 Agent 选择与账号/用量界面；这是架构模式建议，不是改用 Multica 或 Orca 源码，也不变更既定 Easel-For-Hermes 代码基准。

理由：本项目的工作单位是带来源与版本的内容任务；研究、核查、创作和 AI 复盘需保存阶段产物、处理失败重试，并将结果送入正式作品和人工审核流程。中心任务账本加可替换执行器更直接承接这些要求。Orca 典型会话模式便于用户直接操控多个 CLI、终端与工作树，适合作为交互参考，但若以终端会话作为业务主体，仍需另补结构化入库与业务状态。

建议首版部署为同一台电脑上的 Web/API、持久化任务与本地 Worker，后台随工作台启动；先使用单机领取任务的模式，不为调度模式单独引入远程服务器或跨设备配对。未来远程 Web 再将执行器拆为本机 daemon。Agent 和 API 仍用统一执行契约，用户按任务选择，授权输入和候选输出由工作台验证。

代价与边界：任务派发、状态、适配器和结构化结果处理比单纯启动 CLI 更有开发成本；仍须实现隔离与能力验收，不能把 Multica 模式当作安全保证。本次建议尚未当作用户新的部署决定写入核心文档，未运行或安装应用。
