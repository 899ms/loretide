## 4. 发现、严重程度与处理条件

### F01：当前权威文档含过时实施状态（P1，固定规范前解决）

证据：docs/11 第21行仍要求 Tailscale/Linux 日常开发；app/docs/development/README.md 第5行明确当前为原生 Windows。docs/11 第128、132行及 docs/04 第261、265行仍写自动检查/诊断尚未实现；docs/13 第5行仍笼统声明全部尚未实现。应用已有相关模块与回归代码，不能由这些旧句子推出“需要从零重建”。

建议：校准当前有效文档的环境和状态栏，保留原需求与验收编号，分别记录“确认需求／已有实现／验证证据／仍未验收”。不把所有“尚未实现”批量改成完成，也不改写历史交付记录。根文档未提交增量应先经文档 PR 确认，再锁定 SHA；本轮没有代为修正文档。

### F02：跨分支引用不能保证新 clone/worktree 可读（P1，正式使用前解决）

app/LORETIDE.md 明确 main 与 app-main 不得合并历史。单分支 app clone 没有父目录 docs；本机 ../docs 可用不代表其他 Agent 可用。

建议新增项目自有来源清单，至少含 repo、main 分支、固定 commit、文件路径、必要文件内容哈希，以及映射到哪些约束。用 GitHub 固定提交链接或只读获取方式取得来源；本地缓存忽略入库、不保存 token。缺少必要来源或哈希不匹配时停止依赖该来源的生成，给出缺项，不静默使用旧缓存。获取私有文档使用已授权 GitHub 身份，不索取或输出凭据。

同一功能记录代码基线 SHA、文档 SHA、规格版本。后续明确用户确认可以修订已锁定规范，但要形成可审查变更，不能借锁版本拒绝最新需求。

### F03：协作规范存在镜像差异（P1，执行入口开放前解决）

根 CONTRIBUTING.md 已有主任务派发前预占、实际线程标识和派发失败处理；app/docs/development/ai-collaboration.md 未包含同样完整的前置派发段。两边仍用通用“浏览器证据”措辞，最新禁止自动 UI 验收规则则在 app/docs/development/README.md 中。

建议指定一份协作规则为权威，另一份作为注明来源版本的摘要；明确浏览器证据由用户手动验证产生。constitution 提炼不可突破的规则，入口文件链接到它和权威规范。保留 app/CLAUDE.md 的有效架构指导，不用生成模板整页覆盖。

### F04：Claude 集成文件会被 Git 忽略（P1，分发前解决）

app/.gitignore 第60行忽略整个 .claude/。实际 git check-ignore 命中 .claude/skills/speckit-specify/SKILL.md。因此本机安装成功仍可能导致其他 clone 完全收不到 Claude 指令。

建议仅允许纳入经过审查的 .claude/skills/speckit-* 文件，继续忽略本地设置、身份与会话文件；Codex 的 .agents/skills 与现有 .agents/worktrees 必须分别管理。禁止通过取消整个目录忽略或 git add .agents 来解决。生成路径与 app 已跟踪路径的本轮比较没有发现同名碰撞，但这不等于忽略规则正确，也不排除以后新文件冲突。

### F05：规格定位与 Git 分支不是同一状态（P1，并发执行前解决）

common.ps1 第79～110、160～221行：项目定位可由 SPECIFY_INIT_DIR 指定；规格目录优先取 SPECIFY_FEATURE_DIRECTORY，再读 .specify/feature.json。不会根据 task/issue-* Git 分支自动推导正确规格。

实测同时存在旧 SPECIFY_FEATURE=001-assessment-only 与新 DIRECTORY=specs/002-explicit-context 时，PathsOnly 输出的 BRANCH 与 FEATURE_DIR 可以不一致。PathsOnly 只解析路径，不证明该规格存在；完整 prerequisites 对不存在目录返回1。

建议每个 worktree 启动时校验 repo、真实分支、Issue、feature ID、规格路径与源码基线的一致性。工作树内只设所需上下文，不设用户级全局 SPECIFY_FEATURE* 环境变量；feature.json 保持本地忽略，不能共享绝对 Windows 路径。一个功能拆成多个 Issue 时，规格先进入共同基线，各执行者再基于同一规格版本工作。

默认递增规格编号来自本地目录；多个未同步 worktree 可能各取相同编号。初期由主任务登记功能编号并发布规格，避免把“各自脚本成功”视为全局唯一性证明。

### F06：默认 taskstoissues 缺少功能命名空间（P1，该命令不可原样开放）

生成的 speckit-taskstoissues/SKILL.md 第69～71行按 Issue 标题中的 T001 等局部任务编号去重，再跳过已匹配编号。功能 A 与功能 B 都有 T001 时，B 可能误认 A 的 Issue 并漏建。本结论来自模板算法审查，没有向真实 GitHub 执行创建实验。

默认流程也不具备本项目完整的 ready 前置条件、唯一执行者确认、文件边界、独立环境与主任务审查规则，并指定使用 GitHub MCP；本地有 gh 不等于该入口自然可用。

建议第一阶段禁用自动转换，由主任务按照既有流程建立有边界的 Issue。后续若启用，唯一键为 repo+feature ID+task ID，存储明确 Issue URL/正文标记；重复运行、关闭后重跑、跨功能同号均需定向验证。允许一个交付 Issue 关联若干内部任务，避免每条文档小任务都生成一张 Issue。ready 标签只能在依赖与领取条件齐备后添加。

### F07：默认 implement 执行整个 tasks.md（P1，执行入口必须限范围）

生成的 implement 第3、94、154、172、223行定义执行全部任务、允许 [P] 并行并勾选完成。这与一个 Issue 一个执行者的边界不等价。converge 可追加未完成工作，也不能据此授权扩大当前 Issue。

建议默认仅开放 specify、clarify、plan、tasks、analyze 等规划入口；执行需读取已领取 Issue 及其允许的 task IDs/文件范围。禁止“顺手完成”其他任务或只因 [P] 标记就派发 Agent。阻塞回到 GitHub 记录依赖，交付 Draft PR 与 review-needed，合并/关闭仍由主任务决定。

tasks.md 的勾选表示该实现任务已交付，不等于已合并或用户验收；关联 PR/Issue 提供证据。GitHub 是领取与审查状态源，records 保存证据；不要让各分支 tasks.md 成为第二个抢占系统。

### F08：测试模板需明确适配，不是 Spec Kit 强制 UI 测试（P1，模板落地前解决）

tasks-template.md 第12行把测试任务列为可选，第85行在可选测试段中给出先失败后实现的建议。不能把这些示例描述成工具硬性要求 UI 单测；也不能借“可选”取消现有必须保留的非 UI 检查。

项目规则必须写为：禁止编写或运行 UI 单元测试，本地与 CI 均适用；禁止 computer use/自动点击验收；不得通过更换扩展名或测试分类绕过。保留变更相关的非 UI 契约、Go、权限、模块边界、类型检查与构建。未执行的 UI 检查标记“按策略未执行，等待用户验证”，不能标记通过。

每项涉及 UI 的交付列具体页面/控件、操作、预期结果和用户确认状态；无 UI 影响则明确写无。模拟场景测试、静态门禁或构建成功不能替代真实模型安全验收。

### F09：生成模板不是现有架构的替代方案（P2，首个计划前适配）

plan-template.md 示例包含 src/、backend/、frontend/ 及多种示例技术栈。这些是待替换占位项，不是迁移指令。现有 app/CLAUDE.md 指定 server/ Go/Chi、apps/web Next.js、platform 分层等规则。

计划必须映射实际模块、公开接口、数据所有者、消费者、迁移及回滚范围。引用 content-boundaries.json 与检查器，不弱化边界以让新模板“通过”。既有功能仅在被修改时补规格；保留原 R/AC、D11/D13、ARCH/LT 编号，用映射关系承接，不另造一套产品目标。

### F10：软性提示与扩展 Hook 不是安全门禁（P2，启用扩展前解决）

部分生成入口仅在 constitution 存在时读取；空占位 constitution 不能证明项目原则已经建立。模板中的扩展配置解析失败会报告后继续，带 condition 的 Hook 可能交由其他执行器处理，不能把这些提示当作强制规则检查。

建议对缺失/占位 constitution、来源不可获取、Issue 无授权范围等关键前置条件设置明确停止行为。初期不安装额外执行、发布或 Git 自动化扩展。真实执行器禁用、独立数据库/端口、禁止模型凭据读取等要求保留在现有实现与流程检查中；仅写一段 constitution 不会产生运行时保护。

### F11：版本与本地定制需要升级策略（P2，首个升级前明确）

生成的 init-options、integration 和各 manifest 可记录版本/文件状态。本轮双集成 status 为 OK，受管理文件修改数0。以后有意修改指令或模板应登记本地差异；不能为了 status 归零覆盖规则或忽略升级冲突。

建议记录 CLI 来源版本、生成版本、集成选项与项目适配版本。优先采用所固定版本支持的覆盖机制，并验证其解析结果；若直接定制生成文件，保留差异清单和重放说明。升级先在临时目录生成与比对，再独立 PR，不让各 Agent 按自己的全局版本反复 init --force。

## 6. 推荐推进顺序

1. **规范校准（main 文档 PR）**：修正当前环境/状态的过时表述，合并最新验收禁令与协作入口说明。保持需求编号及未完成项可追溯。得到可锁定的文档提交。
2. **接入底座（app-main Draft PR）**：独立 worktree 初始化固定版本、Codex/Claude 集成、来源清单、constitution、模板与白名单忽略规则。只改配置/文档；暂不开放自动 Issue 转换。该步骤可以先在独立分支准备，但来源锁定依赖步骤1。
3. **一个新功能试点**：选择依赖已满足、边界明确的功能；规格→必要澄清→计划→任务→一致性检查→主任务发布/映射 Issue。执行者仍须领取后开始。小修复和在审 PR 不强行迁入新流程。
4. **评估自动化是否有价值**：试点证明两种 Agent 都能读取同一规格、保持边界和正确交付后，才考虑适配 taskstoissues/converge。收益不足则长期保留人工映射，不必为完整使用每个命令增加维护成本。

以上是建议的交付单元，**尚未新建 Issue、领取任务或发布 PR**。不要预先给它们编号，也不要把依赖未满足的工作标 ready。
