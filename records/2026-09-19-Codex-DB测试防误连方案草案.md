# Database test anti-misconnection: read-only implementation draft

## Status and boundary

Prepared on 2026-09-19 against PR #100 head
`e8ff309fb6d21b32e944d197a1ce9fe92d06edfd`.

This is a design draft only. It makes no repository, PR, CI, database, service,
or test-execution change. It is intended for a separate, explicitly authorized
task after PR #100 review. No conclusion below treats a database-name prefix,
loopback address, environment variable, or marker row as proof that a target
is isolated from a hostile or careless privileged operator.

## Verified current state

### The two package-wide entry points

- `server/internal/handler/handler_test.go:44`
  - Falls back from an unset `DATABASE_URL` to
    `postgres://multica:multica@localhost:5432/multica?sslmode=disable`.
  - On pool creation or ping failure, prints a skip message and exits `0`
    before `m.Run()`.
  - Uses static root-fixture identifiers (`handler-test@multica.ai`,
    `handler-tests`) and cleanup deletes by email/slug, not captured IDs.
- `server/cmd/server/integration_test.go:43`
  - Has the same default DSN and `os.Exit(0)` behavior.
  - Uses static root-fixture identifiers (`integration-test@multica.ai`,
    `integration-tests`) and cleanup deletes by email/slug, not captured IDs.

Consequences:

1. An unavailable default database can report a green package while every
   database-independent test in that package was skipped before execution.
2. An explicitly supplied but wrong reachable database can receive synthetic
   data.
3. Static fixture names permit cross-run collision and name-based cleanup is
   too broad for a test-isolation contract.

### Existing guards and CI

- `server/scripts/verify-handler-test-db.sh` currently requires the generic
  `DATABASE_URL`, `LORETIDE_HANDLER_TEST_DB`, and
  `LORETIDE_HANDLER_TEST_ROLE`; it checks the connected database/user against
  those values and only accepts a database name beginning
  `loretide_handler_test_`. It does not itself require opt-in, derive a run
  identity, check role attributes, or establish runner provenance.
- `.github/workflows/loretide-content.yml` has the PR #100 job
  `issue-98-account-profile-db`. It creates a run-specific database/role,
  separately checks role attributes and target-db ownership, migrates, then
  runs five handler and five `cmd/server` tests serially using one temporary
  database. It currently passes generic `DATABASE_URL` and the two legacy
  expected-name variables, but not an explicit test opt-in or per-suite
  identity.
- `.github/workflows/ci.yml` `backend-tests` exports a shared
  `DATABASE_URL=.../multica` and calls `scripts/test-go.sh --race --only
  regular`. That wrapper runs `go test` over all regular packages, including
  these two packages. `scripts/test-go.test.sh` only verifies wrapper argument
  construction.
- `internal/handler` has 293 test files; at least 253 refer to its package DB
  globals (`testHandler`, `testPool`, `dbfx`, or root fixture IDs).
  `cmd/server` has 53 test files; at least 33 refer to its package router/DB
  globals. The remaining 40 and 20 files respectively are candidates for
  database-free execution, but must be compiled/audited rather than assumed
  database-free from this text search alone.

## Desired behavior

### Default, database-free path

This is a required Phase 2 outcome, not a claim about the current tree:
`go test ./...` must compile and run the audited database-free tests in both
packages even when no database configuration exists. It must not invoke either
database `TestMain`, attempt a default DSN, or convert the whole package into
an exit-0 skip.

### Explicit database-test path

Phase 1 database-suite execution remains untagged because the 346-file test
classification has not happened yet. It requires all of:

```text
LORETIDE_DB_TESTS=1
LORETIDE_DB_TEST_DATABASE_URL=<credentialed DB URL>
LORETIDE_DB_TEST_DATABASE=<exact expected database>
LORETIDE_DB_TEST_ROLE=<exact expected role>
LORETIDE_DB_TEST_RUN_ID=<validated run identity>
LORETIDE_DB_TEST_SUITE=handler | cmd-server
```

`TestMain` for each suite must fail with exit status `2` before attempting a
connection when any required value is absent, malformed, or inconsistent. It
must never invent a DSN or read generic `DATABASE_URL`. The suite identifier is
fixed by code (`handler` or `cmd-server`) and must match the environment.

After connection, the test guard should query and compare:

- `current_database()` with `LORETIDE_DB_TEST_DATABASE`;
- `current_user` with `LORETIDE_DB_TEST_ROLE`;
- `rolsuper`, `rolcreatedb`, `rolcreaterole`, `rolreplication`, and
  `rolbypassrls` are all false;
- the connected role owns the *target* database.

The owner check demonstrates that the test role owns the target database; it
does not demonstrate that it owns no other database. These checks prevent
ordinary missing/miswired configuration from reaching tests. They are not an
unforgeable provenance or isolation proof: someone able to control the
database, role, and all environment values can imitate them. Runner-level
database provisioning and review of that privileged boundary remain required.

An optional run/suite marker created by the CI provisioner may be checked for
diagnostics, but must be described only as an additional consistency signal,
not as an authentication mechanism.

## Recommended implementation shape

### Phase 1: bounded safe entry, before classification

This is the smallest safety patch, not a DB-free classification solution. Its
exact initial repository scope is:

```text
server/internal/handler/handler_test.go
server/cmd/server/integration_test.go
server/internal/testutil/dbtest/guard.go            # new
server/internal/testutil/dbtest/guard_test.go       # new, pure
server/scripts/verify-handler-test-db.sh
server/scripts/test-go.sh
server/scripts/test-go.test.sh
server/scripts/test-go-db.sh                         # new
server/scripts/test-go-db.test.sh                    # new
.github/workflows/ci.yml
.github/workflows/loretide-content.yml
docs/development/testing-database-suites.md          # new
records/<new issue record>.md
```

It removes default DSNs and exit-0 skip behavior from the two DB `TestMain`
entry points. An untagged invocation of either package without full special
configuration exits nonzero before connecting. Generic `backend-tests` must temporarily exclude
these two packages and invoke them only through the dedicated DB wrapper/job;
otherwise its inherited generic `DATABASE_URL` would become a false implicit
opt-in. This bounded phase restores no standalone DB-free coverage for these
two packages yet; it prevents silent green and unsafe connection attempts.

Its dependencies are explicit: a dedicated runner job and the CI wrapper must
land in the same change as the TestMain behavior, or the generic wrapper would
fail every time it reaches either package.

### Phase 2: full DB-free classification migration

Add a `dbtest` build constraint to database-dependent test files and to the
two DB `TestMain` files. Keep database-free test files untagged. Do not use an
exit-0 package-wide skip as the selection mechanism.

Initial file range to inventory and classify:

```text
server/internal/handler/**/*_test.go  (293 files; 253 helper-dependent hits)
server/cmd/server/**/*_test.go         (53 files; 33 helper-dependent hits)
```

This touches up to all 346 files and is a separate large migration, not a
minimal patch. The first implementation must produce an audited manifest of
every tagged/split file and compile both packages in both modes. A
helper-reference search is an input to that manifest, not final classification:
a file can access the database without one of those globals, and a mixed pure/DB
file must be split rather than have its pure tests hidden behind the tag. The
read-only candidate and syntactic-mixed list is in
`Loretide-DB-Test-Classification-ReadOnly.md`.

Concrete changed/new files:

```text
server/internal/handler/handler_test.go             # dbtest TestMain/root fixture in Phase 2
server/cmd/server/integration_test.go               # dbtest TestMain/root fixture in Phase 2
server/internal/handler/**/*_test.go                # tag or split after approved audit
server/cmd/server/**/*_test.go                      # tag or split after approved audit
server/internal/testutil/dbtest/guard.go            # new shared opt-in/config/identity guard
server/internal/testutil/dbtest/guard_test.go       # pure config validation tests
server/internal/testutil/dbtest/fixture.go          # new unique suite fixture IDs + cleanup helpers
server/internal/testutil/dbtest/fixture_test.go     # no live DB; validates naming/config only
server/scripts/verify-handler-test-db.sh            # retain name or replace with generic verifier
server/scripts/test-go.sh                            # preserve DB-free default, never adds dbtest
server/scripts/test-go-db.sh                         # new explicit DB-suite wrapper
server/scripts/test-go.test.sh                       # update/add wrapper contract cases
server/scripts/test-go-db.test.sh                    # new fake-go/env refusal tests
.github/workflows/ci.yml                             # generic DB-free and dedicated runner jobs
.github/workflows/loretide-content.yml               # PR #100 compatibility env/tag changes
docs/development/testing-database-suites.md          # new operator/developer contract
records/<new issue record>.md                         # scope, evidence, residual limitations
```

Bulk-tagging all files would hide database-free tests and violate the desired
behavior. The classification list is read-only and deliberately separates
candidate results from implementation approval.

### 2. Make root fixture data unique and cleanup ID-scoped

Each `TestMain` must create a suite scope from the validated run ID plus a
fresh random component. It should capture, at minimum, the returned user,
workspace, runtime, and seeded-agent IDs.

Suggested setup/teardown contract:

```text
suite = { RunID, Suite, UserID, WorkspaceID, RuntimeID, AgentID }
setup:  INSERT ... RETURNING id for every root row; retain returned IDs.
cleanup: delete dependent optional rows using captured IDs;
         delete workspace WHERE id = captured WorkspaceID;
         delete user      WHERE id = captured UserID;
```

Do not run a pre-setup cleanup by static email or slug. Do not delete by a
name reconstructed from a run identifier. Existing `testutil.Fixture`
per-test `t.Cleanup` behavior is already ID-oriented for many helpers, but all
manual cleanup SQL in the two suites must be audited and changed where it
matches name, slug, or broad workspace criteria.

Use the unique names only for observability. Cleanup authority comes from the
captured database IDs, not from the uniqueness of the name.

### 3. Centralize hard opt-in and live identity checks

`internal/testutil/dbtest/guard.go` should expose a small API used by both
`TestMain` implementations:

```go
type Config struct {
    DatabaseURL, Database, Role, RunID, Suite string
}

func LoadRequired(expectedSuite string) (Config, error) // env-only, no I/O
func VerifyConnected(ctx context.Context, pool *pgxpool.Pool, cfg Config) error
```

`LoadRequired` is pure and unit tested. It reads only
`LORETIDE_DB_TEST_DATABASE_URL`, never `DATABASE_URL`. `VerifyConnected` runs
only after an explicit opt-in and an already chosen special URL. It uses
server-returned identity, not URL parsing alone, and reports the role
attribute/ownership mismatch without printing credentials. The caller converts
all configuration or live identity failures to a nonzero pre-`m.Run` exit.

Update `verify-handler-test-db.sh` to require the same opt-in/config contract
and invoke it from CI before Go starts. The shell check and Go check are
defense in depth with the same expected values, not independent proof.

### 4. Dedicated runner validation

Recommended steady-state CI has two independent GitHub-hosted jobs:

```text
handler-db-tests
  fresh runner -> native temporary PostgreSQL -> unique handler DB/role
  -> migrations -> verifier -> go test -tags=dbtest ./internal/handler
  -> JSON artifact -> guarded exact DB/role cleanup

server-router-db-tests
  fresh runner -> native temporary PostgreSQL -> unique cmd-server DB/role
  -> migrations -> verifier -> go test -tags=dbtest ./cmd/server
  -> JSON artifact -> guarded exact DB/role cleanup
```

Each job derives a database/role from the CI run identity *and its fixed suite
name*, validates decimal/run components before any privileged action, provisions
with a least-privilege login role, masks credentials, exports only
`LORETIDE_DB_TEST_DATABASE_URL` to its test step, checks the connected identity,
and performs an `if: always()` cleanup that re-derives and exactly compares
expected names before terminate/drop. A fresh independent runner plus
privileged provisioning is the isolation boundary; a loopback host or an
`loretide_*` prefix alone is not.

Migration is a separate CI sub-process in the already verified runner. It may
map `DATABASE_URL="$LORETIDE_DB_TEST_DATABASE_URL"` for exactly
`go run ./cmd/migrate up`; that mapping must be command-scoped and must not be
exported into the test command environment.

For targeted tests, a checked-in manifest of expected top-level names is passed
to `go test -run`; a JSON parser requires exactly one terminal `pass` per named
test and per discovered descendant, and treats missing JSON, missing test,
`skip`, or `fail` as a failure. For full DB packages, create an explicit suite
manifest or split into bounded manifests; do not equate one package-level pass
with proof that a selected test was executed.

## Compatibility changes required for existing CI

### PR #100 workflow (`.github/workflows/loretide-content.yml`)

The existing approved job can remain the short-term Phase 1 compatibility path without
new permissions. It must preserve the generated special URL and, before each
current command, set:

```bash
LORETIDE_DB_TESTS=1
LORETIDE_DB_TEST_DATABASE_URL="$database_url"
LORETIDE_DB_TEST_DATABASE="$expected_db"
LORETIDE_DB_TEST_ROLE="$expected_role"
LORETIDE_DB_TEST_RUN_ID="${GITHUB_RUN_ID}_${GITHUB_RUN_ATTEMPT}"
LORETIDE_DB_TEST_SUITE=handler      # handler command only
go test ... ./internal/handler ...

LORETIDE_DB_TEST_SUITE=cmd-server   # cmd/server command only
go test ... ./cmd/server ...
```

It must call the updated shell verifier with
`LORETIDE_DB_TEST_DATABASE_URL` before either suite. The migration line is the
only line that receives a command-scoped generic `DATABASE_URL` mapping. The
two current commands may share the PR-specific temporary database only as an
interim compatibility mode because they remain serial and have distinct suite
fixture IDs. The recommended later split is two runners/databases as described
above.

The existing JSON parser already rejects missing expected top-level tests and
descendant skip/fail; retain that behavior and add manifests only when the
scope grows beyond its current ten named tests.

### General backend CI (`.github/workflows/ci.yml`)

- Do **not** set `LORETIDE_DB_TESTS=1` or
  `LORETIDE_DB_TEST_DATABASE_URL` globally in `backend-tests`; that job's
  shared `multica` database is not the dedicated-suite runner contract.
- In Phase 1, change `scripts/test-go.sh` to exclude `internal/handler` and
  `cmd/server` from its regular package list, and run both through the
  dedicated DB wrapper/job. This is an explicit temporary coverage trade-off,
  not a claim that their DB-free tests already run by default.
- Only after Phase 2 classification may `scripts/test-go.sh` include those
  packages without `-tags=dbtest`, so audited DB-free files execute. That is a
  required acceptance gate for Phase 2, not current behavior.
- Add explicit, independent database-suite jobs/wrappers rather than silently
  relying on the existing global `DATABASE_URL`.
- Update `scripts/test-go.test.sh` to assert the default wrapper never injects
  the dbtest tag. Add `scripts/test-go-db.test.sh` cases for absent opt-in,
  missing required variable, wrong suite, and exact command construction.
- Preserve existing migrations only for jobs that actually need them; the
  DB-free default path should not need a database merely to execute handler or
  cmd/server pure tests.

Other database-using packages remain outside this narrow two-suite repair. The
general backend job's remaining database behavior must be documented as an
independent follow-up, not claimed fixed by this work.

## Acceptance gates for the implementation task

1. Phase 1: `go test` for either package exits nonzero before connecting
   when opt-in/config is absent or malformed.
2. Phase 1: generic CI does not reach either package with its shared generic
   database configuration; the dedicated jobs execute the required DB suites.
3. A controlled wrong expected database/role environment fails before `m.Run`.
4. In a dedicated CI runner, both suites verify connected identity/role
   attributes/target owner, migrate, and pass their explicit test manifests.
5. Root fixture cleanup queries use captured IDs; a seeded unrelated row with a
   similar email/slug is unaffected in a dedicated test regression.
6. JSON evidence proves every intended top-level and descendant test terminal
   action is `pass`; missing/skip/fail is red.
7. Final cleanup proves only the exact re-derived run/suite database and role
   were targeted.
8. Phase 2: `go test ./internal/handler` and `go test ./cmd/server` run the
   audited database-free subset with neither special nor generic database URL,
   no connection attempt, and no package-wide exit-0 bypass.

## URL parsing, transport, and redaction requirements

- The test guard must pass `LORETIDE_DB_TEST_DATABASE_URL` directly to pgx and
  not reconstruct a URL from host, port, user, or database fragments.
- It must reject URL query overrides that can change identity or routing after
  the supplied expected database/role was selected, including at minimum
  `host`, `hostaddr`, `port`, `user`, `dbname`, `database`, `service`, and
  `servicefile`. Treat unrecognized connection-routing keys as a hard error
  until explicitly reviewed.
- Multi-host URLs are not accepted in the first repair: reject more than one
  host, `target_session_attrs`, and host lists. A later explicit design may
  permit a reviewed topology, but cannot assume the first host is the target.
- Unix-socket connections are not accepted in the first repair: reject an empty
  host and percent-encoded or decoded absolute socket paths. The runner
  provisioner may use a local socket as its privileged admin transport, but the
  test role's URL contract must stay explicit and separately reviewed.
- Do not use a loopback hostname as proof of isolation. If CI chooses loopback
  for a temporary runner, it is only transport detail; connected identity and
  runner provisioning are still checked.
- Errors, logs, GitHub annotations, test names, and JSON artifacts must redact
  passwords and URL userinfo. Diagnostic output may name the expected database,
  expected role, suite, and run ID, but never emit the complete special URL or
  raw parser error if it includes one.

## Compile-without-TestMain check

The implementation task must prove test compilation separately from execution:

```text
go test -c -o <validated temporary path> ./internal/handler
go test -c -o <validated temporary path> ./cmd/server
```

`go test -c` builds a test binary and does not run `TestMain`; the validation
harness must create unique temporary targets, verify they are inside its
temporary directory before deletion, remove them after compilation, and report
that no database URL was supplied. This compile check complements, but does not
replace, dedicated-runner execution.

After Phase 2 tags are fully classified, repeat the same checks once without a
tag (database-free subset) and once with `-tags=dbtest` (database suite).

## Explicit non-goals and residual risk

- This design does not declare an environment variable, marker, prefix, or
  loopback address unforgeable.
- It does not protect against a malicious privileged CI/database operator;
  privileged provisioning remains the trust boundary.
- It does not change production database permissions, business data, migrations,
  services, UI, or PR #100 in this preparation task.
- It does not solve database-test isolation for every other package; it creates
  a pattern and fixes the two package-wide silent-exit entry points first.
