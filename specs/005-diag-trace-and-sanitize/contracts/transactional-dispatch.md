# Contract: 事务内登记 + 提交后派发

**本功能只交付接口与进程内实现，不落库、不新增迁移**（spec FR-017）。签名按可被持久 outbox 实现替换设计。

## 登记项

```text
{ id, kind, payload, idempotencyKey }
```

| 字段 | 作用 |
|---|---|
| `id` | 唯一标识，持久实现用作主键与去重依据 |
| `kind` | 路由到接收方 |
| `payload` | 载荷字节 |
| `idempotencyKey` | 防重放；与既有 `Receiver` 去重语义一致 |

## 两个动作

| 动作 | 时机 | 保证 |
|---|---|---|
| 登记 | 业务事务**内** | 生死与事务绑定 |
| 派发 | 事务**提交后** | 提交则派发或进入可见待派发；回滚则不存在、不派发 |

## 不变量

- 事务回滚 → 派发次数 **0**，且不产生任何「已成功」痕迹。
- 事务提交 → 派发 **1** 次，或处于可见的待派发状态；二者必居其一。
- 派发失败 → 可见（计入既有 `LogBuffer.Errors` / `Dropped`，不新增指标名），业务操作照常成功。
- 相同 `idempotencyKey` 重复派发 → 接收方不产生重复业务效果。
- 待派发队列有界 → 超出按既有「丢弃可见」口径处理。
- **关键审计不走本接口**：`Store.Audit` 在事务内写、失败即整体回滚的既有行为**不变**，不得因本接口而降级为「只计数」。

## 明确的限制

**进程退出会丢失未派发项。** 这是不落库的直接后果，已由 spec FR-010a 与 US3 验收场景 6 写成验收项。交付文档必须写明，不得声称已保证跨重启不丢失。持久落库版本列为后续任务。

## 可替换性

一个持久实现必须能在**不改调用方**的前提下替换进程内实现：登记落表、提交后由派发方扫描待派发行。四元组是它所需的最小集合，因此签名不需要变。
