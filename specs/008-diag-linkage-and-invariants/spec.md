## 规格修正：§5 的三条缺口描述与代码不符

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从一条审计事件落到它的技术追踪（Priority: P1）

排障的人在操作时间线上看到一条失败的审计事件。他点「查看追踪」，面板切到技术日志，并且**只**显示这条事件所属的那次追踪——不是全量日志，也不是上一次筛选的残留。如果这条事件没有可用的追踪编号，他会被明确告知「这条事件没有关联追踪」，而不是看到一屏无关的日志还以为那就是结果。

**Why this priority**: 这是 D13-V02 的核心动作，也是整张对照表里被引用最多的一条排障路径。当前实现会在 `traceId` 为空时**静默跳到未筛选的技术日志**，这比没有跳转更危险：读者会把别的事件当成本次故障的原因。

**Independent Test**: 把跳转目标的推导做成纯函数后，可在 node 环境下独立断言「给定一条事件 → 得到哪组筛选条件 / 或得到一个明确的不可跳转理由」，无需挂载任何界面。

**Acceptance Scenarios**:

1. **Given** 一条 `traceId` 与 `runId` 都齐备的审计事件，**When** 请求跳转，**Then** 得到一组筛选：技术日志、该 `traceId`、该 `runId`，且 component/severity/errorCode/from/until 全部清空、游标归零。
2. **Given** 一条 `traceId` 为空的事件，**When** 请求跳转，**Then** 得到「不可跳转」结果并附原因，**且不得**产生一组空筛选。
3. **Given** 一条 `traceId` 齐备但 `runId` 为空的事件，**When** 请求跳转，**Then** 仍按 `traceId` 跳转，`runId` 不参与筛选（追踪可以跨运行，缺运行号不该阻断）。
4. **Given** 上一次筛选留有 severity 与时间范围，**When** 跳转发生，**Then** 这些条件被清空，结果只受本次事件决定。

### User Story 2 - 判断「下一动作」是否真的可执行（Priority: P1）

面板给每条错误显示一个「下一动作」。读者据此决定做什么。这个动作必须**对所有实际会出现的错误码都有定义**，并且必须是一组**有限的、读者认得出的动作**——不能出现一个谁也不知道怎么执行的词，也不能出现空白。

**Why this priority**: 映射已在生产代码里（见上方规格修正），但**没有任何测试证明它是穷尽的**。新增一个错误码时，它会静默落到默认分支 `inspect_trace`，而这未必是对的动作——例如一个新的配额类错误应当指向 `check_local_client`。这是一条会随时间静默退化的性质。

**Independent Test**: 遍历所有模拟场景声明的 `expected_code` 以及所有已知错误码，断言每个码映射出的动作都落在已知动作集合内且非空，可在 Go 测试中独立完成。

**Acceptance Scenarios**:

1. **Given** 全部 16 个模拟场景各自的 `expected_code`，**When** 逐一求其下一动作，**Then** 每个结果都非空且属于已知动作集合。
2. **Given** 一个此前未见过的错误码，**When** 求其下一动作，**Then** 得到默认动作而非空值——默认行为被显式断言，而不是靠「碰巧没人改」。
3. **Given** `FILE_MISSING` 与 `FILE_CHANGED`，**When** 求其下一动作，**Then** 均得到 `check_registered_file`（当前**唯一未被断言**的分支）。
4. **Given** 任一可重试码，**When** 求其下一动作，**Then** 动作与「可重试」标记**同时**成立——两者不得各自为政。

### User Story 3 - 快照不会悄悄带上媒体内容（Priority: P2）

复现清单里的输入快照记录的是版本号、引用和哈希，**不包含**任何图片、音频或二进制附件。今天这一点成立，但只是因为没人加过这样的字段。需要一条断言把它钉死：任何人给快照加了一个能装二进制内容的字段，测试必须变红。

**Why this priority**: 这是 D13-V06 的隐私性质，一旦破坏是数据外泄级别的问题；但它今天并未被违反，所以排在两条排障路径之后。

**Independent Test**: 对快照结构做一次结构性断言（字段集合与各字段的形状），与任何界面无关。

**Acceptance Scenarios**:

1. **Given** 当前的快照结构，**When** 检查其全部字段，**Then** 不存在任何二进制载荷字段，且该断言以**字段清单**的形式表达——新增字段会使断言失败，直到有人显式确认它不是媒体。
2. **Given** 一份序列化后的快照，**When** 检查其体积与内容形状，**Then** 所有值都是有界的标识串、版本号或哈希，没有任意长度的载荷。

### User Story 4 - 复现一次运行不会改写用户的偏好（Priority: P2）

用户设置过自己的来源偏好。为排障复现一次历史运行时，复现读取的是**当时那次运行的快照**，绝不把快照里的偏好写回成用户当前的偏好。排障不该有副作用。

**Why this priority**: 副作用一旦发生，用户的配置被静默改掉，且很难归因。现有断言是顺带的（埋在一个确定性循环里，只检查固定夹具的值没变），不是针对这条性质的。

**Independent Test**: 以一个**与夹具默认值不同**的偏好构造运行，复现后断言用户侧偏好未被改写，可在 Go 测试中独立完成。

**Acceptance Scenarios**:

1. **Given** 一次快照中偏好为 A 的历史运行，**When** 复现它，**Then** 复现结果携带偏好 A，且**没有任何写入路径**把 A 写回偏好存储。
2. **Given** 同一次复现，**When** 检查快照的其它输入字段，**Then** 它们同样只被读取、未被回写。
3. **Given** 复现使用的偏好值与夹具默认值不同，**When** 断言执行，**Then** 断言能区分「真的没改」与「碰巧都等于默认值」——这是现有顺带断言做不到的。

---

### User Story 5 - 一条链走通：审计事件 → 追踪 → 运行 → 原故障运行（Priority: P3）

每一环今天都被单独测过，但没有一条测试从**一次真实产生的运行**出发走完整条链。需要一条端到端断言：由一次真实运行产生审计事件，从事件取出追踪编号查到技术事件，从技术事件取出运行号查到该运行，再从该运行取出原故障运行号查到原运行。

**Why this priority**: 每环可靠不等于链条连通——环与环之间的标识符是否真的对得上，今天没有任何断言。但它依赖前面几项先把语义定清楚，所以排在最后。

**Independent Test**: 在后端集成测试中由真实运行产生数据并逐跳查询，不涉及界面。

**Acceptance Scenarios**:

1. **Given** 一次真实执行并产生了审计与技术事件的运行，**When** 从审计事件的追踪编号查技术事件，**Then** 至少查到一条，且其运行号等于该次运行。
2. **Given** 一次以某历史运行为原故障发起的复现，**When** 沿运行号→原故障运行号查询，**Then** 查到的正是那次历史运行。
3. **Given** 链条中任一跳的标识符被清空，**When** 沿链查询，**Then** 该跳返回「查不到」而**不是**返回一个无关结果——空标识符不得退化成通配。

---

### Edge Cases

- 事件的 `traceId` 为空（脱敏会把非法格式的追踪编号清空）：跳转必须给出明确的不可跳转理由，不得跳到未筛选日志。
- 事件的 `traceId` 齐备但该追踪的技术事件已过保留期：跳转本身成立，结果为空列表，需与「不可跳转」区分开。
- 错误码为空字符串：下一动作仍须非空（默认分支）。
- 快照新增了一个合法的非媒体字段：断言应当失败并要求人确认，而不是自动放行——这是本性质的**成本**，也是它的**作用**。
- 原故障运行号格式合法但该运行不可读（保留期或权限）：链条断言须区分「不可读」与「不存在」。
- 跨层链条中同一追踪编号出现在多次运行里：断言须按运行号收敛，不得假定追踪与运行一一对应。

## Requirements *(mandatory)*

### Functional Requirements

**G1 — 审计事件到技术追踪的跳转**

- **FR-001**: 系统 MUST 以一个可独立求值的推导，把「一条事件」映射为「一组技术日志筛选条件」或「一个不可跳转的理由」，使该推导无需界面即可被断言。
- **FR-002**: 当事件缺少可用追踪编号时，系统 MUST 返回不可跳转并说明原因，MUST NOT 返回一组会显示全量日志的空筛选。
- **FR-003**: 跳转产生的筛选 MUST 只由该事件决定：此前的组件、严重级、错误码与时间范围条件一律清空，分页游标归零。
- **FR-004**: 跳转 MUST 只使用现有的事件查询与其现有筛选参数，MUST NOT 新增任何服务端查询参数、端点或数据读取路径。

**G2 — 到对象版本的跳转**

- **FR-005**: 系统 MUST 让读者能从一条事件定位到它所记录的对象与版本。
- **FR-006**: 该定位 MUST 优先在**不新增数据读取路径**的前提下实现；现有事件查询**不支持**按对象类型或对象标识筛选（已核实：服务端筛选结构与其 SQL 仅支持追踪、组件、严重级、错误码、运行、时间与游标），因此若确定需要服务端筛选，该新增 MUST 在计划中**单列为一项新增数据读取路径**并说明为何缺口无法以现有数据闭合。
- **FR-007**: 当事件的对象版本为空时，系统 MUST 明确呈现「未记录版本」，MUST NOT 显示空白或伪造一个版本。

**G3 — 下一动作的有效性判定**

- **FR-008**: 系统 MUST 保证任一错误码求得的下一动作非空，且属于一个**有限且封闭**的已知动作集合。
- **FR-009**: 系统 MUST 以断言覆盖全部现有分支，含当前唯一未被断言的 `check_registered_file` 分支。
- **FR-010**: 系统 MUST 断言映射对**全部模拟场景声明的预期错误码**是穷尽的——新增一个不在映射内的错误码时，断言失败而非静默落到默认分支。
- **FR-011**: 系统 MUST 断言「动作」与「可重试」两个字段在每个分支上一致。

**G4 — 无自动媒体快照**

- **FR-012**: 系统 MUST 以一条显式断言证明输入快照不含任何二进制或媒体载荷字段。
- **FR-013**: 该断言 MUST 以字段清单的形式表达，使快照新增字段时断言失败并要求人确认该字段不是媒体。

**G5 — 复现不回写偏好**

- **FR-014**: 系统 MUST 以一条具名断言证明复现一次历史运行不改写用户侧偏好。
- **FR-015**: 该断言 MUST 使用与夹具默认值**不同**的偏好值，以区分「真的没改」与「碰巧都等于默认值」。

**G6 — 跨层关联的端到端断言**

- **FR-016**: 系统 MUST 有一条从真实运行出发、逐跳走完「审计事件 → 追踪 → 运行 → 原故障运行」的断言。
- **FR-017**: 该断言 MUST 验证每一跳的标识符确实对得上，而非各跳分别非空。
- **FR-018**: 当链条中某个标识符为空时，系统 MUST NOT 把它当作通配匹配到无关记录。

**贯穿约束**

- **FR-019**: 本特性 MUST NOT 新增任何数据读取路径，除非某项缺口无法以现有查询与数据闭合；此类新增 MUST 在计划中单列并给出理由（当前已知唯一候选：FR-006 的对象维度筛选）。
- **FR-020**: 本特性 MUST NOT 新增 UI 单测。界面行为一律进入 `manual-ui-todo.md` 并标注为待用户验证。
- **FR-021**: 凡把既有界面逻辑提取为可测推导的改动，MUST 保持既有界面行为不变，除非该行为本身是被修的缺陷（已知唯一一处：FR-002 的空追踪编号静默跳转）。

### Key Entities

- **诊断事件**：一次被记录的操作或技术步骤。携带对象类型/标识/版本、追踪编号、跨度与父跨度、运行号、错误码、下一动作、可重试标记。是 G1、G2、G3、G6 的共同输入。
- **跳转意图**：由一条事件推导出的「去哪里看」——要么是一组筛选条件，要么是一个不可跳转的理由。G1 的产出物。
- **下一动作**：面向读者的、有限集合中的一个可执行动作名。G3 的判定对象。
- **输入快照**：一次运行的输入指纹，只含版本号、引用、哈希与数值参数。G4、G5 的对象。
- **运行**：一次模拟执行，携带运行号、场景、模块、构建、回归判定与可选的原故障运行号。G6 链条的中段与末段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对照表 §5 的六项中，**至少五项**（G1、G3、G4、G5、G6）转为「自动测试已通过」，其判定依据是实跑用例而非代码存在。
- **SC-002**: 排障者从一条失败的操作记录出发，**无需手工输入任何编号**即可看到该次故障对应的技术追踪；追踪编号缺失时，**100%** 的情况下看到明确说明而非一屏无关日志。
- **SC-003**: 全部 16 个模拟场景的预期错误码，**100%** 映射到非空且属于已知集合的下一动作。
- **SC-004**: 给快照新增一个媒体字段、或让复现回写偏好、或切断链条中任一跳——这三种改动**各自**至少使一条用例变红（以变异验证实测，不以「写完看绿」代替）。
- **SC-005**: 本特性不新增数据读取路径；若最终新增，计划中单列的条目数 **≤ 1**，且附有「为何无法以现有数据闭合」的说明。
- **SC-006**: 新增 UI 单测数量为 **0**；界面侧条目全部进入手动清单并标注待用户验证。

## Assumptions

- 对照表 §5 是本特性的唯一输入范围；六项之外的缺口不在范围内（原则 VIII）。
- 政策阻断项不在范围内：D13-V10「真实重跑需重新校验」与 D13-V12「真实 Codex 及远程阶段实测」要求真实执行器，按原则 IX 保持禁用。
- 浏览器侧一律手动验收（原则 II）。本特性产出的手动条目是**新增**的，不替代已有的 57 条。
- 「已知动作集合」取当前生产代码中实际产生的五个动作，本特性不新增动作种类，除非 Q3 的回答要求。
- G5 针对的「临时恢复」按上方规格修正的认定，指**从快照复现一次运行**；仓库中不存在其它恢复流程。
- 跳转只使用现有的事件查询与其现有筛选参数，不新增服务端查询能力（FR-004、FR-019）；唯一可能的例外是 FR-006。
- 六项彼此独立，可分别交付；G6 在语义上依赖 G1/G2 定清楚，因此排在最后。

## 待澄清问题（不阻塞后续阶段）
