# Feature Specification: 计划轮换页必须在窗口内送达

**Feature Branch**: `claude/013-diag-stream-rotation`

**Created**: 2026-09-15

**Status**: Draft

**Input**: 主任务 2026-09-15 在真实浏览器补跑 runbook `§8` 实时流，发现两条硬缺陷（`002-V05-01`、`002-V05-02`），需要修复「计划轮换对用户不可见」这条 PR #21 声称已闭合的保证。

## Current State（以实测数据与代码为准）

### 主任务的两组实测

**缺陷一 —— `002-V05-01`（页面采样）**

- 采样 448 秒 / 224 样本，状态在 `connected` 与 `disconnected` 间反复，累计 **18 次**断线提示「实时流已断开，正在从上次游标重新连接。」
- 翻转时刻（秒）：`8→10, 34→36, 62→64, 88→90, 116→118, 142→144, 170→172, 196→198 …`，**间隔 26～28 秒**。
- 网络面板：面板自己发出 10 条 `/api/content-diagnostics/stream`，**9 条末尾状态 503**，1 条 200（当时仍在流中）。
- `V05-01` 要求全程 `connected`、零断线提示。

**缺陷二 —— `002-V05-02`（原始流抓取）**

同页面用 `fetch` 直抓一次原始流（带 `X-Workspace-Slug`、`credentials: include`、读到 `done` 并吐出尾部缓冲）：

```text
status 200 / application/x-ndjson / 恰好 25011ms / 26 行 NDJSON
含 "rotate" 的行：0 条
末行：{"events":[],"cursor":919,"gap":false,"has_more":false}
```

主任务的判断是「两条是同一根因的两面」。**这个判断成立**，下面给出根因。

### 复现实验：换一个窗口长度，缺陷就不出现

现有测试 `TestContentDiagnosticStreamClosesPlannedWindowWithRotate` 用 **50ms** 窗口且**一直是绿的**。而 ticker 周期是 **1 秒**（`content_diagnostics.go:41`）。50ms < 1s 意味着**截止定时器在 ticker 一次都还没跳之前就到期**——这条测试从来没有走过生产环境走的那条路。

把窗口换成 ticker 周期的整数倍（真实 ticker、真实 deadline，无代理），在本机实跑三轮：

```text
window=2s   pages=4   rotate_pages=1   elapsed=2.003s   last_rotate=true
window=3s   pages=5   rotate_pages=1   elapsed=3.004s   last_rotate=true
window=5s   pages=7   rotate_pages=1   elapsed=5.002s   last_rotate=true
```

**处理器确实会发出 `rotate=true` 的页**，三轮九次全部如此。但注意页数与耗时：

| 窗口 | 页数 | 构成 |
|---:|---:|---|
| 2s | 4 | `t=0,1,2` 三页 + **轮换页** |
| 3s | 5 | `t=0,1,2,3` 四页 + **轮换页** |
| 5s | 7 | `t=0,…,5` 六页 + **轮换页** |

规律是 `窗口秒数 + 2` 页，且 `elapsed` 一律**略大于**窗口长度（`3.004s`、`5.002s`）。**轮换页是在窗口到期之后才被写出去的。**

### 根因

把这条规律外推到生产的 25 秒窗口：

| 应该发生 | 主任务实测 |
|---|---|
| `t=0…25` 共 **26 页**（无 rotate） | **26 行 NDJSON** ✓ |
| 随后 `t≈25.0 + δ` 第 **27 页**，带 `rotate:true` | **没有第 27 行**，流在 **25011ms** 结束 |

26 行对上了，第 27 行没了，而流结束时刻 **25011ms** 正好是那 11 毫秒——处理器在写第 27 页之前要先做**两次数据库查询**（`getWorkspaceMember` 复核成员身份、`Store.Query` 取页），这两次查询的耗时就是那个 δ。

代码里这件事是明写的（`content_diagnostics.go:42-47`）：

```text
for {
  member 复核（DB）
  page := Query(...)（DB）
  page.Rotate = rotate      ← rotate 是上一轮 select 里设的
  write + flush
  if rotate { return }
  select { ctx.Done / deadline.C → rotate=true / ticker.C }
}
```

`rotate` 只能在 `select` 里被置真，而 `select` 在**写完一页之后**才执行。所以**轮换页永远是窗口到期之后新起的一轮**，它的写出时刻必然 **> 窗口长度**。

**根因一句话：轮换页被安排在窗口之外，因此只要传输层在窗口边界附近切断连接，这一页必然赶不上。** 它不是「有时丢」，是**结构上必然晚到**；晚多少取决于那两次数据库查询，与传输层的限制赛跑。

这也解释了那 9 条 503：连接在上游仍在做数据库查询时被切断，代理把这个结束状态记成 503。

### 已排除的嫌疑

主任务提了两个嫌疑，(a) 的一半可以直接排除：

| 嫌疑 | 结论 |
|---|---|
| (a) Go server 的 `WriteTimeout` 在 25s 附近切断 | **排除**。`server/cmd/server/main.go:299` 明写 `ReadTimeout` 与 `WriteTimeout` **故意置零**（为 WebSocket 升级留出长连接），`main_test.go:362` 有断言锁住这一点 |
| (a) 另一半 / (b) 代理在 25s 附近切断或缓冲 | **未排除，但不影响修法**。`apps/web/next.config.ts` 把 `/api/:path*` rewrite 到 `REMOTE_API_URL`，走 Next.js 自己的转发 |

**为什么不需要先定位代理的确切超时值**：修法不是「把超时调大」，而是**让轮换页落在窗口之内**。窗口之内送达的页不与任何边界赛跑，无论那个边界是 25s、30s 还是别的值。调大超时只是把赛跑推后，赛跑本身还在。

### 不在本功能范围

不碰 `server/internal/daemon` 与上游 Multica 其它代码；不写 UI 单测；不改诊断的脱敏、审计、执行器禁用等既有不变量；不新增前端读取路径；不解决 `002-V05-03` 的口径冲突（见下）。

### 记录：`002-V05-03` 的口径冲突（本特性不解决）

runbook 的实时流区块**字面写着**「不应用上方历史筛选」，而条目 `002-V05-03` 要求**筛选跟随**。两句话互相矛盾，读到的人无法判断该记通过还是未通过。

代码一侧的事实：`packages/views/content/diagnostics/index.tsx` 的 `useDiagnosticStream` **确实**把 `component` / `severity` / `errorCode` / `traceId` / `from` / `until` 传给了流，`stream-state.ts` 也有 `filter-change` 转移（游标归零、已报告的缺口保留）。**实现是「筛选跟随」的**，与条目一致，与 runbook 那句话不一致。

**建议**（留给主任务裁决，不在本 PR 动手）：改 runbook 那句话，不改实现——实现与条目一致，而且「筛选跟随」是更有用的行为（看着某个错误码的人切到实时流，期待看到的是同一个错误码）。改动面是一行文档。

## Clarifications

### Session 2026-09-15（待主任务裁决，已按推荐值暂定，不阻塞）

- **Q1**（轮换时机）：轮换页要提前到窗口内，就必然牺牲一点窗口时长。→ **暂定 A**：**提前一个 ticker 周期**——把「下一跳会越过截止线」的那一页标为轮换页并结束。25 秒窗口因此在 `t=24` 结束，留 **1 秒**余量。代价是每个窗口少一页。替代是「提前一个固定毫秒数」，但那要新引入一个常量，而 ticker 周期是现成的、且正好是「下一页什么时候来」的答案。见 FR-002。
- **Q2**（现有 50ms 测试怎么办）：该测试的窗口短于一个 ticker 周期，是它给了「轮换页有绿测」的假信心。→ **暂定 A**：**把它的窗口改成 ticker 周期的整数倍**（建议 3s），使它走生产走的那条路；并保留一条「窗口短于一个 tick 时首页即轮换页」的用例，说明那种退化形态是正确的而不是被忽略的。见 FR-006。
- **Q3**（是否同时动代理）：代理的确切超时值未定位。→ **暂定 A**：**本特性不动代理**。窗口内送达之后，代理超时不再参与正确性；若主任务希望把代理超时一并查清，建议另开一条，不与本修复捆绑——捆绑会让「修好了吗」这个问题失去单一答案。见「不在本功能范围」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 计划轮换对用户不可见 (Priority: P1)

盯着实时流的人，在一个又一个 25 秒窗口过去时，看到的始终是「已连接」。不出现断线提示，不出现闪烁。

**Why this priority**: 这是 PR #21 声称已经闭合、而实测证明没有闭合的那条保证。`002-V05-01` 与 `002-V05-02` 都是它的验收路径。

**Independent Test**: 在真实浏览器打开诊断页 → 技术日志 → 连接实时流，采样状态行 ≥ 3 个窗口（≥ 90 秒），断线提示计数应为 **0**。

**Acceptance Scenarios**:

1. **Given** 一个完整窗口的流，**When** 读到最后一页，**Then** 该页 `rotate` 为真，且**在窗口边界之前**已经送达。
2. **Given** 客户端状态机收到该页，**When** 计算下一状态，**Then** 状态**不进入断线态**，且立即从游标续连。
3. **Given** 连续跑 3 个以上窗口，**When** 统计断线提示，**Then** 计数为 0。

---

### User Story 2 - 轮换页不与传输层边界赛跑 (Priority: P1)

轮换页的送达不依赖「代理的超时比窗口长多少」这个谁也说不准的量。

**Why this priority**: 与 US1 同为 P1，且是 US1 能不能**稳定**成立的原因。把超时调大能让今天的实测变绿，但下一个部署环境的超时不一样，缺陷就回来了——而且回来的时候症状完全相同，没人会想到是同一件事。

**Independent Test**: 在真实 ticker / 真实 deadline、窗口为 ticker 周期整数倍的条件下跑完整个窗口，断言**整条流在窗口边界之前结束**。

**Acceptance Scenarios**:

1. **Given** 窗口为 ticker 周期的整数倍，**When** 流结束，**Then** 结束时刻**严格早于**窗口边界。
2. **Given** 窗口到期之后，**When** 观察处理器，**Then** **不再有**任何数据库查询或写出——窗口之外零动作。
3. **Given** 任一早于最后一页的页，**When** 读 `rotate`，**Then** 为假；标记**有且仅有一页**。

---

### Edge Cases

- 窗口短于一个 ticker 周期（测试里的退化形态）：首页即是「最后一页」，它就该带 `rotate` 并立刻结束。
- 成员身份在窗口中途被撤销：仍按既有行为**不带 rotate 直接关闭**——那是真断线，客户端应当看见（`TestContentDiagnosticStreamEndsWithoutRotateWhenMembershipIsRevoked` 锁住这一点）。
- 客户端在窗口中途主动断开（`r.Context().Done()`）：同上，不发轮换页。
- 窗口边界恰好落在 ticker 跳点上：这正是生产的情形（25s ÷ 1s），必须是被测试覆盖的主路径而不是边角。

## Requirements *(mandatory)*

### 轮换时机（US1、US2）

- **FR-001**: 计划窗口的最后一页 MUST 携带 `rotate` 标记，且 MUST 在**窗口边界之前**写出并冲刷。
- **FR-002**: 轮换与否 MUST 在**写这一页之前**判定，判据是「再等一个 ticker 周期就会越过窗口边界」（Q1 = A 暂定）。MUST NOT 在窗口到期后新起一轮来写轮换页。
- **FR-003**: 窗口到期之后 MUST NOT 再发起任何数据库查询或响应写出。
- **FR-004**: 一条流中带 `rotate` 的页 MUST 有且仅有一页，且 MUST 是最后一页。
- **FR-005**: 非计划结束（成员身份撤销、客户端断开、查询失败）MUST NOT 带 `rotate` —— 那是真断线，客户端必须看见。

### 测试（US2）

- **FR-006**: 计划轮换的回归测试 MUST 在**真实 ticker 与真实 deadline**、窗口为 ticker 周期**整数倍**的条件下运行；MUST NOT 只用短于一个 ticker 周期的窗口（Q2 = A 暂定）。该测试 MUST 断言流的结束时刻**早于**窗口边界。
- **FR-007**: MUST 有一条端到端断言：一个完整窗口的流，最后一页 `rotate` 为真，**且客户端状态机在收到该页后不进入断线态**。两侧 MUST 基于**同一份真实报文**，而不是各自手搓的对象。
- **FR-008**: MUST NOT 新增 UI 单测。

### 范围

- **FR-009**: 改动 MUST 限于 `server/internal/handler` 的流处理，必要时 `packages/core/content/diagnostics/stream-state.ts`。
- **FR-010**: 本特性 MUST NOT 改动代理配置（Q3 = A 暂定）。若实测证明窗口内送达仍不足，MUST 作为单独一条提出，不与本修复捆绑。
- **FR-011**: MUST NOT 改动 `server/internal/daemon` 或上游 Multica 其它代码。

### 文档

- **FR-012**: MUST 把 `002-V05-03` 的口径冲突记录下来并给出建议，**MUST NOT 在本特性里解决它**。

## Success Criteria *(mandatory)*

- **SC-001**: 真实浏览器连续采样 ≥ 3 个窗口，断线提示计数为 **0**。
- **SC-002**: 一个完整窗口的流，最后一页 `rotate` 为真，且流的结束时刻**严格早于**窗口边界。
- **SC-003**: 一条流中 `rotate` 为真的页数恰为 **1**。
- **SC-004**: 成员身份撤销时结束的流，`rotate` 为真的页数为 **0**。
- **SC-005**: 计划轮换的回归测试所用窗口 ≥ **2 个** ticker 周期。
- **SC-006**: 客户端状态机在收到真实末页后的状态**不是** `disconnected`，且要求立即续连。
- **SC-007**: 代理配置改动行数为 **0**。
- **SC-008**: `server/internal/daemon` 与上游 Multica 其它代码改动行数为 **0**。
- **SC-009**: 新增 UI 单测数为 **0**。

## UI Impact

**无界面改动。** 本特性改的是服务端何时写出轮换标记；面板代码不在范围内。按 2026-09-15 的 SOP 规则，界面整套继承上游 Multica 的设计系统与设计 token，本特性不新增控件、不调样式。`002-V05-01` / `V05-02` 的验收仍由主任务在真实浏览器完成——这正是本特性要让它们能通过的原因。

## Assumptions

- ticker 周期 1 秒、窗口 25 秒是当前生产值；修法不依赖具体数值，只依赖「窗口是若干个 ticker 周期」。
- 代理在窗口边界附近切断这一点**未被直接证实**，但修法不依赖它成立：窗口内送达在任何超时值下都正确。
- 客户端状态机对 `rotate` 页的处理（保持 `connected`、立即续连）**今天已经正确**，本特性不改它，只为它补一条基于真实报文的断言。
