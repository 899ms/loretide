# Contract: 账号配置版本（`content_account_revision`）

## 这张表的性质：只插不改不删

一行写下去就不再变。变更**永远是追加一行**，不是更新原行。

这不是洁癖：验收要求「旧版本可读、新运行才采用新配置」，而一个可被 `UPDATE` 的历史表无法兑现这句话——任何一次读改写都能悄悄改掉过去。

**唯一的删除场景**：账号或工作区被删除时随之清除。

## 表

| 列 | 类型 | 说明 |
|---|---|---|
| `revision_id` | `text` PK | **跨表引用一律用它**。运行钉住的就是这个 |
| `account_id` | `text` | 所属账号 |
| `workspace_id` | `text` | 所属品牌。隔离靠应用层过滤 + 授权助手；**无外键** |
| `revision` | `bigint` | **按账号独立**计数，从 1 起。供人读与排序，**不用于跨表引用** |
| `persona_prompt` | `text` | 可以是空串——空是合法状态，见下 |
| `created_at` | `timestamptz` | |

**约束与索引**（各自独立迁移文件，一文件一语句）：

- `CREATE UNIQUE INDEX CONCURRENTLY (account_id, revision)` —— **不写在建表语句里**（Q3 裁决）。它既是并发互斥的依据，也是求当前版本的索引。
- `CREATE INDEX CONCURRENTLY (workspace_id)` —— 供工作区删除。

**无外键、无级联。**

## 空提示词是合法的

SOP §3.1：「创作者确认后形成 AccountConfigRevision，**未确认项保留为待补充**」。

创作者确认了、人设还没想好——这是一个**有效版本**，内容是空串。

- 空串 → 成功，产生版本。
- 纯空白 → **与空串同等对待**，不做 trim 后拒绝。
- 读回 → **空串**，不是 `null`、不是「未设置」、不是错误。

把空当成非法会让创作者卡在流程里无法推进。

## 当前版本怎么求

该账号 `revision` 最大的那一行。**没有指针列**（Q2 裁决 A）。

理由：指针是第二份真相，一旦与实际最大值漂移，账号就会指向一个不是最新的版本——而这种 bug 不会报错，只会安静地用错配置。没有第二份真相就不可能漂移。

## 并发：有界重试，仍冲突才 409

写入流程：读该账号当前最大 `revision` → 插入 `revision + 1`。

两个写入者同时读到同一个 `N`，都试图插 `N+1`：唯一索引让**其中一个失败**（SQLSTATE `23505`）。

**失败方重试，最多 3 次**；仍冲突则返回 **409 诊断错误对象**。

| 不选的做法 | 为什么 |
|---|---|
| 直接 409 不重试 | 两次确认都真实发生过，历史应当两条都留下。直接 409 会让一次确认**消失**，而创作者只看到一个失败，不知道该不该重做 |
| 无限重试 | 持续争用下会把一次写入拖成不确定时长的循环 |

## 接口

| 操作 | 说明 |
|---|---|
| 设置提示词 | 产生**新版本**（不是更新） |
| 读当前版本 | `revision` 最大的那行 |
| 读指定版本 | 按 `revision_id` |
| 列出某账号的版本 | 按 `revision` 排序 |

**本卡不提供删除或修改版本的接口**——那与「只插不改不删」直接矛盾。

### 授权与拒绝

每个操作先经 `workspacecore.Authorize`。拒绝用其规范映射：

| 情况 | 响应 |
|---|---|
| 非成员 / 角色不足 / 账号属于别的品牌 / 账号不存在 / 版本不存在 | **404** + 诊断错误对象 |
| 未认证 | **401** |
| 提示词超长 | **400** + 诊断错误对象 |
| 并发冲突且重试耗尽 | **409** + 诊断错误对象 |

**404 的五种情况响应必须逐字节相同**，否则拒绝本身能被用来探测哪些 id 是真的。

## 不变量

| # | 规则 | 断言位置 |
|---|---|---|
| A1 | 连续两次设置 → 版本 1、2；版本 1 内容不变 | `content_account_revision_test.go` |
| A2 | 空提示词成功并产生版本；读回为空串 | `revision_test.go` + handler |
| A3 | 纯空白与空串同等对待 | `revision_test.go` |
| A4 | 改 A 三次后 B 仍在版本 1 且内容不变 | handler |
| A5 | 改动后用旧 `revision_id` 读到的仍是旧内容 | handler |
| A6 | 版本行**不可更新**：无任何接口能改已存在的版本 | handler（无此端点）+ 查询层无 UPDATE |
| A7 | **真并发**两次写入 → 版本号 1、2，无重复、无丢写 | handler（两个 goroutine） |
| A8 | 重试耗尽 → 409，不死循环 | `revision_test.go`（注入恒冲突的假 store） |
| A9 | 跨品牌读写 → 404，与「不存在」逐字节相同 | handler |
| A10 | 提示词超长 → 400，不落库 | `revision_test.go` + handler |
| A11 | 删除工作区 → 版本行清零；新表不在 `unclassified` | handler + 清单用例 |

## 接入合同

**本卡不新增模块目录**——版本表与代码都归 `ip-profile`（与 `content_account` 同模块）。因此 `pnpm check:diagnostics-contract` 仍应报 **`checked 3 landed modules`**，不是 4。

E2 由真实接入满足：**每次写入版本都记一条审计事件**（谁、在哪个账号、第几版）。
