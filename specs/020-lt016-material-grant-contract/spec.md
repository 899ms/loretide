## 这张卡交付什么，不交付什么

**交付**：一个**纯判定函数**与它的形状定义——`Grant`、`ResourceRef`、`Principal`，以及 `CanRead`。加一份合同文档和一张权限矩阵。

**不交付**：素材表、知识表、Grant 表、任何迁移、任何 HTTP 端点、任何界面。资源实体在 LT-017 之后落地，**存储扩展在首个资源切片落实**（任务卡原文）。

**为什么这样切**：把判定写成一个对「调用方交上来的事实」做决定的纯函数，它现在就能被测穷尽——权限矩阵不需要一张表就能跑满——而等资源切片落地时，接上去的是数据来源，不是判定逻辑。反过来先建表再补判定，判定就会长在每个资源模块里各写一遍。

## User Scenarios & Testing *(mandatory)*

### User Story 1 —— 同品牌里，另一个账号的专属资料读不到（P1）

一个任务在账号 A 下运行，去读一份标着「属于账号 B」的素材。**拒绝**，即使 A 和 B 在同一个品牌里。

**为什么是 P1**：这是 W-02 出口的核心断言。品牌隔离（LT-010）只管到品牌边界，品牌**内部**账号之间的隔离在此之前没有任何东西负责。

**验收**
1. 拒绝；
2. 拒绝结果**不含资源正文、不含资源 id**，与「这份资料不存在」**同形**；
3. A 持有的、面向 A 的授权不会因为「同一个品牌」而顺延到 B 的资料。

### User Story 2 —— 两个账号的人设提示词一模一样，仍然读不到对方的资料（P1）

有人把账号 B 的人设提示词复制到账号 A。A 的任务去读 B 的专属资料。**拒绝。**

**为什么单列**：这是 D11-V01 最容易被误解的一句。人设提示词是**表达配置**，不是凭证；两份配置内容相同只说明它们写得像，不说明它们是同一个主体。若判定里有任何一步比较了提示词、或以提示词派生出的东西作 key，这条就会悄悄失效。

**验收**：判定结果与提示词内容**无关**——用例把两个账号的提示词设为逐字节相同，断言判定仍然拒绝。

### User Story 3 —— 授权撤销之后立刻失效（P1）

一份授权本来允许任务读账号 A 的素材。授权被撤销。同一个任务再读。**拒绝。**

**验收**
1. 撤销后的授权判定为拒绝，**不管它的有效期还剩多久**；
2. 合同文档写明：**将来若缓存判定结果，撤销必须使缓存失效**。本卡**不实现缓存**——`Authorize` 今天就不缓存，理由是「被移除的那一刻就出局」，这一层沿用同一条原则。

### User Story 4 —— 过期的授权不再有效（P1）

授权有效期到了。**拒绝**，不需要任何人去撤销它。

**验收**：判定以调用方传入的「现在」为准（注入时钟），不读系统时间——否则用例无法在不睡觉的情况下测过期。

### User Story 5 —— 授权只在它写明的范围内有效（P1）

一份写明「账号 A 的素材」的授权，不能用来读：
- 另一个品牌的任何东西（品牌不一致）；
- 同品牌另一个账号的东西（账号不一致）；
- 账号 A 的**另一类**资源，比如知识条目（资源类型不一致）；
- 一个不属于任何账号的资源，如果授权写的是账号级（归属层级不一致）。

### User Story 6 —— 品牌共享的资料，本品牌内可读（P2）

不是所有资料都专属于某个账号。品牌级的公共素材，**同品牌的任何账号**都可读，不需要逐账号授权。

**为什么需要这条**：没有它，「归属」就只有一个层级，而 SOP 里品牌共享的素材是常态。有了它，「专属」才是一个有意义的状态。

### Edge Cases

- 授权为空 / 零值 → 拒绝（不是「放行」的默认）；
- 资源引用缺品牌或缺账号 → 拒绝，不猜；
- 同一个任务持有多份授权 → 只要有一份覆盖即可放行；
- 授权覆盖面**大于**请求（例如品牌级授权读账号级资源）→ 允许，这是包含关系不是越权；
- 授权覆盖面**小于**请求 → 拒绝；
- 主体类型不匹配（授权发给任务 T1，拿着它的是 T2）→ 拒绝。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：MUST 定义 `ResourceRef`（品牌 / 账号 / 资源类型 / 资源 id）与 `Grant`（主体 / 覆盖范围 / 有效期 / 撤销标记）的形状。
- **FR-002**：MUST 提供一个**可复用的读取前校验入口**，对给定主体、资源引用与授权集合作出判定。
- **FR-003**：判定 MUST 是纯函数：不查库、不读系统时间、不缓存。
- **FR-004**：品牌不一致 MUST 拒绝。
- **FR-005**：同品牌但账号不一致且资源为账号专属 MUST 拒绝。
- **FR-006**：资源类型不在授权范围内 MUST 拒绝。
- **FR-007**：已撤销的授权 MUST 拒绝，**无视有效期**。
- **FR-008**：已过期的授权 MUST 拒绝，无需撤销。
- **FR-009**：主体不匹配 MUST 拒绝。
- **FR-010**：品牌级资源对同品牌主体 MUST 允许，无需逐账号授权。
- **FR-011**：判定 MUST NOT 读取、比较或派生自人设提示词或任何账号表达配置；MUST 有用例以「两账号提示词逐字节相同」钉住。
- **FR-012**：拒绝 MUST 与「资源不存在」同形，MUST NOT 含资源正文、资源 id 或归属信息。
- **FR-013**：拒绝 MUST 经诊断记一条技术事件，沿用 `workspace-core` 既有的记录路径。
- **FR-014**：本卡 MUST NOT 新增迁移、表、外键或级联。
- **FR-015**：本卡 MUST NOT 新增 HTTP 端点或界面。
- **FR-016**：合同文档 MUST 写明缓存失效要求；本卡 MUST NOT 实现缓存。
- **FR-017**：MUST 有一张权限矩阵夹具，覆盖品牌/账号/资源类型/主体/撤销/过期各维度。
- **FR-018**：`pnpm check:diagnostics-contract` MUST 通过。

### Key Entities

- **Principal**：发起读取的主体。种类 + id。本卡关心两种：**任务**（`task`）与**人**（`human`）。种类是判定的一部分，不是标签。
- **ResourceRef**：一份资源的归属坐标——品牌、（可选的）账号、资源类型、资源 id。**账号为空即品牌级共享**。
- **Grant**：一份授权——发给谁、覆盖哪个品牌/账号/哪些资源类型、什么时候到期、是否已撤销。
- **Decision**：与 `workspace-core` 现有 `Decision` 同族的类型化判定，带 `Reason`，**不据此构造响应**。

## Assumptions

1. **授权从哪来，本卡不管。** 谁签发、存在哪、怎么下发，属于 LT-017 之后的资源切片。本卡只定义「拿到一份授权之后怎么判」。
2. **不做授权的传递或委派。** 一份授权不能派生出另一份。需要就再签一份。
3. **资源类型是字符串枚举**，首版取 SOP 里已经出现的两类（素材、知识）。加类型不需要迁移，因为本卡不落库。
4. **不实现缓存**，理由与 `Authorize` 相同：撤销要立刻生效。缓存的要求写进合同，留给真要缓存的那张卡。
5. **本卡不接任务工作流**（任务卡原文：「任务工作流稍后接入，不创建全套引擎」）。

## 待澄清问题（已按推荐值暂定，不阻塞）

### Q1 这一层放哪个模块？

`workspace-core` 的包注释**明确写着**它不回答归属问题，理由是「调用方拥有自己的表，得自己查」。这句话是本问题的全部难点。

- **A（推荐，已暂定）：放 `workspace-core`，并把那句包注释改精确。** 理由：那句话反对的是「替调用方去查表」，而本卡的判定**不查任何表**——归属事实由调用方作为 `ResourceRef` 交上来，和 `Authorize` 让调用方交 `Membership` 是同一个形状。两者都是「对你给我的事实作判定」。好处：模块图仍是 12 个，接入合同仍是 `checked 3 landed modules`，每个资源模块已经依赖 `workspace-core`，不必再加一条依赖边。**代价是要改一句上游注释**——那句话是 `#69`（我自己）写的，改动会在 PR 正文里单列。
- **B**：新建第 13 个模块 `material-grant`，登记进 `modules` 并让每个资源模块加依赖边。分层更干净，但要动 `specs/001` 定下的模块图，且新目录立刻受 E1/E2/E3 约束（接入合同变成 `checked 4`）。
- **C**：放 `ip-profile`。不选：授权是关于**资源**的，`ip-profile` 是关于账号表达配置的，放进去会让那个模块开始长出与它无关的职责。

### Q2 本卡要不要落库？

- **A（推荐，已暂定）：不落库，零迁移。** 只做形状 + 判定 + 合同 + 矩阵夹具。与任务卡「存储扩展在首个资源切片落实」一致，也与「资源实体尚不存在」这个事实一致——没有资源表的时候建一张指向它们的授权表，等于先定死一个还没有人用过的形状。
- **B**：本卡就建 Grant 表。好处是 LT-017 少一步；代价是这张表要在没有任何读方的情况下定型，而且按仓库规则它还得配索引迁移与工作区删除清单条目——为一个尚无消费者的表付全套成本。

### Q3 主体是「任务」还是「账号」？

- **A（推荐，已暂定）：主体是任务（或人），授权里另外写明它能替哪个账号读。** 因为一次读取的发起者是一次运行，而同一个账号可以有很多次运行；把主体定为账号，就没法只撤销其中一次运行的权限。
- **B**：主体就是账号。更简单，但撤销的粒度只能到账号，且「任务 Grant」这个名字就名不副实了。
