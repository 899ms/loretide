## 1. 本轮补的五条 SC，和为什么它们是缺口不是新需求

覆盖矩阵（§3）跑出来有五条 FR **没有任何 SC 钉住**。它们都是第一轮就写进 FR、但当时没配验收口径的：

| 缺口 | 补成 | 为什么不算扩大范围 |
|---|---|---|
| FR-013 的「读 `ip-profile` 源文件对表」没有 SC；FR-017 的「不发明枚举」只写在 FR 里 | **SC-018** | 两者都是裁决点名的要求（Q4=A 的对表用例、Q5 的不发明）。没有 SC，实施时「对表用例」会变成可选项，而「不发明枚举」半年后会被当成疏漏补全 |
| FR-014 的「`ready` 及之后要求 `approved`」没有 SC | **SC-019** | Q2=A 的全部内容就是这条前置条件。三条用例（draft 可建 / ready 被拒 / approved 后成功）才分得清「拒绝」与「一直拒绝」 |
| FR-014a / FR-017b 的「必带原因」没有 SC | **SC-020** | §9.2 原文「并注明原因」。四条各自点名，与 SC-004 同一理由：合并成一条，任一半坏了都会被另一半掩盖 |
| FR-016 的「actor 服务端取、不接受调用方指定」没有 SC | **SC-021** | 这是发布记录唯一的不可伪造字段。没有用例，「从 body 读 actor 更方便」是实施时很自然的选择 |
| FR-021 的删除栅栏只在 tasks 里有 T024，spec 侧没有 SC | **SC-022** | #104 的口径。T024 已经存在，补的是它在 spec 里的验收面 |

**没有新增任何 FR**，五条 SC 全部指向已有的 FR。

## 4. 仍然登记在册的两个不确定

1. **`failed` / `removed` 的原因借用了 `receipt_note`**（FR-017b）。Q3 要求「失败、延后必带 reason」，Q5 定死的字段清单里没有 `reason` 列。我选了复用自由文本的 `receipt_note` 并要求此时非空，**没有自作主张加一列**。改成独立列是两处改动（FR-017b 与建表迁移）。
2. **`DeliveryPackage` 是派生视图，不是第五张表**（Assumptions 7）。§9.1 列的七项在本卡的落点：冻结正文 / 目标渠道 / 版本清单 ← 审核请求快照；交接者与时间 ← 交付任务；媒体文件与来源附录本阶段只有「缺失说明」那一半。建第五张表会存一份与快照重复的真相。若 §9.1 要求它是可独立引用的实体，那是一张表 + 三个迁移。

**一处我特意没做**：「延后」没有变成第七个状态。§9.2 的「标记实际发布失败、延后或取消」里的延后，在本卡是改 `scheduled_at` 或进 `held`，两者都写迁移记录与原因；§7.1 的六个状态里没有它，加一个会与 `held` 语义重叠。
