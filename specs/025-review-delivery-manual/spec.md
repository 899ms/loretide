### 4. 迁移规则（#122 之后全部生效）

R1/R2 无外键无级联；R3/R4 每个索引 `CREATE INDEX CONCURRENTLY` **单文件单语句**；**R5**（从 483 起）建表迁移**不得**含 `PRIMARY KEY` / `UNIQUE`；**R6** 每个建索引的 up 迁移登记进 `cmd/migrate` 的 `concurrentIndexCleanups`，索引名逐字相同，**建表迁移不登记**；新表进 `workspace_delete_manifest_test.go` 并在删除链同一 CTE 里各有一条按 `workspace_id` 的 `DELETE`。

仓库里当前最大迁移号是 **493**；`specs/024` 的提案占用 **494–503**。**本卡的迁移号在实施时按当时的最大值顺延**，规格不写死数字——024 尚未合入，写死等于赌它的编号不变。

### 5. 写路径与授权

- 写事务**第一句**取 `LockForContentDiagnosticWrite`（#104 的删除栅栏），不靠「顺便审计了」间接获得；
- 越权一律经 `workspace-core` 的 `RefusalStatus` / `RefusalBody`，与「不存在」同形；
- 带路径参数的端点按工作流第 12 步：必须有一条**穿过真实中间件、参数值 ≠ 上下文值**的用例。本卡的新 id 有三类：审核请求、交付任务、发布记录。

### 6. 执行器禁用，且本卡多一条「不碰平台」

宪法 IX 之外，本卡自己加一条更强的：**不调用任何平台发布 API，不产生任何外发请求**。「发布」在本阶段**只是一条人录入的记录**，系统不代表任何人向任何地方发布。`scripts/check-diagnostics-no-upload.mjs` 的形状是现成的守卫写法。

### 7. 与 `feedback-learning` 的边界

`feedback-learning` 在登记表里**依赖 `review-delivery`**，方向是「它读我」。**本卡只存记录，不做任何聚合、统计、趋势或建议**——那些属于 `feedback-learning`，方向反了就会变成循环依赖，`check:content-boundaries` 的环检测会红。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把一版渠道稿交出去审，并拿回处置 (Priority: P1)

小张写完了小红书那篇的渠道稿，存成了第 3 版。他提交审核。审核人小李看到的是**第 3 版的全文**，不是小张此刻编辑框里的内容——即使小张在等审核的时候又改了两轮。小李写下意见并选择「要求修改」。小张看到意见，改完存成第 5 版，再次提交审核。两次审核请求都在，各自指着自己那一版。

**Why this priority**：SOP §6.2 的底线是「没有模型时仍可人工审核」。没有这一条，审核这一步在产品里根本不存在；后两条都建立在「有一个被审过的东西」之上。

**Independent Test**：只实现这一条即可验收——提交一版、给出处置、再提交一版，两条请求各自绑定正确的版本 id。交付与发布都不必存在。

**Acceptance Scenarios**：

1. **Given** 某文档有第 3 版，**When** 提交审核，**Then** 产生一条 `pending` 的审核请求，绑定的版本 id 就是第 3 版。
2. **Given** 审核请求已提交，**When** 作者随后又存了第 4、第 5 版，**Then** 该请求绑定的版本**一个字节都没变**——「提交审核会冻结具体渠道版本」（§7.1 原文）。
3. **Given** 一条 `pending` 请求，**When** 审核人处置为 `changes_requested` 并写下意见，**Then** 状态与意见都被记下，且**谁在什么时候做的**可追。
4. **Given** 同一篇文档已有一条终态请求，**When** 再次提交审核，**Then** 成功，产生**第二条**请求——重复提交是正常的产品行为，不是冲突。
5. **Given** 一条已处置的请求，**When** 任何人试图改写它的意见或处置，**Then** 不存在这样的路径（见 **Q3** 的裁决口径）。
6. **Given** 请求属于 A 品牌，**When** B 品牌的成员按 id 读它，**Then** 得到与「不存在」**逐字节相同**的拒绝。

### User Story 2 - 排一个交付待办，然后把稿子交出去 (Priority: P2)

审核通过后，小张建一个交付任务：渠道是小红书，计划时间是周四上午十点。**系统不会在周四替他发**——那是一条人看的待办。周四他把稿子导出，交给运营同事，把任务标成「已交接」。中途如果要等一张配图，他把任务标成 `held` 并写原因；要是这篇不做了，标 `cancelled`。

**Why this priority**：它是审核与发布之间的那一段。没有它，「审过了」与「发出去了」之间没有任何可安排、可追踪的东西。

**Independent Test**：建任务 → ready → scheduled（带时间）→ handed_off（带交接方式），另跑一条 held 与一条 cancelled。**全程没有任何外发请求**。

**Acceptance Scenarios**：

1. **Given** 一条交付任务，**When** 设为 `scheduled` 并给一个计划时间，**Then** 时间被记下，**且到点时系统什么也不做**——没有定时器、没有队列、没有发布调用。
2. **Given** 一条 `scheduled` 任务，**When** 标为 `handed_off`，**Then** 必须同时记下**交接方式**（导出 / 交给运营者）。
3. **Given** 任务在等一样东西，**When** 标为 `held`，**Then** 必须记下原因；**When** 条件满足后回到 `ready`，**Then** 两次迁移都在记录里。
4. **Given** 任务已 `cancelled`，**When** 试图再把它推进，**Then** 被拒绝，且拒绝说明它已终止。
5. **Given** 任务引用的审核请求不是通过状态，**When** 建任务或推进它，**Then** 按 **Q2** 的裁决处理（暂定：允许建，但推进到 `ready` 之后需要一条通过的审核）。

### User Story 3 - 发布这件事由人说了算，并且要说清凭什么 (Priority: P3)

稿子发出去了（由运营同事在小红书后台手动发的）。小张回到系统里录一条发布记录：**是谁说的**（他自己转述运营同事）、**证据是什么**（作品链接）、**怎么核验的**（他本人点开链接看过）。第二天链接失效了，他再录一条 `removed`。第一条记录**原样留着**。

**Why this priority**：它是 §9.2 的底线——不能让系统自称发布成功。三个必填项的存在本身就是这条底线：没有声明者、没有证据、没有核验方式的「已发布」，等于系统在替人做保证。

**Independent Test**：录一条 `reported_published`（三项必填齐全）→ 录一条 `verified_published` → 录一条 `removed`；三条都在，第一条逐字节不变。

**Acceptance Scenarios**：

1. **Given** 要录一条发布记录，**When** 声明者、证据、核验方式任一缺失，**Then** 拒绝并**点名缺哪一项**（不是一句「参数错误」）。
2. **Given** 已录入一条 `reported_published`，**When** 再录一条 `verified_published`，**Then** 两条都在；查询「当前状态」得到最新那条。
3. **Given** 一条已录入的记录，**When** 任何人试图修改或删除它，**Then** 不存在这样的端点。
4. **Given** 核验方式取值不在受控集内，**When** 提交，**Then** 400 并点名该字段。
5. **Given** 发布记录存在，**When** 任何一段代码试图据此发起外发请求，**Then** 不存在这样的路径——守卫用例扫模块源码。

### Edge Cases

- **提交审核时文档还没有任何版本**：拒绝。没有版本就没有可冻结的东西，而「顺手存一版」会把人没决定过的内容写进历史（024 FR-009 已拒绝过这种兜底）。
- **提交审核的文档不是渠道稿**：暂定允许（正文也可以被审）。§7.1 说的是「冻结具体渠道版本」，那是**冻结**的口径，不是**只有渠道稿能审**的限制。若应当限制，见 **Q4** 的附带问。
- **审核请求被取消后又想审**：再提交一条新的。`cancelled` 是终态。
- **同一版被审两次**：合法，两条请求。与 023 的「一版简报可多次开始」同构。
- **交付任务的计划时间是过去时间**：允许——人可能在补记一件已经排过的事。**系统不据此做任何事**，所以过去时间不构成错误。
- **审核请求被取消，而交付任务已引用它**：见 **Q2**。暂定：交付任务保留引用与自身状态，不被级联改动（也没有级联可用——无外键）。
- **工作区在写入过程中被删**：删除栅栏拒绝，与「工作区不存在」同形，不留半条记录。
- **发布记录的证据是一段文字而不是链接**：允许。§9.2 要的是「证据」，不是「URL」；强制 URL 会把「运营同事发了截图给我」这种真实情形挡在外面。

## Requirements *(mandatory)*

### Functional Requirements

**审核请求**

- **FR-001**：系统 MUST 允许把**某文档的某一个具体版本**提交审核，绑定的 MUST 是 work-editor 的不可变版本稳定键（`version_id`），MUST NOT 是文档 id 或「当前版本」这类会变的指针。
- **FR-002**：审核请求的状态 MUST 是 `pending` / `changes_requested` / `approved` / `rejected` / `cancelled`（§7.1 原文），受控集以 Go 枚举为准、库 `CHECK` 兜底。
- **FR-003**：`pending` MUST 是唯一的初始状态；其余四个 MUST 是终态；终态之间 MUST NOT 互相迁移。
- **FR-004**：提交审核 MUST 同时冻结一份**不可变的交付快照**，记下提交那一刻的渠道与被审版本等上下文（**内容见 Q1**）。事后修改文档、版本以外的任何配置 MUST NOT 改变它。
- **FR-005**：同一文档 MUST 可以被提交审核多次，每次产生一条独立的请求；重复提交 MUST NOT 被当作冲突拒绝。
- **FR-006**：处置 MUST 记下审核意见、处置人与处置时间。
- **FR-007**：审核请求 MUST NOT 提供修改已处置记录的路径（**存储形态见 Q3**）。

**交付任务**

- **FR-008**：交付任务的状态 MUST 是 `draft` / `ready` / `scheduled` / `handed_off` / `cancelled` / `held`（§7.1 原文）。
- **FR-009**：`scheduled` MUST 带一个计划时间，且该时间 MUST 只是人看的待办——系统 MUST NOT 因此在任何时刻自动执行任何事（无定时器、无队列、无发布调用）。
- **FR-010**：`handed_off` MUST 带**交接方式**，受控集覆盖「导出」与「交给运营者」两种（**取值见 Q4**）。
- **FR-011**：`held` MUST 带原因；从 `held` 回到 `ready` MUST 是合法迁移，且两次迁移 MUST 都留下记录。
- **FR-012**：`cancelled` MUST 是终态；已取消的任务 MUST NOT 被推进。
- **FR-013**：交付任务 MUST 记下渠道；渠道取值 MUST 走受控集（**来源见 Q4**）。
- **FR-014**：交付任务与审核请求的关系 MUST 按 **Q2** 的裁决；无论哪种裁决，**数据库里 MUST NOT 有外键**，关系在应用代码里解。

**发布记录**

- **FR-015**：发布记录的状态 MUST 是 `reported_published` / `verified_published` / `failed` / `removed` / `unknown`（§7.1 原文）。
- **FR-016**：每条记录 MUST 带**声明者**、**证据**、**核验方式**三项，三项 MUST 必填；缺任一项 MUST 拒绝并**点名**缺的那一项。
- **FR-017**：声明者与核验方式 MUST 走受控集（**取值见 Q5**）；证据 MUST 是自由文本（一段话、一个链接、一句「运营同事发了截图」都算）。
- **FR-018**：发布记录 MUST 只插不改不删：没有 UPDATE 语句，没有 DELETE 语句（工作区删除链那一条除外），没有更新端点，没有删除端点。守卫用例照 022 / 023 的形状扫查询文件。
- **FR-019**：「当前发布状态」MUST 由最新一条记录给出，MUST NOT 另存一份可变的当前状态列——两份真相里总有一份会错。

**共同约束**

- **FR-020**：所有读写 MUST 按 `workspace_id` 过滤；越权 MUST 经 `workspace-core` 产出与「不存在」同形的拒绝，且同一类拒绝的响应体 MUST 逐字节相同（`trace_id` 除外）。
- **FR-021**：每一条写入 MUST 在同一事务内先取工作区删除栅栏（#104）。
- **FR-022**：每一条改变状态的操作 MUST 在同一事务内写审计（`Store.AuditTx`），审计写失败即整体回滚。
- **FR-023**：本卡 MUST NOT 调用模型、MUST NOT 起真实执行器、**MUST NOT 发起任何外发请求**；最后一条 MUST 有守卫用例。
- **FR-024**：本卡 MUST NOT 做任何聚合、统计或建议——那属于 `feedback-learning`，它依赖本模块而不是相反。
- **FR-025**：新表 MUST 遵守 R1–R6，并 MUST 进工作区删除清单，删除链同一 CTE 里各有一条按 `workspace_id` 的 `DELETE`。
- **FR-026**：每个带路径参数的新端点 MUST 有一条穿过真实中间件、参数值 ≠ 上下文值的用例（第 12 步）。本卡的路径参数有两类（`{reviewId}` / `{deliveryId}`，发布记录只有集合端点），**两类各有一条**。
- **FR-027**：交付 MUST 拆成「存储与接口 PR」与「页面 PR」两次。
- **FR-028**：页面 MUST 只复用既有 Multica 组件，MUST NOT 新增控件、MUST NOT 改样式；四语言 MUST 齐。
- **FR-029**：MUST NOT 写 UI 单测；界面项 MUST 进 `manual-ui-todo.md`。
- **FR-030**：本卡 MUST NOT 引用 `ip-profile` 或 `topic-planning` 的 Go 包；需要它们的 id 时 MUST 存字符串（登记表里没有这两条依赖方向）。

### Key Entities

- **审核请求（Review Request）**：一次「请人看这一版」。绑定一个不可变 `version_id`、一个渠道、一份冻结的交付快照；有五个状态、一段意见、处置人与时间。被交付任务引用。
- **交付任务（Delivery Task）**：一件「把这篇交出去」的待办。带渠道、计划时间（人看的）、交接方式；六个状态。**它不是调度器的输入。**
- **发布记录（Publication Record）**：一条人录入的「它现在在外面是什么状态」。五个状态，每条带声明者、证据、核验方式。**只插不改**，当前状态是最新一条。
- **作品版本（既有，024）**：`content_artifact_version.version_id`，append-only。审核请求绑定它。
- **作品与文档（既有，024）**：`content_work` / `content_artifact`。本卡只存它们的 id 字符串。

## Success Criteria *(mandatory)*

- **SC-001**：提交审核后对同一文档再存 3 个版本，读回该请求绑定的版本内容**逐字节不变**；一条用例。
- **SC-002**：同一文档连续提交两次审核，产生两条 id 不同的请求，**第一条逐字节不变**；一条用例。
- **SC-003**：审核请求的五个状态、交付任务的六个状态、发布记录的五个状态，**每一个合法迁移各一条用例**；每一条**非法**迁移（终态再推进、跳过 `pending` 直接终态、`cancelled` 复活）各一条用例。
- **SC-004**：发布记录的三个必填项**各缺一次**，三次都被拒且**各自点名**缺的那一项；三条用例，不合并。
- **SC-005**：发布记录与状态迁移记录的守卫用例：查询文件里出现 `UPDATE` 或删除链之外的 `DELETE` 即红；一次可编译变异（加一条 UPDATE）确认它会红。
- **SC-006**：外发守卫：模块源码里不存在任何 HTTP 客户端调用；一次可编译变异（加一个 `http.Get`）确认它会红。
- **SC-007**：两类路径参数 id（`{reviewId}` / `{deliveryId}`）**各有一条**穿过真实中间件、参数 ≠ 上下文值的用例；把别的工作区的 id 填进来得到与「不存在」同形的拒绝，两种拒绝体**互相逐字节相同**。
- **SC-008**：删一个工作区后，四张新表在该工作区的行数**各自**为 0；四条用例（表数随 Q1 / Q3 的裁决变化，裁决后回写）。
- **SC-009**：接入合同三条全绿，落地模块数 **+1**；迁移规则 R1–R6 逐条全绿，其中 R5 确认建表迁移不含 `PRIMARY KEY` / `UNIQUE`，R6 确认每条索引登记名与迁移逐字相同、建表迁移未被登记。
- **SC-010**：`scheduled` 的计划时间到点后系统无任何动作：代码里不存在读取该时间的调度路径；一条检索用例。

## Assumptions

1. **「提交审核会冻结具体渠道版本」的「冻结」是引用不可变版本，不是复制全文**。版本表本身 append-only，引用它即等于冻结；复制一份全文会造出第二份可能不一致的真相（与 024 拒绝复制快照字段同一理由）。
2. **本卡不定义「谁可以审」**。审核人是工作区成员即可；角色化的审核权限（只有 owner 能批）不在本卡，也没有既有实体可挂。
3. **交付任务与发布记录之间不强制一一对应**。一次交接可能对应多条发布记录（发了又删又发），反过来也可能有记录而没有任务（补记历史）。
4. **本卡不动 work-editor 的任何表**。「已审核版本永不删除」在 024 是结构保证（没有删除路径），本卡不另加保护。
5. **`source-inbox` 虽在依赖表里但本卡不用**。
6. 界面沿用账号页 / 选题页既有的 Settings 版式，不引入第二套视觉语言。

## Out of Scope

- 任何模型调用、任何自动审核、任何自动发布（EP-06 / EP-08 / 平台接入）。
- 定时执行：`scheduled` 只是待办，本卡**不引入任何调度器**。
- 反馈的聚合、统计、趋势、复盘建议（`feedback-learning`）。
- 角色化审核权限、多级审核、会签。
- 平台数据回流（阅读量、互动数）——那需要平台 API，本卡明确不碰。
- 附件与素材引用清单（等 W-03）。
- 桌面端接线与侧边栏入口（与 `/topics`、`/accounts` 一致，URL 直达）。

### Q1：「交付快照」到底是什么

Issue 原话是「审核绑定不可变版本**和交付快照**」。仓库里叫「快照」的只有 EP-04b 的 `content_start_snapshot`（**输入**快照）。三种读法：

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（暂定推荐）** | 审核请求行上一列 `snapshot jsonb`，记提交那一刻的渠道、被审版本、文档、作品、（可得时的）开始快照 id | 不加表；照抄 023 的既有手法 |
| B | 新建独立的「交付快照」表，审核请求与交付任务都引用它 | 多一张表与三个索引；换来两者共享同一份冻结上下文 |
| C | 「交付快照」就是 EP-04b 的输入快照，审核请求同时引用 `version_id` 与 `snapshot_id` | 不加表，但语义错位：输入快照记的是**开工时**的配置，不是**提交审核时**的交付上下文 |

**需要 §8 原文**：如果 §8 写明了交付快照包含哪几项，A 的列清单按原文定。

### Q2：交付任务与审核请求的关系

| 选项 | 含义 |
|---|---|
| **A（暂定推荐）** | 交付任务**可选地**引用一条审核请求；推进到 `ready` 之后的状态要求被引用的请求是 `approved`，`draft` 阶段不要求 |
| B | 强制引用且必须 `approved` 才能建任务 |
| C | 完全不引用，两者平行 |

B 挡住了「一边等审一边排期」；C 让「审过了才能交付」这条产品规则无处落地。

### Q3：状态迁移记在哪里

审核请求与交付任务都会迁移状态。两种形态：

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（暂定推荐）** | 主行的 `status` 列**可变**（照 `content_topic_card.status`），**每次迁移另写一条不可变的迁移记录**（谁、何时、从什么到什么、原因/意见） | 多一张 append-only 表；换来完整的处置历史与 §7.1「记录动作」的口径 |
| B | 只有可变的 `status` 列，迁移历史靠审计事件 | 少一张表；但审计事件是诊断读模型（会脱敏、会按保留期清），拿它当产品历史用是借用 |
| C | 全 append-only：主行也只插不改，当前状态取最新一条 | 表最少；但「列出所有待审请求」要对每个请求取最新一条，查询会变难看 |
