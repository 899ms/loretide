## SOP 原文（§8 / §9.1 / §9.2 / §9.3，主控 2026-09-21 提供）

**下面每一句都是原文，不是转述。**本规格的每一条受控集、每一个必填项、每一条「系统不做什么」都要能指回其中一句；指不回去的就是我发明的，已在「裁决记录」里单独标出。

**§8 审核**

> 通过审核的对象是**具体渠道、具体文档版本及附件、具体交付配置的快照**。AI 的自检报告作为审核参考，不能执行人工通过动作。
>
> 内容、附件或目标账号发生变化时，现有审核记录仍属于原快照。新的交付组合需要重新审核；系统不得把"已通过"自动套在新版本上。
>
> 渠道首版四个：小红书图文/视频、微信公众号文章、抖音短视频、视频号短视频（「属于设计建议」，可增）。
>
> 个人模式可用"确认并提交审核"或"审核通过并安排交接"的连续操作减少跳转，后台仍分别保存记录。

**§9.1 交接与登记**

> 审核通过后生成 `DeliveryPackage`，含冻结的渠道正文、媒体文件或缺失说明、制作说明、来源附录、目标渠道、交接者及版本清单。用户设定时间后，日历记录本次交接安排。到期后产生站内待办；用户导出或复制稿件并到平台发布。导出成功、复制完成或交接给他人都不自动等于发布成功。运营者登记实际发布时间、平台账号、页面链接或内容 ID、截图/回执、是否在平台上修改。若平台编辑了正文，保留发布后快照或差异说明；无法拿到完整正文时将版本匹配标为 unknown。

**§9.2 边界**

> 渠道适配指内容格式与文件导出，不包括向平台创建草稿、写入排期或直接发布。
>
> 忘记登记时工作台继续显示"待登记"，不推断平台状态。运营者可标记实际发布失败、延后或取消，并注明原因。系统不保存平台发布密钥，也不提供发布执行接口。

**§9.3 目标变更**

> 用户把新稿选为交付目标，或更改附件、账号及实质性渠道配置时，相关待执行任务进入 held，直到新快照审核完成。用户也可明确选择继续交付旧的已审核快照，界面展示版本号和预览。已经实际发布的内容保留原记录；……不改写历史。

### 5. 写路径与授权

- 写事务**第一句**取 `LockForContentDiagnosticWrite`（#104 的删除栅栏），不靠「顺便审计了」间接获得；

### 6. 执行器禁用，且本卡多一条「不碰平台」

宪法 IX 之外，本卡自己加一条更强的：**不调用任何平台发布 API，不产生任何外发请求**。「发布」在本阶段**只是一条人录入的记录**，系统不代表任何人向任何地方发布。`scripts/check-diagnostics-no-upload.mjs` 的形状是现成的守卫写法。

### 7. 与 `feedback-learning` 的边界

`feedback-learning` 在登记表里**依赖 `review-delivery`**，方向是「它读我」。**本卡只存记录，不做任何聚合、统计、趋势或建议**——那些属于 `feedback-learning`，方向反了就会变成循环依赖，`check:content-boundaries` 的环检测会红。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把一版渠道稿交出去审，并拿回处置 (Priority: P1)

小张写完了小红书那篇的渠道稿（`kind = channel_draft`，目标账号是品牌的小红书号），存成了第 3 版。他提交审核。审核人小李看到的是**第 3 版的全文**，不是小张此刻编辑框里的内容——即使小张在等审核的时候又改了两轮。小李写下意见并选择「要求修改」。小张看到意见，改完存成第 5 版，再次提交审核。两次审核请求都在，各自指着自己那一版。

**Why this priority**：SOP §6.2 的底线是「没有模型时仍可人工审核」。没有这一条，审核这一步在产品里根本不存在；后两条都建立在「有一个被审过的东西」之上。

**Independent Test**：只实现这一条即可验收——提交一版、给出处置、再提交一版，两条请求各自绑定正确的版本 id。交付与发布都不必存在。

**Acceptance Scenarios**：

1. **Given** 某文档有第 3 版，**When** 提交审核，**Then** 产生一条 `pending` 的审核请求，绑定的版本 id 就是第 3 版。
2. **Given** 审核请求已提交，**When** 作者随后又存了第 4、第 5 版，**Then** 该请求绑定的版本**一个字节都没变**——「提交审核会冻结具体渠道版本」（§7.1 原文）。
3. **Given** 一条 `pending` 请求，**When** 审核人处置为 `changes_requested` 并写下意见，**Then** 状态与意见都被记下，且**谁在什么时候做的**可追。
4. **Given** 同一篇文档已有一条终态请求，**When** 再次提交审核，**Then** 成功，产生**第二条**请求——重复提交是正常的产品行为，不是冲突。
5. **Given** 一条已处置的请求，**When** 任何人试图改写它的意见或处置，**Then** 不存在这样的路径；状态怎么变的记在**独立的、只插不改的迁移记录**里（裁决 Q3=A）。
6. **Given** 请求属于 A 品牌，**When** B 品牌的成员按 id 读它，**Then** 得到与「不存在」**逐字节相同**的拒绝。

### User Story 2 - 排一个交付待办，然后把稿子交出去 (Priority: P2)

审核通过后，小张建一个交付任务：渠道是小红书，计划时间是周四上午十点。**系统不会在周四替他发**——那是一条人看的待办。周四他把稿子导出，交给运营同事，把任务标成「已交接」。中途如果要等一张配图，他把任务标成 `held` 并写原因；要是这篇不做了，标 `cancelled`。

**Why this priority**：它是审核与发布之间的那一段。没有它，「审过了」与「发出去了」之间没有任何可安排、可追踪的东西。

**Independent Test**：建任务 → ready → scheduled（带时间）→ handed_off（带交接方式），另跑一条 held 与一条 cancelled。**全程没有任何外发请求**。

**Acceptance Scenarios**：

1. **Given** 一条交付任务，**When** 设为 `scheduled` 并给一个计划时间，**Then** 时间被记下，**且到点时系统什么也不做**——没有定时器、没有队列、没有发布调用。
2. **Given** 一条 `scheduled` 任务，**When** 标为 `handed_off`，**Then** 必须同时记下**交接方式**（`export` 导出 / `copy` 复制 / `handed_to_operator` 交给运营者）；**且这三种都不等于发布成功**——作品此刻仍然不是「已发布」（§9.1 原文）。
3. **Given** 任务在等一样东西，**When** 标为 `held`，**Then** 必须记下原因；**When** 条件满足后回到 `ready`，**Then** 两次迁移都在记录里。
4. **Given** 任务已 `cancelled`，**When** 试图再把它推进，**Then** 被拒绝，且拒绝说明它已终止。
5. **Given** 任务引用的审核请求不是通过状态，**When** 建任务，**Then** 允许（`draft` 阶段可以一边等审一边排期）；**When** 推进到 `ready` 及之后，**Then** 被拒，直到那条请求是 `approved`（裁决 Q2=A）。
6. **Given** 一条已排期的任务引用着第 3 版的已通过快照，**When** 小张把第 5 版选为交付目标（或换了附件、换了账号、改了实质性渠道配置），**Then** 该任务**自动进入 `held`**，直到新快照审核通过；**或者** 小张明确选择「继续交付第 3 版的已审快照」，**Then** 任务回到原状态，且这个选择被记进迁移记录（§9.3）。

### User Story 3 - 发布这件事由人说了算，并且要说清凭什么 (Priority: P3)

稿子发出去了（由运营同事在小红书后台手动发的）。在小张回来登记之前，工作台一直显示这篇**待登记**——系统不去猜它到底发没发。小张回到系统里录一条发布记录：发布时间、平台账号、**页面链接或内容 ID**、回执说明（「运营同事发了截图」）、**怎么核验的**（他本人点开链接看过，写进 `verification_note`），并注明平台有没有改过正文。平台把标题改了，他标 `platform_edited = true` 并写下改了什么；正文他拿不全，`version_match` 记 `unknown`。第二天链接失效了，他再录一条 `removed`。第一条记录**原样留着**。

**Why this priority**：它是 §9.2 的底线——**不推断平台状态**，不让系统自称发布成功。必填项的存在本身就是这条底线：没有链接/内容 ID 的「已发布」、没有核验说明的「已核验」，等于系统在替人做保证。

**Independent Test**：录一条 `reported_published`（带链接）→ 录一条 `verified_published`（带链接与核验说明）→ 录一条 `removed`；三条都在，第一条逐字节不变。交接完成但一条都没录时，读路径给出「待登记」。

**Acceptance Scenarios**：

1. **Given** 要录一条 `reported_published` 或 `verified_published`，**When** 缺 `page_url_or_content_id`（或 `verified_published` 缺 `verification_note`），**Then** 拒绝并**点名缺哪一项**（不是一句「参数错误」）。
2. **Given** 已录入一条 `reported_published`，**When** 再录一条 `verified_published`，**Then** 两条都在；查询「当前状态」得到最新那条。
3. **Given** 一条已录入的记录，**When** 任何人试图修改或删除它，**Then** 不存在这样的端点。
4. **Given** `version_match` 取值不在 `matched` / `differs` / `unknown` 之内，**When** 提交，**Then** 400 并点名该字段。**核验方式与声明者是自由文本，没有受控集**——SOP 没给枚举，本卡不发明（裁决 Q5）。
5. **Given** 发布记录存在，**When** 任何一段代码试图据此发起外发请求，**Then** 不存在这样的路径——守卫用例扫模块源码。**系统也不保存任何平台发布密钥、不提供任何发布执行接口**（§9.2 原文）。
6. **Given** 一条 `handed_off` 的交付任务且尚无发布记录，**When** 读这篇作品的发布状态，**Then** 得到派生的「待登记」；**Then** 录一条记录后「待登记」消失。**「待登记」不是存储里的状态**。

### Edge Cases

- **提交审核时文档还没有任何版本**：拒绝。没有版本就没有可冻结的东西，而「顺手存一版」会把人没决定过的内容写进历史（024 FR-009 已拒绝过这种兜底）。
- **提交审核的文档不是渠道稿**：**拒绝**（裁决：Q4 附带一问＝是）。§8 说审核对象是「具体渠道、具体文档版本及附件、具体交付配置的快照」——没有渠道就没有可审的对象。正文与研究报告不可提交；拒绝时点名 `kind`。
- **审核请求被取消后又想审**：再提交一条新的。`cancelled` 是终态。
- **同一版被审两次**：合法，两条请求。与 023 的「一版简报可多次开始」同构。
- **交付任务的计划时间是过去时间**：允许——人可能在补记一件已经排过的事。**系统不据此做任何事**，所以过去时间不构成错误。
- **审核请求被取消，而交付任务已引用它**：交付任务保留引用与自身状态，不被级联改动（也没有级联可用——无外键）。但它**推不动**：FR-014 要求 `ready` 及之后被引用的请求是 `approved`，所以它卡在原地，界面要说明卡在哪里。
- **工作区在写入过程中被删**：删除栅栏拒绝，与「工作区不存在」同形，不留半条记录。
- **发布记录的证据是一段文字而不是链接**：`page_url_or_content_id` 接受**链接或内容 ID**（§9.1 原文就是「页面链接或内容 ID」），其余情形写进自由文本的 `receipt_note`。强制 URL 会把「运营同事发了截图给我」和「公众号只有一个内容 ID」两种真实情形都挡在外面。
- **拿不到平台上的完整正文**：`version_match` 记 `unknown`（§9.1 原文），**不当作失败、不阻断**。把「我不知道」记成 `differs` 会在日后被读成「平台改过」。
- **平台在发布后编辑了正文**：`platform_edited = true` + `edit_note`。**被审的那一版一个字节都不动**（§9.3「不改写历史」）。

## Requirements *(mandatory)*

### Functional Requirements

**审核请求**

- **FR-001**：系统 MUST 允许把**某文档的某一个具体版本**提交审核，绑定的 MUST 是 work-editor 的不可变版本稳定键（`version_id`），MUST NOT 是文档 id 或「当前版本」这类会变的指针。
- **FR-002**：审核请求的状态 MUST 是 `pending` / `changes_requested` / `approved` / `rejected` / `cancelled`（§7.1 原文），受控集以 Go 枚举为准、库 `CHECK` 兜底。
- **FR-003**：`pending` MUST 是唯一的初始状态；其余四个 MUST 是终态；终态之间 MUST NOT 互相迁移。
- **FR-004**：提交审核 MUST 同时冻结一份**不可变的交付快照**，键**恰好八个**（裁决 Q1=A，按 §8「具体渠道、具体文档版本及附件、具体交付配置」定死）：`channel`、`work_id`、`artifact_id`、`version_id`、`account_id`、`start_snapshot_id`（可为空串，空串是真实状态）、`attachments`（数组）、`delivery_config`（对象）。写入后 MUST NOT 存在任何更新该列的路径。
- **FR-004a**：`attachments` 在本阶段 MUST 恒为空数组——附件清单是 W-03 的事，本卡没有可引用的存储。MUST 有一条负例断言没有任何写路径能往里塞东西。
- **FR-004b**：`delivery_config` 是**扩展键对象**，首版 MUST 只放渠道模板标识。它的存在是为了让「具体交付配置」这一项在 §8 的原文里有落点，而不是等到需要时再加一次迁移。
- **FR-004c**：**「已通过」MUST NOT 被自动套在新版本上**（§8 原文）。通过只对该快照有效：同一文档的新版本、换附件、换目标账号，MUST 产生**新的**审核请求；MUST NOT 存在任何把旧请求的 `approved` 迁移到新版本的路径。这是结构保证——`approved` 写在绑定着具体 `version_id` 的那一行上，没有第二处可以读它。
- **FR-005**：同一文档 MUST 可以被提交审核多次，每次产生一条独立的请求；重复提交 MUST NOT 被当作冲突拒绝。
- **FR-006**：处置 MUST 记下审核意见、处置人与处置时间。
- **FR-006a**：**通过动作 MUST 只能由人执行**（§8 原文「AI 的自检报告作为审核参考，不能执行人工通过动作」）。本阶段执行器全线禁用是结构保证；另 MUST 有一条守卫断言模块源码里不存在任何模型调用。
- **FR-007**：审核请求 MUST NOT 提供修改已处置记录的路径。状态变化 MUST 写进**独立的、只插不改的迁移记录**（裁决 Q3=A），记下谁、何时、从什么到什么、原因。
- **FR-007a**：**只有渠道稿可以提交审核**（裁决：Q4 附带一问＝是，依据 §8「审核对象是具体渠道的…快照」）。`kind ≠ channel_draft` 的文档提交 MUST 被拒并**点名** `kind`。
- **FR-007b**：审核请求 MUST 记下目标账号（`account_id`）——§8 把「目标账号」算进快照，且「更改…目标账号」是 §9.3 里触发重审的三件事之一。

**交付任务**

- **FR-008**：交付任务的状态 MUST 是 `draft` / `ready` / `scheduled` / `handed_off` / `cancelled` / `held`（§7.1 原文）。
- **FR-009**：`scheduled` MUST 带一个计划时间，且该时间 MUST 只是人看的待办——系统 MUST NOT 因此在任何时刻自动执行任何事（无定时器、无队列、无发布调用）。
- **FR-009a**：§9.1 的「到期后产生站内待办」MUST 由**读时派生**给出（`scheduled_at` 已过且尚未 `handed_off`），MUST NOT 由任何后台任务、定时器或队列产生。**「到期」是一次比较，不是一个事件。**
- **FR-010**：`handed_off` MUST 带**交接方式**，受控集**恰好三个**：`export`（导出）/ `copy`（复制）/ `handed_to_operator`（交给运营者）——§9.1 原文点名的就是这三种动作。
- **FR-010a**：**三种交接方式 MUST NOT 被当作发布成功**（§9.1 原文「导出成功、复制完成或交接给他人都不自动等于发布成功」）。`handed_off` MUST NOT 产生任何发布记录，MUST NOT 让任何读路径把作品显示为「已发布」。
- **FR-011**：`held` MUST 带原因；从 `held` 回到 `ready` MUST 是合法迁移，且两次迁移 MUST 都留下记录。
- **FR-011a**（§9.3）：交付任务引用的审核快照与**当前选定的交付目标**不一致时——新稿被选为交付目标，或附件、账号、实质性渠道配置被更改——该任务 MUST 自动进入 `held`，直到新快照审核通过。用户 MUST 可以明确选择**继续交付旧的已审核快照**；该选择 MUST 被记进迁移记录，界面 MUST 展示被交付快照的版本号与预览。
- **FR-012**：`cancelled` MUST 是终态；已取消的任务 MUST NOT 被推进。
- **FR-013**：渠道受控集 MUST 是**恰好四个**（§8 首版）：`xiaohongshu`（小红书图文/视频）、`wechat_mp`（微信公众号文章）、`douyin`（抖音短视频）、`shipinhao`（视频号短视频）。MUST 有一条用例**读 `ip-profile` 的 Go 源文件**比对两边的平台清单（裁决 Q4=A；`review-delivery` 的依赖表里没有 `ip-profile`，所以不能 import）。
- **FR-014**（裁决 Q2=A）：交付任务 MUST 可以**可选地**引用一条审核请求；推进到 `ready` **及之后**的任何状态 MUST 要求被引用的请求是 `approved`，`draft` 阶段 MUST NOT 要求。**数据库里 MUST NOT 有外键**，关系在应用代码里解。
- **FR-014a**：`held`、`cancelled`、发布失败、延后 **MUST 带原因**（§9.2「注明原因」）；缺原因 MUST 被拒绝并**点名**。

**发布记录**

- **FR-015**：发布记录的状态 MUST 是 `reported_published` / `verified_published` / `failed` / `removed` / `unknown`（§7.1 原文）。
- **FR-016**：每条记录 MUST 记下**系统 actor**（谁在系统里录的，由服务端从会话取，MUST NOT 由调用方指定）；另有可选的自由文本 `declared_by`，用于「我转述的是运营同事小王」这种情形。
- **FR-017**（裁决 Q5：**原文没有枚举，本卡不发明枚举**）。发布记录的字段 MUST 是：
  - `page_url_or_content_id`——§9.1 的「页面链接或内容 ID」，`reported_published` / `verified_published` **必填**；
  - `receipt_note`——自由文本，§9.1 的「截图/回执」（截图上传本身等 W-03）；
  - `verification_note`——自由文本的核验说明，`verified_published` **必填**；
  - `published_at`——§9.1 的「实际发布时间」；
  - `platform_account`——自由文本，§9.1 的「平台账号」；
  - `platform_edited`（布尔）+ `edit_note`——§9.1 的「是否在平台上修改」与差异说明；
  - `version_match`——**恰好三态** `matched` / `differs` / `unknown`（§9.1 原文点名了 `unknown`）。
- **FR-017a**：拿不到完整正文时 `version_match` MUST 可以是 `unknown`，且 `unknown` MUST NOT 被当作失败或阻断后续操作。把「我不知道」记成 `differs` 会在日后被读成「平台改过」。
- **FR-017b**：`failed` 与 `removed` MUST 带原因，落在 `receipt_note` 上且此时 MUST 非空（§9.2「注明原因」）。**这一处是我在 Q5 的字段清单里就近选的落点**——清单里没有专门的 `reason` 列，见「裁决记录」的「我补的两处」。
- **FR-018**：发布记录 MUST 只插不改不删：没有 UPDATE 语句，没有 DELETE 语句（工作区删除链那一条除外），没有更新端点，没有删除端点。守卫用例照 022 / 023 的形状扫查询文件。
- **FR-019**：「当前发布状态」MUST 由最新一条记录给出，MUST NOT 另存一份可变的当前状态列——两份真相里总有一份会错。
- **FR-019a**：**「待登记」MUST 是派生显示**（存在 `handed_off` 的交付任务、且该文档没有任何发布记录），MUST NOT 是存储里的状态，且系统 MUST NOT 据此推断平台上的真实状态（§9.2「忘记登记时工作台继续显示"待登记"，不推断平台状态」）。
- **FR-019b**：平台在发布后编辑了正文时 MUST 能记下（`platform_edited` + `edit_note`），且 MUST NOT 改写被审的那一版——**已发布的内容保留原记录，不改写历史**（§9.3）。

**共同约束**

- **FR-020**：所有读写 MUST 按 `workspace_id` 过滤；越权 MUST 经 `workspace-core` 产出与「不存在」同形的拒绝，且同一类拒绝的响应体 MUST 逐字节相同（`trace_id` 除外）。
- **FR-021**：每一条写入 MUST 在同一事务内先取工作区删除栅栏（#104）。
- **FR-022**：每一条改变状态的操作 MUST 在同一事务内写审计（`Store.AuditTx`）**与一条迁移记录**，任一写失败即整体回滚。
- **FR-023**：本卡 MUST NOT 调用模型、MUST NOT 起真实执行器、**MUST NOT 发起任何外发请求**、**MUST NOT 保存任何平台发布密钥**、**MUST NOT 提供任何发布执行接口**（§9.2 原文）。最后三条 MUST 有守卫用例。
- **FR-023a**：渠道适配在本卡的含义 MUST 只是「内容格式与文件导出」，MUST NOT 包括向平台创建草稿、写入排期或直接发布（§9.2 原文）。
- **FR-024**：本卡 MUST NOT 做任何聚合、统计或建议——那属于 `feedback-learning`，它依赖本模块而不是相反。
- **FR-025**：新表 MUST 遵守 R1–R6，并 MUST 进工作区删除清单，删除链同一 CTE 里各有一条按 `workspace_id` 的 `DELETE`。
- **FR-026**：每个带路径参数的新端点 MUST 有一条穿过真实中间件、参数值 ≠ 上下文值的用例（第 12 步）。本卡的路径参数有两类（`{reviewId}` / `{deliveryId}`，发布记录只有集合端点），**两类各有一条**。
- **FR-027**：交付 MUST 拆成「存储与接口 PR」与「页面 PR」两次。
- **FR-028**：页面 MUST 只复用既有 Multica 组件，MUST NOT 新增控件、MUST NOT 改样式；四语言 MUST 齐。
- **FR-029**：MUST NOT 写 UI 单测；界面项 MUST 进 `manual-ui-todo.md`。
- **FR-030**：本卡 MUST NOT 引用 `ip-profile` 或 `topic-planning` 的 Go 包；需要它们的 id 时 MUST 存字符串（登记表里没有这两条依赖方向）。
- **FR-031**（§8 个人模式）：界面 MAY 提供「确认并提交审核」「审核通过并安排交接」这类连续操作以减少跳转，但后台 MUST **分别保存记录**——一次连续操作 MUST 产生两条独立的记录与各自的迁移记录，MUST NOT 合并成一条。

### Key Entities

- **审核请求（Review Request）**：一次「请人看这一版」。绑定一个不可变 `version_id`、一个渠道、一个目标账号、一份冻结的八键交付快照；有五个状态、一段意见、处置人与时间。被交付任务引用。
- **状态迁移记录（Transition）**：审核请求与交付任务的每一次状态变化各一条，**只插不改不删**，记谁、何时、从什么到什么、原因。
- **交付任务（Delivery Task）**：一件「把这篇交出去」的待办。带渠道、计划时间（人看的）、交接方式；六个状态。**它不是调度器的输入。**
- **发布记录（Publication Record）**：一条人录入的「它现在在外面是什么状态」。五个状态，带链接或内容 ID、回执、核验说明、发布时间、平台账号、平台是否改过、版本匹配三态。**只插不改**，当前状态是最新一条。
- **DeliveryPackage（§9.1，**派生视图，不是第五张表**）**：「已通过的审核请求 + 它的快照 + 引用它的交付任务」拼出来的只读视图。见「裁决记录」的「我补的两处」。
- **作品版本（既有，024）**：`content_artifact_version.version_id`，append-only。审核请求绑定它。
- **作品与文档（既有，024）**：`content_work` / `content_artifact`。本卡只存它们的 id 字符串。

## Success Criteria *(mandatory)*

- **SC-001**：提交审核后对同一文档再存 3 个版本，读回该请求绑定的版本内容**逐字节不变**；一条用例。
- **SC-002**：同一文档连续提交两次审核，产生两条 id 不同的请求，**第一条逐字节不变**；一条用例。
- **SC-003**：审核请求的五个状态、交付任务的六个状态，**每一个合法迁移各一条用例**；每一条**非法**迁移（终态再推进、跳过 `pending` 直接终态、`cancelled` 复活、`handed_off` 之后再动）各一条用例。发布记录**没有状态机**，不在此列。
- **SC-004**：三条独立的必填用例，**不合并**：`reported_published` 缺 `page_url_or_content_id`、`verified_published` 缺 `page_url_or_content_id`、`verified_published` 缺 `verification_note`；三次都被拒且**各自点名**缺的那一项。
- **SC-004a**：`version_match = unknown` 的记录**可以录入**、不被当作失败、不阻断后续录入；一条用例。越界的第四个取值被拒并点名；一条用例。
- **SC-005**：发布记录与状态迁移记录的守卫用例：查询文件里出现 `UPDATE` 或删除链之外的 `DELETE` 即红；一次可编译变异（加一条 UPDATE）确认它会红。
- **SC-006**：**四条**守卫：模块源码里不存在任何 HTTP 客户端调用、不存在任何平台密钥的读写、不存在任何发布执行接口（§9.2）、不存在任何模型调用（§8「AI 不能执行人工通过动作」，FR-006a）；一次可编译变异（加一个 `http.Get`）确认会红。
- **SC-007**：两类路径参数 id（`{reviewId}` / `{deliveryId}`）**各有一条**穿过真实中间件、参数 ≠ 上下文值的用例；把别的工作区的 id 填进来得到与「不存在」同形的拒绝，两种拒绝体**互相逐字节相同**。
- **SC-008**：删一个工作区后，**四张**新表在该工作区的行数**各自**为 0；四条用例。
- **SC-009**：接入合同三条全绿，落地模块数 **+1**；迁移规则 R1–R6 逐条全绿，其中 R5 确认建表迁移不含 `PRIMARY KEY` / `UNIQUE`，R6 确认每条索引登记名与迁移逐字相同、建表迁移未被登记。
- **SC-010**：`scheduled` 的计划时间到点后系统无任何动作：代码里不存在读取该时间去执行的调度路径；一条检索用例。「到期待办」只出现在读时派生的结果里（SC-013a）。
- **SC-011**：交付快照的键**恰好八个**，多一个或少一个即红；一条用例。`attachments` 恒为空数组：不存在任何往里写东西的路径，一条负例。
- **SC-012**：把任务推到 `handed_off`（三种交接方式**各一条**）之后，该文档的发布记录数仍为 **0**，读路径**不**把它显示为「已发布」；三条用例。**这是 §9.1 那句「都不自动等于发布成功」的唯一可执行形式。**
- **SC-013**：「待登记」是派生的：有 `handed_off` 任务且无发布记录时读路径给出它，录一条记录后它消失；两条用例。另一条检索用例确认**存储层没有任何叫「待登记」的状态值或列**。
- **SC-013a**：计划时间已过且未交接时，读路径把任务标为「到期待办」；把时间改到将来后它消失；两条用例。**没有任何后台任务参与**。
- **SC-014**（§9.3）：一条引用第 3 版已审快照的 `scheduled` 任务，把第 5 版选为交付目标后**自动变 `held`**；明确选择「继续交付第 3 版」后回到原状态，且该选择与原因都在迁移记录里；两条用例。换附件、换账号各再一条。
- **SC-015**：`kind ≠ channel_draft` 的文档提交审核被拒并**点名 `kind`**；一条用例。
- **SC-016**（§8 个人模式）：一次「审核通过并安排交接」的连续操作产生**两条独立记录**（一条处置、一条交付任务）与**各自的迁移记录**；一条用例。
- **SC-017**：`approved` **不会**被套到新版本上：同一文档在请求通过后存新版本，读新版本的审核状态得到「未提交」而不是「已通过」；一条用例。
- **SC-018**：受控集**恰好五个**（`channel` / 三套 `status` / `handoff_method` / `version_match` / `subject_kind`），一条检索用例确认**没有第六个**——特别是没有声明者或核验方式的枚举（裁决 Q5）。另一条用例**读 `ip-profile` 的 Go 源文件**比对四个渠道值（FR-013）。
- **SC-019**：`draft` 阶段引用一条 `pending` 请求建任务**成功**；把它推到 `ready` **被拒**并说明是前置条件不满足；请求变 `approved` 后同一次推进**成功**；三条用例（FR-014）。
- **SC-020**：**四条**缺原因的用例：交付任务的 `held` / `cancelled`、发布记录的 `failed` / `removed`，各缺一次原因，四次都被拒且**各自点名**（§9.2「注明原因」，FR-014a / FR-017b）。
- **SC-021**：发布记录的声明者由服务端从会话取：body 里塞一个别人的 `actor_id` **不生效**，存下来的仍是调用者；一条用例（FR-016）。
- **SC-022**：工作区删除已提交后，**五条写路径**（提交审核 / 处置 / 建任务 / 推进状态 / 录发布）各有一条真实 DB 用例被栅栏拒绝，且不留半条记录（FR-021，#104 口径）。

## Assumptions

1. **「提交审核会冻结具体渠道版本」的「冻结」是引用不可变版本，不是复制全文**。版本表本身 append-only，引用它即等于冻结；复制一份全文会造出第二份可能不一致的真相（与 024 拒绝复制快照字段同一理由）。
2. **本卡不定义「谁可以审」**。审核人是工作区成员即可；角色化的审核权限（只有 owner 能批）不在本卡，也没有既有实体可挂。§8 只要求「不能由 AI 执行通过动作」，那一条本卡有（FR-006a）。
3. **交付任务与发布记录之间不强制一一对应**。一次交接可能对应多条发布记录（发了又删又发），反过来也可能有记录而没有任务（补记历史）。
4. **本卡不动 work-editor 的任何表**。「已审核版本永不删除」在 024 是结构保证（没有删除路径），本卡不另加保护。
5. **`source-inbox` 虽在依赖表里但本卡不用**。
6. 界面沿用账号页 / 选题页既有的 Settings 版式，不引入第二套视觉语言。
7. **§9.1 的 `DeliveryPackage` 不是第五张表**，是派生的只读视图（见「裁决记录」）。
8. **§9.1 的「日历记录本次交接安排」在本卡就是那条 `scheduled_at`**。本仓库没有日历实体，也不该为此新建一个；界面上它是一个时间，不是一个日历。

## Out of Scope

- 任何模型调用、任何自动审核、任何自动发布（EP-06 / EP-08 / 平台接入）。
- 定时执行：`scheduled` 只是待办，本卡**不引入任何调度器**；「到期待办」是读时派生（FR-009a）。
- 附件与媒体文件本身（W-03）：快照里的 `attachments` 本阶段恒为空数组；§9.1 的「媒体文件或缺失说明」在本阶段只有「缺失说明」那一半。
- 截图上传（W-03）：`receipt_note` 本阶段只是自由文本。
- 反馈的聚合、统计、趋势、复盘建议（`feedback-learning`）。
- 角色化审核权限、多级审核、会签。
- 平台数据回流（阅读量、互动数）——那需要平台 API，本卡明确不碰；§9.2 原文也写死了「系统不保存平台发布密钥，也不提供发布执行接口」。
- 附件与素材引用清单（等 W-03）。
- 桌面端接线与侧边栏入口（与 `/topics`、`/accounts` 一致，URL 直达）。

### 我在裁决之外补的两处（都标出来了，改起来很便宜）

1. **`failed` / `removed` 的原因落在 `receipt_note`**（FR-017b）。Q3 要求「失败、延后必带 reason」，而 Q5 定死的字段清单里**没有**专门的 `reason` 列。我没有新增一列，而是复用了自由文本的 `receipt_note` 并要求此时非空。**若主控要的是独立一列，改的是 FR-017b 与建表迁移各一处。**
2. **`DeliveryPackage` 是派生视图，不是第五张表**（Key Entities / Assumptions 7）。§9.1 列的七项在本卡的落点是：冻结的渠道正文、目标渠道、版本清单 ← 审核请求的快照；交接者与时间 ← 交付任务；**媒体文件与来源附录本阶段只有「缺失说明」那一半**（附件等 W-03）。为此建第五张表会存一份与快照重复的真相。**若 §9.1 要求它是可独立引用的实体，那是一张表 + 三个迁移。**

### 一处我特意没做

「延后」没有变成第七个状态。§9.2 的原文是「标记实际发布失败、延后或取消，并注明原因」——延后在本卡就是**改 `scheduled_at` 或进 `held`**，两者都会写迁移记录与原因。加一个 `postponed` 状态会与 `held` 语义重叠，而 §7.1 的六个状态里没有它。
