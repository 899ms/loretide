## User Scenarios & Testing *(mandatory)*

### User Story 1 - 发出去两周后，把真实数据抄进来 (Priority: P1)

小张那篇小红书两周前发的，当时录了一条发布记录。今天工作台提醒他「这条该补录了」。他打开去平台看了一眼，把阅读量、点赞、收藏、评论数抄进来，选了「发布后 14 天」这个观测时点。系统没有去平台查任何东西——这几个数字是他自己抄的，界面上也这么写着。

**Why this priority**：这是 §10.1 的整句话。没有它，「真实结果」在产品里根本不存在，§10.2 的复盘与 §10.3 的经营结论都无从谈起。

**Independent Test**：对一条已有的发布记录补录一次指标，读回来数值不变、观测时点记下了、谁录的记下了。反馈摘录与工作台都不必存在。

**Acceptance Scenarios**：

1. **Given** 一条 `verified_published` 的发布记录，**When** 补录一组指标，**Then** 产生一条指标记录，绑定那条发布记录，并记下观测时点、录入人与录入时间。
2. **Given** 同一条发布记录，**When** 在另一个观测时点再补录一次，**Then** 产生**第二条**记录，第一条**逐字节不变**——同一篇在不同时点有不同的数，这是数据不是冲突。
3. **Given** 指标已录入，**When** 任何人试图改写或删除它，**Then** 不存在这样的路径。
4. **Given** 指标记录存在，**When** 任何一段代码试图据此向平台发起请求，**Then** 不存在这样的路径——守卫用例扫模块源码。
5. **Given** 记录属于 A 品牌，**When** B 品牌的成员按 id 读它，**Then** 得到与「不存在」**逐字节相同**的拒绝。
6. **Given** 工作区在写入过程中被删，**When** 补录提交，**Then** 删除栅栏拒绝，与「工作区不存在」同形，不留半条记录。

### User Story 2 - 把人说的话原样记下来 (Priority: P2)

评论区有人说「这篇看完就去买了」，运营同事私信里转述了另一条。小张把两条都摘进来：一条来源是平台评论，一条是他人转述，各自记下时间。他**没有**把它们总结成一句话——总结是 §10.2 的事，这里只存原话。

**Why this priority**：§5.2 说「这些是偏好信号，单次操作不永久改变 IP 定位」。摘录是那个信号的原始形态；先有原样保留的事实，才谈得上后面的聚合。

**Independent Test**：摘三条来源不同的反馈，三条都在，顺序与内容不变。指标登记与工作台都不必存在。

**Acceptance Scenarios**：

1. **Given** 一条发布记录，**When** 摘录一条反馈（正文 + 来源 + 发生时间），**Then** 产生一条记录，**只插不改不删**。
2. **Given** 已有摘录，**When** 再摘一条，**Then** 两条都在，第一条逐字节不变。
3. **Given** 来源取值不在受控集内（**若最终有受控集，见 Q4**），**When** 提交，**Then** 400 并**点名**该字段。
4. **Given** 摘录正文是一段很长的中文，**When** 提交，**Then** 长度上限**按 rune 计数**，不是按字节——按字节会让中文只有英文三分之一的余地。
5. **Given** 摘录存在，**When** 读列表，**Then** 按发生时间倒序，**不做任何汇总、计数或情感判断**。

### User Story 3 - 知道哪些还没补，以及复盘还没开始 (Priority: P3)

工作台第五项现在能显示「待补录的反馈」了：发出去已经过了观测时点、却还没有指标记录的那些。小张点进去逐条补。旁边「AI 复盘」那一栏写着「等数据」，不是空白，也不是转圈——它明确告诉他这一步还没接上。

**Why this priority**：§2 的第五项今天是一块占位（026 FR-005b）。本卡是让它有数据源的那一半。

**Independent Test**：造一条过了观测时点、没有指标的发布记录 → 出现在待补录里；补录之后消失。

**Acceptance Scenarios**：

1. **Given** 一条发布记录已过观测时点且没有任何指标记录，**When** 读待补录列表，**Then** 它在里面。
2. **Given** 同一条记录补录了指标，**When** 再读，**Then** 它不在了。
3. **Given** 一条发布记录还没到观测时点，**When** 读待补录列表，**Then** 它不在里面。
4. **Given** 待补录是**读时派生**的，**When** 检索代码，**Then** 存储层没有任何叫「待补录」的状态值或列——与 025 的「待登记」同一口径。
5. **Given** 「AI 复盘」一栏，**When** 打开页面，**Then** 它**存在**、显示占位状态、写明「暂不可用（执行器禁用，EP-08 接入）」，**没有任何伪造的复盘结论**。

### Edge Cases

- **发布记录没有 `published_at`**（025 允许为空，补记历史时可能不知道）：该条**不进待补录**，因为算不出到期时点。界面写明原因，不是悄悄漏掉。
- **同一条发布记录在多个观测时点各一组指标**：合法，这是本卡的正常形态（US1-2）。
- **一篇作品有多条发布记录**（发了又删又发）：指标绑的是**发布记录**不是作品，所以各自独立。「这篇的数据」是跨记录的读问题，本卡只存不聚合。
- **平台上的数拿不到**（被限流、看不到后台）：指标字段**允许留空**，留空是「还不知道」而不是 0。**这一条很要紧**：把不知道记成 0 会在任何后续聚合里变成真实的坏数据。
- **发布记录状态是 `failed` / `removed`**：仍可补录指标（被删之前可能有数据），也仍可摘录反馈。
- **摘录里出现个人信息**：本卡不做任何脱敏或识别。这是人抄进来的原话，产品历史要逐字保留；**若需要脱敏，那是另一张卡的事**，这里标明而不是偷偷处理。
- **补录时那条发布记录已被工作区删除链带走**：栅栏拒绝，同形拒绝体。

## Requirements *(mandatory)*

### Functional Requirements

**人工指标登记**

- **FR-001**：系统 MUST 允许对**一条具体的发布记录**登记一组人工指标，绑定的 MUST 是 `publication_record_id`。
- **FR-002**：同一条发布记录 MUST 可以在不同观测时点各登记一组；重复登记 MUST NOT 被当作冲突拒绝。
- **FR-003**：每条指标记录 MUST 记下**观测时点**、**录入人**（服务端从会话取，MUST NOT 由调用方指定）与录入时间。
- **FR-004**：指标记录 MUST 只插不改不删：没有 UPDATE，没有 DELETE（工作区删除链除外），没有更新端点，没有删除端点。守卫用例照 022 / 025 的形状扫模块源码，**且必须断言有 `INSERT INTO`**，否则空模块也绿。
- **FR-005**：指标字段的清单 MUST 按 **Q1** 的裁决。**原文没给的 MUST NOT 发明枚举**（025 Q5 的口径）。
- **FR-006**：任何指标字段 MUST 允许留空，且留空 MUST 与 0 区分开——「还不知道」和「是零」在后续聚合里是两件事。
- **FR-007**：指标 MUST 指回作品版本，取法按 **Q2** 的裁决；**数据库里 MUST NOT 有外键**，关系在应用代码里解。

**反馈摘录**

- **FR-008**：系统 MUST 允许对一条发布记录摘录反馈：**正文**（自由文本，必填非空）、**来源**、**发生时间**。
- **FR-009**：来源的取值 MUST 按 **Q4** 的裁决；若 §10.1 没有给出枚举，则来源 MUST 退成自由文本、只保留「必填」。
- **FR-010**：摘录 MUST 只插不改不删，守卫同 FR-004。
- **FR-011**：文本长度上限 MUST 按 **rune** 计数，MUST NOT 按字节。
- **FR-012**：本卡 MUST NOT 对摘录做任何汇总、计数、分类或情感判断——那属于 §10.2。
- **FR-013**：本卡 MUST NOT 对摘录做脱敏或个人信息识别；若需要，MUST 是另一张卡。

**待补录与占位**

- **FR-014**：「待补录」MUST 是**读时派生**：发布记录有 `published_at`、已过观测时点、且没有任何指标记录。MUST NOT 是存储里的状态值或列。
- **FR-015**：`published_at` 为空的发布记录 MUST NOT 进待补录，且界面 MUST 写明原因，MUST NOT 悄悄漏掉。
- **FR-016**：观测时点的来源 MUST 按 **Q5** 的裁决。
- **FR-017**：「AI 复盘」MUST 以占位形式存在：状态取值按 **Q3** 的裁决（Issue 提到 `pending_data` / `queued`），MUST 写明暂不可用的原因，MUST NOT 隐藏、MUST NOT 停在加载态、**MUST NOT 产生任何伪造的复盘结论**。
- **FR-018**：本卡 MUST NOT 产生「待采纳 / 已采纳经营结论」（§10.3），也 MUST NOT 为它建表——那是后续卡片。

**共同约束**

- **FR-019**：所有读写 MUST 按 `workspace_id` 过滤；越权 MUST 经 `workspace-core` 产出与「不存在」同形的拒绝，同类拒绝体 MUST 逐字节相同（`trace_id` 除外）。
- **FR-020**：每一条写入 MUST 在同一事务内先取工作区删除栅栏（#104）。
- **FR-021**：每一条写入 MUST 在同一事务内写审计（`Store.AuditTx`），审计写失败即整体回滚。
- **FR-022**：本卡 MUST NOT 调用模型、MUST NOT 起真实执行器、**MUST NOT 发起任何外发请求**、**MUST NOT 保存任何平台凭据**——指标是人抄进来的，系统不去平台取数。前三条 MUST 有守卫用例。
- **FR-023**：新表 MUST 遵守 R1–R6，MUST 进工作区删除清单，删除链同一 CTE 里各有一条按 `workspace_id` 的 `DELETE`，且**每张表 MUST 有一个 `workspace_id` 打头的索引**。
- **FR-024**：每个带路径参数的新端点 MUST 有一条穿过真实 router 与中间件、参数值 ≠ 上下文值的用例（第 12 步）。

## Success Criteria *(mandatory)*

- **SC-001**：同一条发布记录在两个观测时点各登记一组指标 → 两条记录，**第一条逐字节不变**；一条用例。
- **SC-002**：指标与摘录两张表的守卫用例：模块源码出现 `UPDATE` 或删除链之外的 `DELETE` 即红；**且必须有 `INSERT INTO`**；一次可编译变异（加一条 UPDATE）确认它会红。
- **SC-003**：留空与 0 读回来不同：留空的字段读成「未填」，填 0 的读成 0；一条用例。**这两者混同是本卡最容易悄悄发生的数据损坏。**
- **SC-004**：不外发守卫：模块源码里不存在任何 HTTP 客户端调用、不存在任何平台凭据的读写、不存在任何模型调用；一次可编译变异（加一个 `http.Get`）确认会红。
- **SC-005**：待补录是派生的：造一条过了观测时点、无指标的发布记录 → 在列表里；补录后消失；`published_at` 为空的那条**始终不在**；三条用例。另一条检索用例确认**存储层没有「待补录」这个状态值或列**。
- **SC-006**：摘录按 rune 计数：一条刚好到上限的中文摘录被接受，超一个字被拒；两条用例。
- **SC-007**：路径参数 id 各有一条穿过真实 router 与中间件、参数 ≠ 上下文值的用例；填别的工作区的 id 得到与「不存在」同形的拒绝，拒绝体**互相逐字节相同**。
- **SC-008**：删一个工作区后，新表在该工作区的行数**各自**为 0；每张表一条用例。
- **SC-009**：接入合同三条全绿，**落地模块数 6 → 7**；迁移规则 R1–R6 逐条全绿，其中 R5 确认建表迁移不含 `PRIMARY KEY` / `UNIQUE`，R6 确认每条索引登记名与迁移逐字相同、建表迁移未被登记。
- **SC-010**：本卡不做聚合：检索用例确认模块里不存在 `sum(` / `avg(` / `count(` 之类的聚合查询（按 `workspace_id` 计数的删除清单用例除外），也不存在任何分类或打分路径。
- **SC-011**：AI 复盘占位：它**存在**、状态可读、写明原因；检索用例确认模块里**没有任何**产生复盘内容的路径。
- **SC-012**：渠道受控集（若本卡需要）与 `ip-profile` 的 Go 源文件对表一致；一条用例。**不 import**。
- **SC-013**：工作区删除已提交后，每条写路径各有一条真实 DB 用例被栅栏拒绝，且不留半条记录。

## Assumptions

1. **指标是人抄进来的，不是系统取的**。本卡不接任何平台 API，这与 025 的「不推断平台状态」是同一条底线的延伸。
2. **绑定的是发布记录，不是作品**。一篇发了又删又发会有多条发布记录，各自的数据互不相干；「这篇总共多少阅读」是读端的聚合问题，不在本卡。
3. **留空不是 0**。所有指标字段可空，且存储与读端都要能区分。
4. **本卡不定义「谁可以补录」**。工作区成员即可；角色化权限没有既有实体可挂。
5. **`source-inbox` / `knowledge-base` 不参与**，登记表里也没有这两条方向。
6. 界面沿用账号页 / 选题页 / 作品页既有的 Settings 版式，不引入第二套视觉语言。
7. **观测时点在拿到 §3.2 的口径之前，按 Q5 的推荐值处理**：存在指标记录自己身上，而不是先去建一个品牌级设置。

## Out of Scope

- **§10.2 AI 复盘**与 **§10.3 经营结论沉淀**：依赖执行器，本卡只留占位（FR-017 / FR-018）。
- 任何聚合、统计、趋势、对比、评分、建议——包括「这篇比上篇好」这种最轻的比较。
- 平台数据自动回流：需要平台 API，本卡明确不碰。
- 「待采纳 / 已采纳经营结论」的存储与流程。
- 品牌级「反馈观察时点」设置页（若 Q5 裁成要，它是另一张卡）。
- 摘录的脱敏与个人信息识别。
- 桌面端接线与侧边栏入口（与 `/topics`、`/accounts` 一致，页内展开）。

### Q2：指标怎么指回版本？
