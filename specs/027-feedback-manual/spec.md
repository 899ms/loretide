## SOP 与 PRD 原文（主控 2026-09-21 提供）

**下面每一句都是原文，不是转述。** 本规格的每一个列名、每一个受控集、每一条「系统不做什么」都要能指回其中一句；指不回去的就是我补的，已在「裁决记录」里单独标出。

**§10.1 记录真实结果**

> 首版采用表单与 CSV 导入。每条观测关联发布记录，保存**平台、账号、指标名、数值、单位、统计窗口、采样时间、录入人、证据附件和数据来源类型**。曝光、阅读、播放、完播、点赞、评论、收藏、分享、关注、私信和转化按平台可获得情况填写。未知填空；0 只表示已确认的零值。不同平台的"阅读"和"播放"分别保留，不直接合并排名。评论、私信和线索支持脱敏摘录、分类、自己的解释。数据以运营者手工记录和文件导入进入系统，工作台帮助校验口径、整理和分析。

**§7.1「AI 复盘」行**

> | AI 复盘 | pending_data / queued → generating → generated / failed；可 edited / superseded | 报告直接可用；其中的结论可单独采纳、撤回 |

**§3.2 设定运营规则**

> 设定每周内容节奏、渠道模板、审核规则、默认时区、反馈观察时点。

**PRD R-044 / R-045**

> **R-044**：用表单/CSV 手工录入指标，保存平台定义、单位、观察窗口、采样时间、录入者与证据；空值与零值区分，更新保留历史。

> **R-045**：记录真实评论、私信、线索和自己的解读，支持脱敏、标签和附件；引用摘录与运营者判断分别保存。

**另外三段能指回本仓库文件的原文**（不是本轮提供的，但本规格用到）：

> **§2**（`specs/026` 开头抄录）：「日常使用从"今日工作台"开始。那里应同时呈现值得写的选题、正在推进的作品、需要处理的审核、到期交接和**待补录的反馈**。」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 去平台看了一眼，把真实的数抄进来 (Priority: P1)

小张那篇小红书发出去两周了。他打开平台后台，把曝光、阅读、点赞、收藏、评论几个数抄进来，各自写上单位与统计窗口（「发布后 14 天累计」），采样时间填的是他看这一眼的时刻。转化那一栏他**留空**——小红书后台看不到，而留空和「确认是 0」是两件事。系统没有去平台取任何数字，界面上也这么写着。

**Why this priority**：这是 §10.1 的整句话。没有它，「真实结果」在产品里不存在，§10.2 的复盘与 §10.3 的经营结论都无从谈起。

**Independent Test**：对一条已有的发布记录录一组指标，读回来数值不变、留空的仍是留空、录入人记下了。反馈摘录与工作台都不必存在。

**Acceptance Scenarios**：

1. **Given** 一条 `verified_published` 的发布记录，**When** 录一条曝光指标，**Then** 产生一条指标记录，绑定那条发布记录，十项字段各就各位，`source_type` 是系统写的 `manual`。
2. **Given** 同一条发布记录，**When** 在另一个统计窗口再录一次同一个指标名，**Then** 产生**第二条**记录，第一条**逐字节不变**——同一篇在不同窗口有不同的数，这是数据不是冲突。
3. **Given** 一个平台看不到的指标，**When** 留空提交，**Then** 存下来是空；**When** 另一条填 0 提交，**Then** 存下来是 0，**两者读回来可区分**（§10.1：「未知填空；0 只表示已确认的零值」）。
4. **Given** 指标名不在十一个之内，**When** 提交，**Then** 400 并**点名** `metric`。
5. **Given** 指标已录入，**When** 任何人试图改写或删除它，**Then** 不存在这样的路径——更正的办法是再录一条（R-044「更新保留历史」）。
6. **Given** 指标记录存在，**When** 任何一段代码试图据此向平台发起请求，**Then** 不存在这样的路径——守卫用例扫模块源码。
7. **Given** 记录属于 A 品牌，**When** B 品牌的成员读它，**Then** 得到与「不存在」**逐字节相同**的拒绝。
8. **Given** 工作区在写入过程中被删，**When** 提交，**Then** 删除栅栏拒绝，与「工作区不存在」同形，不留半条记录。

### User Story 2 - 把人说的话原样记下来，和我自己的看法分开 (Priority: P2)

评论区有人说「这篇看完就去买了」。小张把它摘进来，手动把对方昵称抹掉，来源选「评论」。他另起一栏写自己的解读：「转化点在第三段的对比」。**这两件事存在两列里**——一句是别人说的，一句是他想的，混成一段之后谁也分不出哪句是证据、哪句是判断。

**Why this priority**：§5.2 说「这些是偏好信号，单次操作不永久改变 IP 定位」。摘录是那个信号的原始形态；先有原样保留的事实，才谈得上后面的聚合。R-045 明写「引用摘录与运营者判断分别保存」。

**Independent Test**：摘三条来源不同的反馈，三条都在，摘录与解释各自独立，顺序与内容不变。

**Acceptance Scenarios**：

1. **Given** 一条发布记录，**When** 摘录一条反馈（脱敏摘录 + 来源 + 发生时间），**Then** 产生一条记录，**只插不改不删**。
2. **Given** 同一条摘录，**When** 另填「自己的解释」，**Then** 它存在**另一列**；两列都可以单独为空，也可以单独有内容。
3. **Given** 来源不在 `comment` / `private_message` / `lead` 之内，**When** 提交，**Then** 400 并**点名** `source_type`。
4. **Given** 摘录正文是一段很长的中文，**When** 提交，**Then** 长度上限**按 rune 计数**，不是按字节——按字节会让中文只有英文三分之一的余地。
5. **Given** 摘录存在，**When** 读列表，**Then** 按发生时间倒序，**不做任何汇总、计数、分类或情感判断**。
6. **Given** 摘录里还留着真实姓名，**When** 提交，**Then** 系统**照样存下**——脱敏是**人做的**（§10.1「支持脱敏摘录」是支持人去脱敏，不是系统替他脱）。界面写明这一点。

### User Story 3 - 知道哪些还没补，以及复盘还没开始 (Priority: P3)

工作台第五项现在能显示「待补录的反馈」了：发出去了、却一条指标都没录的那些。小张点进去逐条补。旁边「AI 复盘」那一栏写着「待运行」，不是空白，也不是转圈——它明确告诉他这一步还没接上。

**Why this priority**：§2 的第五项今天是一块占位（026 FR-005b）。本卡是让它有数据源的那一半。

**Independent Test**：造一条已发布、没有指标的发布记录 → 出现在待补录里；补录一条指标之后消失。

**Acceptance Scenarios**：

1. **Given** 一条 `reported_published` 或 `verified_published` 的发布记录且没有任何指标记录，**When** 读待补录列表，**Then** 它在里面。
2. **Given** 同一条记录录了一条指标，**When** 再读，**Then** 它不在了。
3. **Given** 一条 `failed` / `removed` / `unknown` 的发布记录，**When** 读待补录列表，**Then** 它**不在**——没发出去的东西谈不上补录真实结果。
4. **Given** 待补录是**读时派生**的，**When** 检索代码，**Then** 存储层没有任何叫「待补录」的状态值或列——与 025 的「待登记」同一口径。
5. **Given** 「AI 复盘」一栏，**When** 打开页面，**Then** 它**存在**、状态是 `pending_data`、显示「待运行」并写明「暂不可用（执行器禁用，EP-08 接入）」，**没有任何伪造的复盘结论**。
6. **Given** §7.1 的状态集有七个值，**When** 检索本模块，**Then** 除 `pending_data` 外**没有任何路径能产生**其余六个——与 024 对 `generated` 的负例同一形状。

### Edge Cases

- **平台看不到某个指标**：留空。**这是本卡最要紧的一条**：把「不知道」记成 0，在任何后续聚合里都是真实的坏数据，而且不一致时没有任何东西会报警（§10.1：「未知填空；0 只表示已确认的零值」）。
- **同一条发布记录在多个统计窗口各一组指标**：合法，这是正常形态（US1-2）。
- **同一个指标名在同一个窗口录了两次（第二次是更正）**：**两条都留着**，读端取最新一条。R-044 的「更新保留历史」就是这个意思；改写第一条等于把错误的那一版抹掉，而「我当时抄错了」本身是历史的一部分。
- **一篇作品有多条发布记录**（发了又删又发）：指标绑的是**发布记录**不是作品，各自独立。「这篇总共多少阅读」是读端的聚合问题，**不在本卡**。
- **不同平台的「阅读」与「播放」**：**分开存、分开读**（§10.1 原文：「分别保留，不直接合并排名」）。本卡不提供任何把两者相加或排名的端点。
- **发布记录没有 `published_at`**（025 允许为空）：不影响待补录——首版判定不带时间逻辑（裁决 Q5=A）。
- **解不出版本**（补记历史时没有交付任务）：版本显示 `unknown`，与 025 `version_match` 的口径一致。**不因此拒绝录入**。
- **摘录里出现个人信息**：本卡不做任何自动脱敏或识别。脱敏是人做的；系统照存。**若要自动脱敏，那是另一张卡**，这里标明而不是偷偷处理。
- **粘贴的 CSV 有一行坏的**：见 FR-011a——整批拒绝并点名是第几行的哪一列，不做部分写入。

## Requirements *(mandatory)*

### Functional Requirements

**人工指标登记（§10.1 十项 + R-044）**

- **FR-001**：系统 MUST 允许对**一条具体的发布记录**登记一条人工指标观测，绑定的 MUST 是 `publication_record_id`（§10.1：「每条观测关联发布记录」）。
- **FR-002**：每条指标记录 MUST 保存 §10.1 点名的**十项**：`platform`、`account_id`、`metric`、`value`、`unit`、`window`（统计窗口）、`sampled_at`（采样时间）、`recorded_by`（录入人）、`evidence_note`（证据）、`source_type`（数据来源类型）。
- **FR-003**：`metric` 的受控集 MUST 是 §10.1 点名的**恰好十一个**：`impression`（曝光）、`read`（阅读）、`play`（播放）、`completion`（完播）、`like`（点赞）、`comment`（评论）、`favorite`（收藏）、`share`（分享）、`follow`（关注）、`direct_message`（私信）、`conversion`（转化）。**MUST NOT 有「其它」**——原文没给。
- **FR-004**：`value` MUST 可空，且**空与 0 MUST 可区分**：空是「未知」，0 是「已确认的零值」（§10.1 原文）。读端 MUST 保持这个区分，MUST NOT 把空读成 0。
- **FR-005**：`unit` MUST 是自由文本（§10.1 只说「单位」，没给枚举）。
- **FR-006**：`window` MUST 记录统计窗口。取值形态见「裁决记录」的补充项。
- **FR-007**：`recorded_by` MUST 由服务端从会话取，MUST NOT 由调用方指定——它是这行上唯一不可伪造的字段。
- **FR-008**：`source_type` MUST **由系统写入**，受控集 `manual` / `csv_import`，MUST NOT 是请求体里的字段。
- **FR-009**：`evidence_note` MUST 是自由文本。**证据附件本身等 W-03**，本阶段 MUST NOT 有任何附件存储路径，并 MUST 有一条负例。
- **FR-010**：指标记录 MUST 只插不改不删：没有 UPDATE，没有 DELETE（工作区删除链除外），没有更新端点，没有删除端点。更正 MUST 是**再录一条**（R-044「更新保留历史」）。守卫用例照 022 / 025 的形状扫模块源码，**且 MUST 断言有 `INSERT INTO`**，否则空模块也绿。
- **FR-011**：系统 MUST 支持批量录入（§10.1「表单与 CSV 导入」）。**首版的 CSV 是「粘贴 CSV 文本」**——解析在前端，提交的是已解析的行；文件上传等 W-03。
- **FR-011a**：批量录入 MUST 是**全有或全无**：任一行不合法则整批拒绝，并**点名第几行的哪一列**。部分写入会让人以为全录上了。
- **FR-012**：`platform` 的受控集 MUST 与 025 的渠道一致（四值），并 MUST 有一条**读 `ip-profile` Go 源文件对表**的用例——本模块 MUST NOT import 它（登记表里没有这条依赖）。
- **FR-013**：「阅读」与「播放」MUST 分开保存、分开读，系统 MUST NOT 提供把两者合并或排名的路径（§10.1：「分别保留，不直接合并排名」）。

**反馈摘录（§10.1 + R-045）**

- **FR-014**：系统 MUST 允许对一条发布记录摘录反馈，保存：`source_type`（受控集**恰好三项** `comment` / `private_message` / `lead`，原文点名「评论、私信和线索」，**无「其它」**）、`redacted_excerpt`（脱敏摘录）、`interpretation`（自己的解释）、`tags`（自由标签）、`occurred_at`（发生时间）、录入人。
- **FR-015**：`redacted_excerpt` 与 `interpretation` MUST 是**两列**，MUST NOT 合并成一段（R-045：「引用摘录与运营者判断分别保存」）。两列 MUST 可以各自为空。
- **FR-016**：脱敏 MUST 由人完成；系统 MUST NOT 做任何自动脱敏或个人信息识别，界面 MUST 写明这一点。
- **FR-017**：摘录 MUST 只插不改不删，守卫同 FR-010。
- **FR-018**：文本长度上限 MUST 按 **rune** 计数，MUST NOT 按字节。
- **FR-019**：本卡 MUST NOT 对摘录做任何汇总、计数、分类或情感判断——那属于 §10.2。

**待补录与 AI 复盘占位**

- **FR-020**：「待补录」MUST 是**读时派生**：发布记录的 `status` 是 `reported_published` 或 `verified_published`、且该记录没有任何指标记录。MUST NOT 是存储里的状态值或列。**首版 MUST NOT 带任何时间逻辑**（裁决 Q5=A：品牌级「反馈观察时点」属 §3.2 另卡）。
- **FR-021**：「AI 复盘」的状态受控集 MUST 是 §7.1 原文的**七个值**：`pending_data` / `queued` / `generating` / `generated` / `failed` / `edited` / `superseded`。
- **FR-022**：本卡 MUST 只产生 `pending_data`，界面显示「待运行」并写明「暂不可用（执行器禁用，EP-08 接入）」。MUST 有一条负例断言**本模块没有任何路径能产生其余六个值**（照 024 对 `generated` 的做法）。MUST NOT 隐藏该栏、MUST NOT 停在加载态、**MUST NOT 产生任何伪造的复盘结论**。
- **FR-023**：本卡 MUST NOT 产生「待采纳 / 已采纳经营结论」（§10.3），也 MUST NOT 为它建表。

**版本与工作台**

- **FR-024**（裁决 Q2=A）：指标 MUST 只绑 `publication_record_id`；版本在**读时**经 `delivery_task_id → review_request_id → version_id` 解出，**解不出时显示 `unknown`**，与 025 `version_match` 的口径一致。MUST NOT 改动 025 的表，**数据库里 MUST NOT 有外键**。
- **FR-025**（裁决 Q6=A 的附加要求）：本卡的**存储与接口 PR** MUST 同时：(a) 更新 `specs/026` 的 **FR-004**（把 `feedback-learning` 从「不读未落地模块」的名单里去掉）与 **FR-005b**（第五项不再是「暂不可用」）；(b) 提供今日工作台第五项要用的 **core 派生函数**。本卡的**页面 PR** MUST 接上第五项。
- **FR-026**：本卡页面 MUST 挂在 025 发布记录那一段之后：在 `review-delivery` 的页面组件上开一个**可选 render 插槽**，由 web 适配器注入，**MUST NOT 改登记表**（与 #161 对 `work-editor` 做的完全一样）。另 MUST 有从 `/{slug}/today` 第五项到此处的跳转。

**共同约束**

- **FR-027**：所有读写 MUST 按 `workspace_id` 过滤；越权 MUST 经 `workspace-core` 产出与「不存在」同形的拒绝，同类拒绝体 MUST 逐字节相同（`trace_id` 除外）。

### Key Entities

- **人工指标观测（Manual Metric）**：一次「我去平台看了一眼，这个数是这些」。十项字段，绑一条发布记录。**只插不改**；更正是再录一条。
- **反馈摘录（Feedback Excerpt）**：一条人说的话（已由人脱敏）**加上**录入者自己的解释，**两列分开**。带来源三选一、标签、发生时间。**只插不改**。
- **待补录（派生）**：已发布、却一条指标都没有的发布记录。**不是存储状态，首版不带时间逻辑。**
- **AI 复盘状态（受控集，只用到一个值）**：§7.1 的七个值；本卡只产生 `pending_data`。**没有报告表**——本阶段产生不出内容，建一张恒空的表只会让人以为它会被填。
- **发布记录（既有，025）**：`content_publication_record`，append-only。指标与摘录都绑它。
- **作品版本（既有，024）**：`content_artifact_version.version_id`，两跳解出，解不出是 `unknown`。

## Success Criteria *(mandatory)*

- **SC-001**：同一条发布记录在两个统计窗口各录一条同名指标 → 两条记录，**第一条逐字节不变**；一条用例。
- **SC-002**：**空与 0 可区分**：留空的读回来是「未知」，填 0 的读回来是 0，两者**不相等**；一条用例。另一条用例断言读端没有把空折成 0 的路径。**这是本卡最容易悄悄发生的数据损坏。**
- **SC-003**：`metric` 受控集**恰好十一个**，多一个少一个即红；越界值被拒并**点名** `metric`；两条用例。另一条检索用例确认**没有「其它」这个值**。
- **SC-004**：`source_type` 由系统写：走表单端点存下来是 `manual`，走导入端点是 `csv_import`；请求体里塞一个 `source_type` **不生效**；三条用例。
- **SC-005**：`recorded_by` 由服务端从会话取：请求体里塞别人的 id **不生效**；一条用例。
- **SC-006**：两张表的守卫用例：模块源码出现 `UPDATE` 或删除链之外的 `DELETE` 即红；**且必须有 `INSERT INTO`**；一次可编译变异（加一条 UPDATE）确认它会红。
- **SC-007**：批量录入全有或全无：一批三行、第二行的 `metric` 越界 → **一行都没写进去**，且拒绝**点名第 2 行的 `metric`**；两条用例（拒绝 + 行数仍为 0）。
- **SC-008**：不外发守卫：模块源码里不存在任何 HTTP 客户端调用、不存在任何平台凭据的读写、不存在任何模型调用；一次可编译变异（加一个 `http.Get`）确认会红。
- **SC-009**：**没有合并阅读与播放的路径**：检索用例确认模块里不存在把两个 `metric` 值相加或排名的代码；`read` 与 `play` 各自读出来互不影响；两条用例（§10.1 原文）。
- **SC-010**：摘录的两列分开：只填摘录 / 只填解释 / 两个都填，三种都能存下且读回来各在各的列；三条用例（R-045）。
- **SC-011**：`source_type`（摘录）受控集**恰好三项**，无「其它」；越界被拒并点名；两条用例。
- **SC-012**：摘录按 rune 计数：一条刚好到上限的中文摘录被接受，超一个字被拒；两条用例。
- **SC-013**：待补录是派生的：已发布无指标的在列表里；录一条指标后消失；`failed` / `removed` / `unknown` 的**始终不在**；三条用例。另一条检索用例确认**存储层没有「待补录」这个状态值或列**，**也没有任何时间比较**。
- **SC-014**：AI 复盘状态集**恰好七个**（§7.1 原文）；本模块**只产生 `pending_data`**，一条负例扫源码确认其余六个值没有产生路径；两条用例。**没有报告表**：迁移里不存在这样一张表。
- **SC-015**：版本两跳解出：有交付任务的解出 `version_id`；补记历史（`delivery_task_id` 为空串）的解出 `unknown` **且不拒绝录入**；两条用例。
- **SC-016**：`platform` 受控集与 `ip-profile` 的 Go 源文件对表一致；一条用例。**不 import**。
- **SC-017**：`evidence_note` 是自由文本且**没有附件路径**：检索用例确认模块里不存在任何文件上传或附件引用；一条用例。
- **SC-018**：删一个工作区后，两张新表在该工作区的行数**各自**为 0；两条用例。
- **SC-019**：接入合同三条全绿，**落地模块数 6 → 7**；迁移规则 R1–R6 逐条全绿，其中 R5 确认建表迁移不含 `PRIMARY KEY` / `UNIQUE`，R6 确认每条索引登记名与迁移逐字相同、建表迁移未被登记。
- **SC-020**：工作区删除已提交后，每条写路径各有一条真实 DB 用例被栅栏拒绝，且不留半条记录。
- **SC-021**：本卡不做聚合：检索用例确认模块里不存在 `sum(` / `avg(` 之类的聚合查询（删除清单的按 `workspace_id` 计数除外），也不存在任何分类或打分路径。
- **SC-022**（FR-025）：存储与接口 PR 落地后，`specs/026` 的 FR-004 名单里**不再有** `feedback-learning`，FR-005b **不再写「暂不可用」**；core 的第五项派生函数存在且有 node 测试。

## Assumptions

1. **指标是人抄进来的，不是系统取的**。本卡不接任何平台 API，这与 025 的「不推断平台状态」是同一条底线的延伸。
2. **绑定的是发布记录，不是作品**。一篇发了又删又发会有多条发布记录，各自的数据互不相干；「这篇总共多少阅读」是读端的聚合问题，不在本卡。
3. **留空不是 0**。所有指标字段可空，且存储与读端都要能区分。
4. **本卡不定义「谁可以补录」**。工作区成员即可；角色化权限没有既有实体可挂。
5. **`source-inbox` / `knowledge-base` 不参与**，登记表里也没有这两条方向。
6. 界面沿用账号页 / 选题页 / 作品页既有的 Settings 版式，不引入第二套视觉语言。
7. **观测窗口存在指标记录自己身上**（`window` + `sampled_at`，§10.1 原文的两个字段）。品牌级「反馈观察时点」是 §3.2 那张卡的活（裁决 Q5=A）。
8. **脱敏是人做的**。§10.1 说「支持脱敏摘录」，支持的是人去脱敏，不是系统替他脱。
9. **没有 AI 复盘报告表**。本阶段产生不出任何内容，建一张恒空的表只会让人以为它会被填。

## Out of Scope

- **§10.2 AI 复盘**与 **§10.3 经营结论沉淀**：依赖执行器，本卡只留占位（FR-017 / FR-018）。
- 任何聚合、统计、趋势、对比、评分、建议——包括「这篇比上篇好」这种最轻的比较。
- 平台数据自动回流：需要平台 API，本卡明确不碰。
- 「待采纳 / 已采纳经营结论」的存储与流程。
- 品牌级「反馈观察时点」设置页——属 §3.2 那张卡（裁决 Q5=A）。
- CSV **文件上传**：首版是「粘贴 CSV 文本」，文件上传与证据附件都等 W-03。
- 把不同平台的「阅读」与「播放」合并或排名（§10.1 明确禁止）。
- **自动**脱敏与个人信息识别（脱敏由人完成）。
- 桌面端接线与侧边栏入口（与 `/topics`、`/accounts` 一致，页内展开）。

### 我在裁决之外补的两处（都标出来了，改起来很便宜）

1. **没有 AI 复盘报告表。** Q3 定了状态集，但没说这个状态存在哪里。本阶段产生不出任何报告内容，所以我把它做成**派生**：没有报告就是 `pending_data`。建一张恒空的表只会让人以为它迟早会被填，而删掉一张已经推过的表要再加一个迁移。**若主控要的是一张真表，那是一张表 + 三个迁移。**
2. **`window`（统计窗口）的取值形态。** §10.1 点名了这个字段但没给形态，裁决写的是「自由文本或起止时间二选一，规格定」。我选**自由文本**：「发布后 14 天累计」「自然月」「上线首日」这类说法，起止时间表达不了，而强行拆成两个时间戳会逼人把不知道的边界编出来。**若要结构化，那是两列 `window_start` / `window_end` 加一条迁移。**

### 一处我特意没做

**没有把「阅读」和「播放」做成同一个指标名。** §10.1 的原文是「不同平台的'阅读'和'播放'分别保留，不直接合并排名」——它们在受控集里是 `read` 与 `play` 两个值，记录层天然分开，另加 SC-009 禁止任何合并或排名的路径。
