## 原文依据

初版规格没有这些原文，三处条款只能按 Issue 转述写。裁决已提供，本节把用得上的原句钉在这里，下文所有字段与规则都从这里推出。

**§3.3**：「优先导入已认可作品、常用参考资料、典型用户问题及可用的真实历史反馈。系统保留它们的**「历史导入」标识**。历史内容不知道采用了哪个原稿版本时，创建「发布后快照」，不虚构版本链。没有历史数据也可开始。」

**§4 表（步骤 1 / 3 / 4）**：

| 步骤 | 人做什么 | 系统做什么 | 产出 |
|---|---|---|---|
| 1 快速采集 | 粘贴链接、速记、上传文件或选择导出资料 | 记录输入类型、采集时间、标签、个人批注 | `Source` 创建成功；解析可继续后台进行 |
| 3 内容解析 | 必要时补标题、正文或上传可读文本 | 抽取正文/页码/时间码，**保留原件与哈希** | `SourceSnapshot`；状态 ready / partial / failed |
| 4 归类与判断 | 采纳分类，**说明为何收藏** | 建议摘要、实体、观点、问题与关联资料 | **原文、自动摘要和个人判断分开保存** |

**§4 段落**：「输入保存成功后即可离开页面；解析失败不丢失原始条目。**重复素材先提示合并关联，保留各次采集批注。** 网页更新生成新快照，历史作品继续引用旧快照。」「首版支持粘贴文本、公开网页及导出文件……」

**§7.1「素材解析」行**：「| 素材解析 | `pending → processing → ready / partial / failed` | **解析状态与知识是否确认分开** |」

**§11「随时」行**：「| 随时 | 收集想法、链接、文件、观察 | 快速入口与待整理收件箱 |」

**PRD**：
- **R-009**：支持速记、粘贴正文、URL、…；文件名、来源、采集时间、个人批注与解析状态可见。
- **R-010**：**原文件与正文快照分别保存**；每个快照保存抓取/解析时间、**内容哈希**、来源链接及页码/段落/时间码定位。部分解析必须明确标示。
- **R-011**：收件箱支持**批量标签、归档、关联已有来源、筛选和去重提示**；**内容相同不删除独立的收藏上下文与批注**。

**docs/12**：`source-inbox` 负责「登记来源、本地文件引用、哈希/缺失状态、解析输入」。

## Current State（以代码为准，2026-09-20 / `app-main` @ `fae5dce`）

### source-inbox 已登记、目录全空

`scripts/content-boundaries.json` 登记了它，依赖是 `["workspace-core", "diagnostics"]`。三个 root（`server/internal/content`、`packages/core/content`、`packages/views/content`）下**都没有 `source-inbox/` 目录**。

已落地的六个模块：`diagnostics`、`workspace-core`、`ip-profile`、`topic-planning`、`work-editor`、`review-delivery`。

### 缺口 A（已由 Q2 裁决）— topic-planning 没有结构化引用位

`topic-planning` 的依赖是 `["workspace-core", "ip-profile", "knowledge-base", "diagnostics"]`，**不含 `source-inbox`**（依赖链 `topic-planning → knowledge-base → source-inbox` 是二跳）。而且 `ExistingContentRelation` 与 `EvidenceGapsAndInvestment` 在 `server/internal/content/topic-planning/contract.go` 里都是 **`string`** 自由文本：

```go
ExistingContentRelation   string `json:"existing_content_relation"`
EvidenceGapsAndInvestment string `json:"evidence_gaps_and_investment"`
```

**裁决 Q2 = A：本卡不做选题卡引用。** 「选题卡引用素材条目」要改 022 已落地的契约，另立一张卡。

### 缺口 B（已裁决）— 今日工作台本卡不接

`/today` 今天是**六个区块**，顺序被 026 的 FR-005 钉死（§2 原文五项），FR-005a 把「账号配置缺项」定为排在五项之后的第六个附加区块。§11「随时」行的「快速入口与待整理收件箱」既不在五项内也不是第六项。

**裁决：本卡不接入**，由 026 的后续修订决定它是第七区块还是页头快速入口。本卡只保证数据可读。

### 缺口 C（已由原文解决）— 「历史导入」

全仓 grep 对「历史导入」/ `historical import` 零命中，此前无从判断。**§3.3 原文已给**：它是系统为导入的历史内容**保留的标识**。按裁决落为**布尔、创建时确定、此后不可改**。

### 可复用的既有模式

- **只插不改 + 状态列**：`review-delivery` 是「主行可改状态 + 一张只插不改的流水表」；`work-editor` 的版本表与 `topic-planning` 的简报表是纯 append-only。
- **只插不改的守卫用例**：扫模块源码里的 `UPDATE <table>` / `DELETE FROM <table>`，**并同时断言存在 `INSERT`**（少了后半条，空模块也是绿的）。
- **受控集**：Go 枚举权威 → 400 诊断式错误；DB `CHECK` 兜底（`review-delivery/contract.go` 的 `oneOf` + `ErrInvalid`）。
- **迁移**：下一个可用号 **516**（现有最大 515）。每张表三个文件：建表 + `id_unique_idx` + `workspace_idx`，各自单语句 `CREATE INDEX CONCURRENTLY`；**R5** 建表不内联 `PRIMARY KEY`/`UNIQUE`；**R6** 每个建索引的 up 登记进 `server/cmd/migrate/main.go` 的 `concurrentIndexCleanups`，名字逐字节一致，建表迁移不登记。
- **栅栏**：写事务第一条语句取 `LockForContentDiagnosticWrite`。
- **第 12 步**：每个带路径参数的端点，要有一条用例穿过真实中间件且**路径参数值与上下文值不同**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把看到的东西先收下来（Priority: P1）

运营者看到一段值得留着的文字（别人的帖子、自己的速记、一段访谈摘录），或者一个想回头再看的链接，**在一个地方把它收下来**，填上它是哪儿来的、为什么收，然后继续手头的事。不需要当场决定它属于哪个选题，也不需要等任何东西处理完——§4 原文：「输入保存成功后即可离开页面」。

**Why this priority**: 这是 §4 步骤 1。收不下来，后面的整理与引用都无从谈起。只做这一个故事就已经有用：一个可信的暂存处。

**Independent Test**: 粘贴一段文本、存下、刷新页面，它还在，并且能看出它是什么时候、由谁、从哪儿收的。

**Acceptance Scenarios**:

1. **Given** 收件箱是空的，**When** 粘贴一段文本、填标题与个人批注并保存，**Then** 列表里多一条，显示标题、类型「粘贴文本」、采集时间与录入人；**同时生成一条快照**，存下原文与它的内容哈希。
2. **Given** 一个链接，**When** 选「URL」类型、粘贴链接并填写批注，**Then** 存下且**不抓取该链接**、**不生成快照**；界面明确写出「不抓取，内容由人填写」。
3. **Given** 粘贴文本的正文为空，或 URL 类型没填链接，**When** 试图保存，**Then** 保存被拒绝并说明是哪个字段；**不产生**一条空条目。
4. **Given** 已存在的一条条目，**When** 任何后续操作，**Then** 它的类型、采集时间、录入人、历史导入标识与已生成的快照**永不改变**。

---

### User Story 2 - 整理成以后用得上的样子（Priority: P2）

运营者回到收件箱，把收下来的东西整理一遍：改标题、补批注与个人判断、打标签、归档。可以**一次选中多条**批量打标签或归档，可以按标签与状态筛选。每一次整理**留下痕迹**，而不是悄悄覆盖。

**Why this priority**: §4 步骤 4 与 R-011。「收成可复用资产」的「可复用」在这一步发生；没有它，收件箱只是一个越堆越高的粘贴板。但 US1 单独也能用。

**Independent Test**: 对一条条目做三次整理，历史里有三条记录，且原文与哈希始终未变。

**Acceptance Scenarios**:

1. **Given** 一条新收的条目，**When** 改标题、写个人判断并打两个标签，**Then** 列表显示新标题与标签；**原文与哈希不变**，且**个人判断与原文是分开的两处**（§4 步骤 4：「原文、自动摘要和个人判断分开保存」）。
2. **Given** 上一条，**When** 查看它的整理历史，**Then** 能看到每次改了什么、谁改的、什么时候。
3. **Given** 选中三条条目，**When** 批量打一个标签并批量归档，**Then** 三条都生效，且**各自**留下一条整理记录。
4. **Given** 一条已归档的条目，**When** 默认筛选下查看列表，**Then** 它不在其中；切到「已归档」筛选**仍可查到**；**没有任何删除操作**。
5. **Given** 一批带标签的条目，**When** 按标签与状态筛选，**Then** 只列出匹配的条目。

---

### User Story 3 - 重复的素材要看得出来，但不许被吃掉（Priority: P2）

运营者把一段两周前已经收过的文本又粘了一次。系统**提示这与某条已有条目内容相同**，但两条都留下——它们是两次不同的采集，各自的批注、采集时间与录入人都是独立的事实。

**Why this priority**: R-011 原文：「内容相同**不删除**独立的收藏上下文与批注」；§4：「重复素材**先提示**合并关联，保留各次采集批注」。这是一条明确的反自动化要求——合并是人的决定，不是系统的。

**Independent Test**: 粘贴同一段文本两次，得到两条条目、一条重复提示，两条的批注各自独立。

**Acceptance Scenarios**:

1. **Given** 已有一条内容哈希为 H 的条目，**When** 粘贴内容完全相同的文本，**Then** 界面提示与哪一条重复，**且仍然存下第二条**；两条的批注、采集时间、录入人互不影响。
2. **Given** 上一条的两条重复条目，**When** 任何操作，**Then** **没有任何合并或删除发生**；「合并关联」本卡不提供（见 Out of Scope）。

---

### User Story 4 - 说清楚什么还没有（Priority: P3）

收件箱明确标注「素材解析暂不可用」，并说明现在的内容都是人填的；不假装有任何自动解析发生过。

**Why this priority**: §7.1 给了一列解析状态，但本卡没有解析器。留白会被读成没做完，显示一个假的「已就绪」则是在撒谎（宪法 IX、X）。与 024 的三个 AI 入口、026 的「待补录的反馈」同一口径：**存在、不可用、写明原因**。

**Independent Test**: 该说明恒定可见，且列表里 0 条由系统生成的摘要、标签或正文。

**Acceptance Scenarios**:

1. **Given** 本卡未接入解析模型，**When** 打开收件箱，**Then** 有一条恒定可见的说明写明「素材解析暂不可用」并说明原因，**且没有任何由系统生成的摘要、实体、观点或关联资料**（§4 步骤 4 的「系统做什么」一列在本卡全部不做）。

---

### Edge Cases

- 粘贴一段**很长**的文本（几万字）：明确接受并正常显示（列表截断、详情完整），或明确拒绝并说明上限；**不能默默截断后存下半截**——那会让哈希对应到一段谁也没打算保存的内容。
- URL **格式不合法**：明确拒绝并说明；不存一条指向垃圾的条目。
- 同一个 **URL** 收两次：两条都留下，但**没有重复提示**——URL 首版不生成快照，因而没有哈希可比（见 Out of Scope 的已知限制）。
- 一条条目**同时**被标 `organized` 与 `archived`：状态是单值，不可能两个都亮。
- 批量操作中**部分失败**：成功的保留、失败的逐条说明；不能整批回滚得无声无息，也不能声称全部成功。
- 跨品牌：切到另一个品牌看不到本品牌的条目；把别的品牌的条目 id 拼进接口，得到与「不存在」同形的拒绝。
- 收件箱里有**几百条**：列表可筛选或翻页，不一次渲染全部。

## Requirements *(mandatory)*

### Functional Requirements

**范围与性质**

- **FR-001**: 本卡 MUST NOT 调用任何 AI 执行器，MUST NOT 产生任何由系统生成的摘要、实体、观点、问题或关联资料（§4 步骤 4 的系统列；宪法 IX）。
- **FR-002**: URL 类型的条目 MUST NOT 触发任何对该 URL 的网络抓取，MUST NOT 生成快照。其内容由人填进批注。
- **FR-003**: 本卡 MUST NOT 实现 `knowledge-base` 的知识卡；收件箱条目是素材，不是知识。
- **FR-004**: 本模块 MUST 只依赖登记表允许的 `workspace-core` 与 `diagnostics`，MUST NOT 修改 `scripts/content-boundaries.json` 的 `modules` 依赖表。

**`Source` 的字段（§4 步骤 1 / 4，R-009 / R-010）**

- **FR-005**: `Source` MUST 记录以下字段：

  | 字段 | 说明 | 可变 |
  |---|---|---|
  | `kind` | 受控集，首版两值：`pasted_text` / `url`。§4 的「速记」归入 `pasted_text` | 否 |
  | `title` | 标题 | 是 |
  | `url` | `kind = url` 时必填；`kind = pasted_text` 时 MUST 为空 | 否 |
  | `captured_at` | 采集时间 | 否 |
  | `recorded_by` | 录入人 | 否 |
  | `tags` | 标签，自由文本短标签 | 是 |
  | `annotation` | 个人批注（§4 步骤 1「个人批注」） | 是 |
  | `personal_judgement` | 个人判断（§4 步骤 4「说明为何收藏」） | 是 |
  | `historical_import` | 布尔（§3.3「历史导入」标识） | **否，创建时确定** |
  | `status` | 受控集：`inbox` / `organized` / `archived` | 是 |

- **FR-006**: `annotation` 与 `personal_judgement` MUST 是**两个分开的字段**，MUST NOT 合并成一段文本（§4 步骤 4：「原文、自动摘要和个人判断分开保存」）。「自动摘要」那一列本卡不建（FR-001）。
- **FR-007**: `historical_import` MUST 在创建时确定，此后 MUST NOT 被任何路径修改。
- **FR-008**: `kind` 与 `status` MUST 是受控集。越界输入 MUST 得到一条说明是哪个字段、期望什么的 400，MUST NOT 是 503，MUST NOT 被静默接受。
- **FR-009**: `Source` 的 `kind`、`url`、`captured_at`、`recorded_by`、`historical_import` MUST 永不改变。

**`SourceSnapshot`（§4 步骤 3，R-010）**

- **FR-010**: 本卡 MUST 建立 `SourceSnapshot`，与 `Source` **分开存放**（R-010：「原文件与正文快照分别保存」）。
- **FR-011**: `kind = pasted_text` 的条目 MUST 在创建时生成**恰好一条**快照，内容是粘贴的原文。
- **FR-012**: 快照 MUST 记录内容哈希（sha256）与采集时间。
- **FR-013**: 快照 MUST 只插不改：任何路径 MUST NOT 更新或删除已生成的快照。
- **FR-014**: `kind = url` 的条目在本卡 MUST NOT 生成任何快照。

**整理（§4 步骤 4，R-011）**

- **FR-015**: `status` MUST 是单值。同一时刻 MUST NOT 有两个状态同时成立。
- **FR-016**: 每一次整理 MUST 留下一条只插不改的记录，包含改了什么、谁改的、何时。
- **FR-017**: MUST NOT 提供删除。`archived` MUST 是一个状态，被归档的条目 MUST 仍可查到。
- **FR-018**: 收件箱 MUST 支持**批量打标签**与**批量归档**（R-011）。批量操作 MUST 为每一条**各自**留下一条整理记录。
- **FR-019**: 批量操作部分失败时 MUST 逐条说明哪些失败及原因，MUST NOT 声称整批成功。
- **FR-020**: 收件箱 MUST 支持按标签与状态筛选（R-011）。

**去重（§4，R-011）**

- **FR-021**: 新建 `pasted_text` 条目时，若已存在内容哈希相同的快照，MUST 提示与哪一条重复。
- **FR-022**: 重复 MUST NOT 阻止保存，MUST NOT 触发任何合并或删除。两条条目各自的 `annotation`、`personal_judgement`、`captured_at`、`recorded_by` MUST 互不影响（R-011：「内容相同不删除独立的收藏上下文与批注」）。

**解析（§7.1）**

- **FR-023**: 本卡 MUST NOT 建立解析状态列。`pending → processing → ready / partial / failed` 随解析器那张卡出现（见 Out of Scope）。
- **FR-024**: 收件箱 MUST 有一条恒定可见的说明写明「素材解析暂不可用」及原因，MUST NOT 显示任何伪造的解析结果或状态。

**存储规则（R1–R6）**

- **FR-025**: MUST NOT 使用外键、级联删除或级联更新；关系与依赖清理在应用层显式处理（R1 / R2）。
- **FR-026**: 每个索引 MUST 用 `CREATE INDEX CONCURRENTLY`，**每个并发索引单独一个单语句迁移文件**（R3 / R4）。
- **FR-027**: 建表迁移 MUST NOT 内联 `PRIMARY KEY` / `UNIQUE`（R5）。
- **FR-028**: 每个建索引的 up 迁移 MUST 登记进 `concurrentIndexCleanups`，名字逐字节一致；建表迁移 MUST NOT 登记（R6）。
- **FR-029**: 每张表 MUST 有一个 `workspace_id` 打头的索引。
- **FR-030**: 写事务的第一条语句 MUST 是删除栅栏。

**边界与授权**

- **FR-031**: 所有查询 MUST 按 `workspace_id` 过滤。越权访问 MUST 返回与「不存在」同形的拒绝，MUST NOT 透露对象是否存在。
- **FR-032**: 每个带路径参数的端点 MUST 有一条用例穿过真实中间件，且**路径参数值与上下文值不同**（工作流第 12 步）。
- **FR-033**: 端点响应 MUST 经 schema 解析后再交给 UI，并 MUST 有畸形响应用例（宪法 VI）。

**页面**

- **FR-034**: 页面 MUST 只挂既有组件，MUST NOT 新增控件或新依赖，MUST 四语言（en / zh-Hans / ja / ko）。
- **FR-035**: MUST NOT 写 UI 单测（宪法 II）；界面项进 `manual-ui-todo.md`。非 UI 的判定与整理逻辑 MUST 有 node 测试。
- **FR-036**: 条目很多时列表 MUST 可筛选或翻页，MUST NOT 一次渲染全部。

### Key Entities

- **`Source`**：一次采集行为的登记。不可变部分（`kind`、`url`、`captured_at`、`recorded_by`、`historical_import`）+ 可整理部分（`title`、`tags`、`annotation`、`personal_judgement`、`status`）。
- **`SourceSnapshot`**：原文与它的哈希，只插不改。`pasted_text` 一条；`url` 本卡零条。
- **整理记录**：对一条 `Source` 的一次整理，只插不改。谁、何时、改了什么。

**本卡不定义**：知识卡（`knowledge-base`）、解析状态列（解析器卡）、文件 / 本地目录 / 素材包（W-03）、选题卡引用（Q2 = A，另立一卡）。

## Success Criteria *(mandatory)*

- **SC-001**: 运营者能在不做任何分类决定的前提下把一段文本或一个链接收下来，**一次操作完成**，保存后即可离开页面（§4）。
- **SC-002**: 任意一条条目的 `kind`、`url`、`captured_at`、`recorded_by`、`historical_import` 与其快照内容/哈希，在经过任意次整理后**逐字节未变**（对一条做 5 次整理后逐项核对）。
- **SC-003**: 整理历史完整：做过 N 次整理就有 N 条记录，0 条丢失、0 条覆盖；批量操作 M 条产生 M 条记录。
- **SC-004**: 收件箱里 **0 条**由系统生成的摘要、实体、观点、问题或关联资料；「解析暂不可用」的说明恒定可见。
- **SC-005**: **0 个**删除入口；被 `archived` 的条目 100% 仍可查到。
- **SC-006**: 保存一个 URL 条目后，该 URL **0 次**被本系统访问（可通过出站请求记录核对）；该条目的快照数为 **0**。
- **SC-007**: 粘贴两次完全相同的文本：得到 **2 条**条目、**1 条**重复提示、**0 次**合并或删除，两条的批注互不影响。
- **SC-008**: 越权访问的拒绝与「不存在」**同形**（逐字节相同的响应体与状态码）。

## Out of Scope（本卡明确不做，且写明它们何时出现）

1. **§7.1 的解析状态列**（`pending → processing → ready / partial / failed`）：**随解析器那张卡出现**。本卡不建这一列——没有任何东西会推进它，建了就是一个恒定不动的装饰性枚举，而写成 `ready` 是在声称解析完成而根本没有解析器。快照表的形状为它留出加列的空间，但本卡不加。
2. **URL 的快照与抓取**：首版 0 抓取。§4 的「网页更新生成新快照，历史作品继续引用旧快照」要等抓取能力，且需要网络策略裁决。
3. **「合并关联」重复素材**：§4 说「先提示合并关联」——本卡只做**提示**那一半。合并是人的决定且会牵动引用关系，另立。
4. **「关联已有来源」**（R-011）：本卡不做。
5. **选题卡引用素材条目**（Q2 = A）：要改 022 已落地的契约，另立一张卡。
6. **今日工作台接入**（§11「随时」行）：由 026 的后续修订接入，届时决定是第七区块还是页头快速入口。本卡只保证数据可读。
7. **文件 / 本地目录 / 素材包**（W-03）、**导出资料**：§4 步骤 1 提到上传文件与导出资料，本卡的输入只有粘贴文本与 URL。
8. **§3.3 的「发布后快照」**：那是历史作品的版本链问题，属 `work-editor` / `review-delivery` 的范围，不是素材收件箱的。
9. **标签实体**：标签是自由文本，本卡不做重命名、合并或标签管理页。

### 一条由裁决直接推出的已知限制

**URL 条目没有去重提示。** 去重按 `content_hash` 判定（裁决），而哈希在快照上，`kind = url` 本卡不生成快照——所以两次收同一个链接不会被提示重复。这是「URL 0 抓取」与「按内容哈希去重」两条决定相乘的结果，不是遗漏。要覆盖它，要么对 URL 本身做规范化后哈希（会把 `?utm_source=` 之类的差异算成不同），要么等抓取能力。**本卡不自行选其一。**

## Assumptions

以下是裁决未明处的默认判断。**每条都可被主任务推翻。**

1. **标签是自由文本**，首版不做标签实体（Out of Scope 9）。
2. **粘贴文本设一个明确上限**（建议与 `work-editor` 的 `MaxBodyRunes = 200000` 同量级），超限**明确拒绝而非截断**——截断会让哈希对应到一段谁也没打算保存的内容。
3. **`historical_import` 的默认值是 `false`**；只有明确标记为历史导入的采集才是 `true`。本卡不提供批量导入入口，所以它今天只能由建条目时显式传入。
4. **重复提示只在新建时给一次**，不做常驻的「重复组」视图。
5. **web-only**：桌面端不接线、侧边栏入口由主任务另行决定，与 `/topics`、`/accounts`、`/diagnostics`、`/today` 一致。
6. **存储与接口 PR / 页面 PR 分界**，与 023 / 024 / 025 一致。页面 PR 的范围按裁决：批量标签、归档、筛选、去重提示。
7. **整理记录记录的是「哪些字段变了」**，不是整条条目的快照——条目的不可变部分本来就不会变，把它们抄进每条记录只会让历史变胖。

`plan.md` / `tasks.md` / `contracts/` 随实施 PR 产出。
