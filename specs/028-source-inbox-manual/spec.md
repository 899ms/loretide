# Feature Specification: source-inbox 首切片——粘贴文本与 URL 的素材收件箱

**Feature Branch**: `claude/spec-028-source-inbox-manual`

**Created**: 2026-09-20

**Status**: Draft（含 3 个待裁决项，其中 Q1 需要主控提供 SOP 原文）

**Input**: Issue #171 — SOP §4「输入到知识：把素材收成可复用资产」的 web-only 半边。以**粘贴文本与 URL** 为输入，把素材收进收件箱、标注来源与「历史导入」标识、整理为可引用条目。素材解析状态按 §7.1 行 `pending → processing → ready / partial / failed`；**本卡无解析模型**，只做人工整理与「解析暂不可用」占位。

> **本规格没有 SOP §4 与 §3.3 的原文。** 派单说明原文由主控在 clarify 时提供。下文凡涉及这两节的地方都**按 Issue 的转述**编写，并在 Q1 里逐段列出需要哪些原文来核对。**在拿到原文前，涉及 §4 / §3.3 的条款都可能需要改写**——022 与 026 都出现过「Issue 转述与原文不一致」的情况（026 的第五项区块即是一例），所以这一条不是形式主义。

## Current State（以代码为准，2026-09-20 / `app-main` @ `fae5dce`）

### source-inbox 已登记、目录全空

`scripts/content-boundaries.json` 登记了它，依赖是 `["workspace-core", "diagnostics"]`。三个 root 下**都没有 `source-inbox/` 目录**：

| root | 是否存在 |
|---|---|
| `server/internal/content/source-inbox` | 否 |
| `packages/core/content/source-inbox` | 否 |
| `packages/views/content/source-inbox` | 否 |

已落地的六个模块：`diagnostics`、`workspace-core`、`ip-profile`、`topic-planning`、`work-editor`、`review-delivery`。

### 缺口 A — topic-planning **不依赖** source-inbox，而且没有任何结构化引用位

Issue 说「选题卡『与已有作品关系』『证据缺口』可引用条目 id（字符串，不 import）」。两件事要分开看：

**1. 不能 import，这点 Issue 说对了。** 登记表里 `topic-planning` 的依赖是 `["workspace-core", "ip-profile", "knowledge-base", "diagnostics"]`——**不含 `source-inbox`**。（依赖链是 `topic-planning → knowledge-base → source-inbox`，是二跳，不是直接边。）

**2. 但今天根本没有地方放这个 id。** `ExistingContentRelation` 与 `EvidenceGapsAndInvestment` 在 `server/internal/content/topic-planning/contract.go` 里都是 **`string`**，即自由文本：

```go
ExistingContentRelation   string   `json:"existing_content_relation"`
EvidenceGapsAndInvestment string   `json:"evidence_gaps_and_investment"`
```

把条目 id 塞进一段自由文本里**不是引用**：它不可校验、不可反查、改名后不会失效也不会更新，而且没有任何东西能阻止它指向一个不存在的条目。要做成真正的引用，需要在选题卡上加一个结构化字段（一个 id 数组），那是**改 022 已落地的契约 + 一次迁移**，超出本卡。→ **Q2**

### 缺口 B — 今日工作台没有「随时」那一行的位置

Issue 说本模块是今日工作台 §11「随时」行「快速入口与待整理收件箱」的数据源。但 `apps/web/app/[workspaceSlug]/(dashboard)/today/page.tsx` 今天是**六个区块**，顺序被 026 的 FR-005 钉死：

1 值得写的选题 → 2 正在推进的作品 → 3 需要处理的审核 → 4 到期交接与待登记 → 5 待补录的反馈（暂不可用）→ 6 账号配置缺项（附加）

026 FR-005 要求「SOP §2 原文的五个区块，顺序与原文一致」，FR-005a 把「账号配置缺项」定为**排在五项之后的第六个附加区块**。**「待整理收件箱」既不在 §2 的五项里，也不是第六项**，所以它要么成为第七个附加区块，要么本卡不接入。→ Assumptions 4（我给了推荐值，不占 clarify 名额）

### 缺口 C — 「历史导入」在代码与既有规格里都不存在

`grep` 全仓（`specs/`、`packages/`、`server/`）**没有任何**「历史导入」/ `historical import` / `historicalImport` 的痕迹，也没有任何既有规格引用过 §3.3。所以这个标识的**含义、取值与用途完全来自 §3.3 原文**，而本规格没有那份原文。→ Q1

### 解析状态：§7.1 的行已给出，但本卡没有解析器

Issue 直接给了原文口径：`pending → processing → ready / partial / failed`。本卡**无解析模型**。于是一个真问题立刻出现：**一段粘贴文本，它的解析状态应该是什么？**

- 说 `ready`，就是在声称「已解析完成」，而根本没有解析器跑过；
- 说 `pending`，则每一条素材永远停在「待解析」，状态列变成一个恒定不动的装饰；
- 而 `processing` / `partial` / `failed` 在没有解析器的情况下**永远不可能出现**。

这不是措辞问题：状态列要么说真话，要么不如不做。→ **Q3**

### 可复用的既有模式（不必重新发明）

- **只插不改 + 状态列**：`review-delivery` 的 `ReviewRequest` / `DeliveryTask` 是「主行可改状态 + 附一张只插不改的 `content_review_transition` 流水表」；`work-editor` 的版本表与 `topic-planning` 的简报表是纯 append-only。两种形状本卡都用得上（条目主行有状态要变，动作要留痕）。
- **只插不改的守卫用例**：扫模块源码里的 `UPDATE <table>` / `DELETE FROM <table>`，**并同时断言存在 `INSERT`**（少了后半条，空模块也是绿的）。
- **受控集**：Go 枚举权威 → 400 诊断式错误；DB `CHECK` 作兜底（`review-delivery/contract.go` 的 `oneOf` + `ErrInvalid = "invalid review delivery input"`）。
- **迁移**：下一个可用号是 **516**（现有最大 515）。每张表三个文件：建表 + `id_unique_idx` + `workspace_idx`，各自单语句 `CREATE INDEX CONCURRENTLY`；**R5** 建表时不内联 `PRIMARY KEY` / `UNIQUE`；**R6** 每个建索引的 up 迁移都要登记进 `server/cmd/migrate/main.go` 的 `concurrentIndexCleanups`（名字逐字节一致，建表迁移不登记）。
- **栅栏**：写事务的第一条语句取 `LockForContentDiagnosticWrite`。
- **第 12 步**：每个带路径参数的端点，要有一条用例穿过真实中间件且**路径参数值与上下文值不同**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把看到的东西先收下来（Priority: P1）

运营者看到一段值得留着的文字（别人的帖子、自己的笔记、一段访谈摘录），或者一个想回头再看的链接，**在一个地方把它收下来**，填上它是哪儿来的，然后继续手头的事。不需要当场决定它属于哪个选题、不需要给它分类、也不需要等任何东西处理完。

**Why this priority**: 这是 SOP §4 的入口。收不下来，后面的整理与引用都无从谈起。只做这一个故事就已经有用：一个可信的暂存处。

**Independent Test**: 粘贴一段文本、存下、刷新页面，它还在，并且能看出它是什么时候、由谁、从哪儿收的。

**Acceptance Scenarios**:

1. **Given** 收件箱是空的，**When** 粘贴一段文本、填标题与来源说明并保存，**Then** 列表里多一条，显示标题、类型「粘贴文本」、来源说明、采集时间与录入人。
2. **Given** 一个链接，**When** 选「URL」类型、粘贴链接并填写摘要，**Then** 存下且**不抓取该链接**；界面明确写出「不抓取，摘要由人填写」。
3. **Given** 正文为空，**When** 试图保存，**Then** 保存不可用并说明原因；**不产生**一条空条目。
4. **Given** 已存在的一条条目，**When** 任何操作，**Then** 它的原文/URL、采集时间与录入人**永不改变**。

---

### User Story 2 - 整理成以后用得上的样子（Priority: P2）

运营者回到收件箱，把收下来的东西整理一遍：改标题、补来源说明、打标签、标记「已整理」或「不用了」。每一次整理**留下痕迹**，而不是悄悄覆盖。

**Why this priority**: 「收成可复用资产」的「可复用」在这一步发生。没有它，收件箱只是一个越堆越高的粘贴板。但 US1 单独也能用。

**Independent Test**: 对一条条目做三次整理，历史里有三条记录，且原文始终未变。

**Acceptance Scenarios**:

1. **Given** 一条新收的条目，**When** 改标题并打两个标签，**Then** 列表显示新标题与标签；**原文不变**。
2. **Given** 上一条，**When** 查看它的整理历史，**Then** 能看到每次改了什么、谁改的、什么时候。
3. **Given** 一条不再需要的条目，**When** 标记为「不用了」，**Then** 它从默认列表里移出但**仍可查到**；**没有任何删除操作**。
4. **Given** 一条标签，**When** 按它筛选，**Then** 只列出带该标签的条目。

---

### User Story 3 - 说清楚什么还没有（Priority: P3）

收件箱明确标注「素材解析暂不可用」，并说明现在的内容是人填的；不假装有任何自动解析发生过。

**Why this priority**: §7.1 给了一列解析状态，但本卡没有解析器。留白会被读成没做完，显示一个假的「已就绪」则是在撒谎（宪法 IX、X）。

**Independent Test**: 该说明恒定可见，且列表里 0 条由系统生成的摘要/标签。

**Acceptance Scenarios**:

1. **Given** 本卡未接入解析模型，**When** 打开收件箱，**Then** 有一条恒定可见的说明写明「素材解析暂不可用」并说明原因，**且没有任何由系统生成的摘要、标签或正文**。

---

### Edge Cases

- 粘贴一段**很长**的文本（几万字）：要么明确接受并正常显示（列表里截断、详情里完整），要么明确拒绝并说明上限；不能默默截断后存下半截。
- 同一段文本/同一个 URL **收两次**：两条都留下（它们是两次不同的采集行为），但界面要能看出重复，不能让人以为存重了是坏了。
- URL **格式不合法**：明确拒绝并说明；不存一条指向垃圾的条目。
- 一条条目**同时**被标「已整理」与「不用了」：状态是单值，不能出现两个都亮。
- 跨品牌：切到另一个品牌看不到本品牌的条目；把别的品牌的条目 id 拼进接口，得到与「不存在」同形的拒绝。
- 收件箱里有**几百条**：列表要能翻页或筛选，不能一次把全部塞进一个页面。

## Requirements *(mandatory)*

### Functional Requirements

**范围与性质**

- **FR-001**: 本卡 MUST NOT 调用任何 AI 执行器，MUST NOT 产生任何由系统生成的摘要、标签或正文（宪法 IX）。
- **FR-002**: URL 类型的条目 MUST NOT 触发任何对该 URL 的网络抓取。摘要 MUST 由人填写。
- **FR-003**: 本卡 MUST NOT 实现 `knowledge-base` 的知识卡；收件箱条目是素材，不是知识。
- **FR-004**: 本模块 MUST 只依赖登记表允许的 `workspace-core` 与 `diagnostics`，MUST NOT 修改 `scripts/content-boundaries.json` 的 `modules` 依赖表。

**条目本身**

- **FR-005**: 条目 MUST 记录：类型（粘贴文本 / URL）、原文或 URL、标题、来源说明、采集时间、录入人、「历史导入」标识、标签。
- **FR-006**: 条目的**原文或 URL、采集时间、录入人** MUST 永不改变。任何「修改」都 MUST 表现为新增一条整理记录，而非覆盖。
- **FR-007**: 类型 MUST 是受控集，首版只有「粘贴文本」与「URL」两个值。越界输入 MUST 得到一条说明是哪个字段、期望什么的 400，MUST NOT 是 503 或静默接受。
- **FR-008**: 正文为空（粘贴文本）或 URL 格式不合法（URL）时 MUST 拒绝保存并说明原因。
- **FR-009**: 「历史导入」标识的语义与取值 MUST 按 SOP §3.3 原文确定 — 见 [NEEDS CLARIFICATION: Q1]。在拿到原文前，本规格按「一个布尔标识：这条素材是历史存量补录进来的，不是当下采集的」编写。

**整理与状态**

- **FR-010**: 条目 MUST 有一个单值状态。同一时刻 MUST NOT 有两个状态同时成立。
- **FR-011**: 每一次整理 MUST 留下一条只插不改的记录，包含改了什么、谁改的、何时。
- **FR-012**: MUST NOT 提供删除。「不用了」MUST 是一个状态，被标记的条目 MUST 仍可查到。
- **FR-013**: 解析状态的口径见 [NEEDS CLARIFICATION: Q3]。
- **FR-014**: 收件箱 MUST 有一条恒定可见的说明写明「素材解析暂不可用」及原因，MUST NOT 显示任何伪造的解析结果。

**与选题卡的关系**

- **FR-015**: 引用如何落地见 [NEEDS CLARIFICATION: Q2]。无论裁决如何，本模块 MUST NOT 被 `topic-planning` import（登记表不允许），MUST NOT 为此修改依赖表。

**存储规则（R1–R6）**

- **FR-016**: MUST NOT 使用外键、级联删除或级联更新；关系与依赖清理在应用层显式处理（R1 / R2）。
- **FR-017**: 每个索引 MUST 用 `CREATE INDEX CONCURRENTLY`，**每个并发索引单独一个单语句迁移文件**（R3 / R4）。
- **FR-018**: 建表迁移 MUST NOT 内联 `PRIMARY KEY` / `UNIQUE`（R5）。
- **FR-019**: 每个建索引的 up 迁移 MUST 登记进 `concurrentIndexCleanups`，名字逐字节一致；建表迁移 MUST NOT 登记（R6）。
- **FR-020**: 每张表 MUST 有一个 `workspace_id` 打头的索引。
- **FR-021**: 写事务的第一条语句 MUST 是删除栅栏。

**边界与授权**

- **FR-022**: 所有查询 MUST 按 `workspace_id` 过滤。越权访问 MUST 返回与「不存在」同形的拒绝，MUST NOT 透露对象是否存在。
- **FR-023**: 每个带路径参数的端点 MUST 有一条用例穿过真实中间件，且**路径参数值与上下文值不同**（工作流第 12 步）。
- **FR-024**: 端点响应 MUST 经 schema 解析后再交给 UI，并 MUST 有畸形响应用例（宪法 VI）。

**页面**

- **FR-025**: 页面 MUST 只挂既有组件，MUST NOT 新增控件或新依赖，MUST 四语言（en / zh-Hans / ja / ko）。
- **FR-026**: MUST NOT 写 UI 单测（宪法 II）；界面项进 `manual-ui-todo.md`。非 UI 的判定与整理逻辑 MUST 有 node 测试。
- **FR-027**: 条目很多时列表 MUST 可筛选或翻页，MUST NOT 一次渲染全部。

### Key Entities

- **收件箱条目**：一次采集行为的结果。不可变部分（原文或 URL、采集时间、录入人、类型、历史导入标识）+ 可整理部分（标题、来源说明、标签、状态）。
- **整理记录**：对一条条目的一次整理，只插不改。谁、何时、改了什么。
- **解析状态**：§7.1 的那一列。本卡没有产生它的东西 → Q3。
- **标签**：自由文本短标签，用于筛选。首版不做标签的独立生命周期（不重命名、不合并）。

**本卡不定义**：知识卡（`knowledge-base`）、素材包 / 文件 / 本地目录（W-03，已明确排除）。

## Success Criteria *(mandatory)*

- **SC-001**: 运营者能在不做任何分类决定的前提下把一段文本或一个链接收下来，**一次操作完成**。
- **SC-002**: 任意一条条目的原文、采集时间与录入人，在经过任意次整理后**逐字节未变**（可对一条做 5 次整理后逐项核对）。
- **SC-003**: 整理历史完整：做过 N 次整理就有 N 条记录，0 条丢失、0 条覆盖。
- **SC-004**: 收件箱里 **0 条**由系统生成的摘要、标签或正文；「解析暂不可用」的说明恒定可见。
- **SC-005**: **0 个**删除入口；被标「不用了」的条目 100% 仍可查到。
- **SC-006**: 保存一个 URL 条目后，该 URL **0 次**被本系统访问（可通过出站请求记录核对）。
- **SC-007**: 越权访问的拒绝与「不存在」**同形**（逐字节相同的响应体与状态码）。

## Assumptions

以下是本规格在原文缺失或派单未明处所做的默认判断。**每条都可被主任务推翻。**

1. **「历史导入」首版按布尔处理**（FR-009）。拿到 §3.3 原文后若它其实是一个来源分类（如「历史存量 / 当下采集 / 迁移自旧系统」），就要改成受控集。**在原文到手前不要把它实现死。**
2. **标签是自由文本**，首版不做标签实体（不重命名、不合并、不做标签管理页）。
3. **不做去重**：同一段文本收两次是两条。它们是两次不同的采集行为，合并会丢掉其中一次的时间与录入人。界面提示重复即可（Edge Case），但不阻止。
4. **今日工作台的接入：本卡不做，留给一张单独的卡**（缺口 B）。理由：026 的 FR-005 / FR-005a 把区块清单与顺序钉死了，「待整理收件箱」既不在 §2 五项内也不是第六项；在本卡顺手加第七个区块等于单方面改掉刚裁定的页面结构。**推荐做法**是本卡只保证数据可读，接入作为 026 的后续修订。若主控要求本卡一并接入，请明确它排第几、以及是否要改 026 的 FR-005a。
5. **粘贴文本设一个明确上限**（建议与 `work-editor` 的 `MaxBodyRunes = 200000` 同量级），超限明确拒绝而非截断。
6. **状态集首版三值**：待整理 / 已整理 / 不用了。这是整理流程的状态，**与 §7.1 的解析状态是两列不同的东西**，不要合并（Q3 若裁定不做解析列，这一列仍然存在）。
7. **web-only**：桌面端不接线、侧边栏入口由主任务另行决定，与 `/topics`、`/accounts`、`/diagnostics`、`/today` 一致。
8. **存储与接口 PR / 页面 PR 分界**，与 023 / 024 / 025 一致。
