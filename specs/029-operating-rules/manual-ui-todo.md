# 手动 UI 清单（029 运营规则设置页面）

两处入口：

1. **`/{workspaceSlug}/settings` → 工作区「通用」分节** —— 四个区块（每周节奏、渠道写法、谁来审、什么时候去看数）加一个保存区，排在**默认时区与自动预检开关之后、危险区之前**。
2. **`/{workspaceSlug}/accounts` → 选中一个账号** —— 新增「主页链接」分节，排在「账号资料」与「人设提示词」之间。

**为什么挂在既有设置分节里，不是一条新路由**：SOP §3.2 五项里有两项（默认时区 LT-009、审核规则的一半 019）早就在这个分节里了。把另外四项挪去别处，等于把同一段 SOP 拆成两页。

**跨模块怎么接的**：区块本体在 `packages/views/content/workspace-core/index.tsx`（`workspace-core` 已在册，**`modules` 依赖表一个字未动**）。上游共享组件 `workspace-tab.tsx` **只加了一行引用**（外加一行 import），因此它按边界检查器的规则进了 `adapters` —— 这一点在 PR 正文单列。

存储与接口由 PR 1（#195）交付，本清单只覆盖页面。全部条目**状态：未执行**——只能由主任务在浏览器逐条验收；本会话不做 computer use，不写 UI 单测（宪法 II）。

## 复用的既有组件（未新增控件、未改样式）

`SettingsSection` / `SettingsCard` / `SettingsRow` / `SettingsSaveState`（`@multica/views/settings/layout`）、`Button` / `Input` / `Textarea`（`@multica/ui`）。没有新建任何控件，没有设任何颜色，**没有下拉框**——八个渠道各自一行，比一个下拉加一个值更直接。

## 本清单最要紧的两条

**U-05 与 U-06 是这张卡的核心。** 一个没人填过的目标条数和一个填了 0 的目标条数，如果页面打印出来一样，那后面任何「这周做够了没有」的判断都建立在假数据上，而且不一致时没有任何东西会报警。**留空显示「未设置」，0 显示「这周不发」，两者必须一眼看得出不同。**

## 已知边界（都是本卡范围之外，不是坏了）

- **不提醒、不调度、不自动发布。** SOP §3.2 原文说排期「用于提醒运营者手动处理」，而本阶段连提醒的载体（通知系统）都没有，所以本卡连提醒也不做，只做「写下来」。
- **观察时点还没有消费方。** 接进 027 的「待补录」判定是 **PR 3**（Issue #197）。在那之前，工作台第五项的口径仍是「发了且一条数都没录」，不看时间。
- **团队复核没有任何存储或控件**，`review_rule` 受控集只有一个值。
- **渠道写法是自由文本**，不是结构化字段；要结构化就得换存储形态（规格 Q1 的选项 B）。
- **没有「这周做够了没有」的计算与展示**——那属于今日工作台（026），本卡只提供目标值。
- **桌面端未接线**（与 `/topics`、`/accounts` 一致）。
