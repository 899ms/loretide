> **§3.2 设定运营规则**
>
> 设定每周内容节奏、渠道模板、审核规则、默认时区、反馈观察时点。排期用于提醒运营者手动处理，不触发平台发布。默认时区由工作区显式设置。个人默认自己审核。后续团队模式可要求不同成员复核。渠道设置保存账号名称或主页链接以便标识，系统不需要平台登录凭据，模型上下文仅接收必要的渠道说明。

### 1. 既有的「品牌级设置」是三个 settings JSONB 键，不是表

```
grep -rhon '"loretide\.[a-z_.]*"' --include=*.go --include=*.ts --include=*.tsx . | grep -v node_modules | sort -u
```

全仓**恰好三个**：

| 键 | 挂在哪 | 默认值 | 定义处 |
|---|---|---|---|
| `loretide.timezone` | 工作区 `settings` | `Asia/Shanghai` | `server/internal/handler/workspace.go:214,218`；`packages/core/workspace/timezone.ts` |
| `loretide.auto_precheck` | 工作区 `settings` | `true` | `workspace.go:280,285`；`packages/core/workspace/auto-precheck.ts` |
| `loretide.scope` | **账号** `settings` | `all` | `server/internal/content/ip-profile/scope.go:42`；`packages/core/content/ip-profile/scope.ts:19` |

三者共用同一套形状，本卡照抄不发明：

- **写时校验**：`validateTimezoneSetting` / `validateAutoPrecheckSetting` 拒绝类型不对的值；**不含该键的更新是合法的**——改品牌名不是一次关于时区的声明。
- **读时填默认且不回写**：`timezoneFilled` / `autoPrecheckFilled` 只在出站方向补默认值。读一个工作区不能写它。
- **「存了」与「存的是什么」是两个问题**：`hasStoredAutoPrecheck` 与 `isAutoPrecheckEnabled` 是两个函数。布尔的零值是 `false`，用真假性回答第一个问题会把「关掉了」读成「没选过」，默认值再把它打开。**本卡每个有零值的字段都会撞上同一件事**（目标条数 0、观察天数 0）。
- **settings 是整体替换**：`server/internal/handler/content_account.go:290` 的 `params.Settings = settings`、`packages/core/workspace/auto-precheck.ts` 里 `withAutoPrecheck` 的注释，都写着这件事。只发一个键会抹掉其余——所以每个新键都要有自己的 `with*` 合并函数。

## 三条待裁决（推荐值暂定，不阻塞）

### Q1：存储形态与模块归属

**问题**：本卡的四项设置存在哪、由谁拥有？

| 选项 | 形态 | 代价 |
|---|---|---|
| **A（推荐）** | 全部作为工作区 `settings` 的 `loretide.*` 键，代码落在 **`workspace-core`**，登记表一个字不改 | 零迁移、零新表、零删除链改动。代价是一个 JSONB 键里塞进了结构化数据（渠道模板是一张表的形状），读写都要在 Go 与 TS 两侧各写一遍校验 |
| B | 新建一张 `content_operating_rule` 表，新增登记表模块 `operating-rules` | 结构清晰、可加索引。代价是改登记表 + 迁移 + 删除链 + 接入合同（落地模块数 8 → 9） |
| C | 混合：节奏 / 审核规则 / 观察时点走 settings 键（它们是少量标量），渠道模板走新表（它是每渠道一行） | 两种形态并存，读端要知道去哪儿找 |

**暂定 A**，理由是 §3.2 这五项里已经落地的两项就是这么存的，而且本卡的量级（一个品牌四个渠道、十一个以内的标量）离需要一张表还很远。**但我不确定**：渠道模板里若要存每渠道的字段约束说明，一个键里会长出一棵不小的树，那时 B 更诚实。

### Q2：渠道模板按哪个渠道集，主页链接存哪

**问题（两半）**：

1. 渠道模板覆盖 **ip-profile 的八个平台**，还是 **review-delivery 的四个渠道**？
2. §3.2 的「主页链接」存在哪？

| 选项 | 渠道集 | 主页链接 |
|---|---|---|
| **A（推荐）** | 八个（跟 `ip-profile`）——品牌能建知乎账号，就该能给知乎配模板 | 存进**账号** `settings` 的新键 `loretide.homepage`，与 `loretide.scope` 同一套，不改 `content_account` 表 |
| B | 四个（跟 `review-delivery`）——只给能交付的渠道配模板 | 同上 |
| C | 八个 | 加一列到 `content_account`，改 `ip-profile` 的表（一个迁移） |

**暂定 A**。理由：主页链接是**账号的标识**（§3.2 原文「以便标识」），账号已有 `settings` 且已有一个 `loretide.*` 键，加第二个键是零迁移；而渠道模板按八个不会让四个那边多出任何东西——交付时只会用到四个里的模板。

**代价要说清**：按八个之后，「渠道模板存在但该渠道不能交付」会是一个常态，界面要写明这件事，不能让人以为配了模板就能发。

### Q3：观察时点落地后，027 的待补录判定改不改

**问题**：本卡交付观察时点之后，`feedback-learning` 的 `NeedsRegistration` 要不要加上时间条件？

| 选项 | 做什么 | 代价 |
|---|---|---|
| **A（推荐）** | 本卡**只交付设置与一个派生函数**（「这条发布记录的观察时点到了没有」），027 的 `NeedsRegistration` 与那条守卫**一个字不改** | 工作台第五项仍然是「发了且没录」，不看时间。观察时点暂时只是一个存着的值，没有消费方 |
| B | 本卡同时改 027：`NeedsRegistration` 加上「已过观察时点」，同时改 `TestThePendingDerivationHasNoTimeLogic` 让它允许时间比较 | 跨卡改动（与 027 的 Q6 同形）。代价是把一条**刻意写的守卫**拆掉，而守卫的注释正是为了防这件事 |
| C | 分两步：本卡交付设置 + 派生函数并在规格里写明「027 的消费由下一张卡做」，同时**不动**守卫 | 与 A 相同，区别只在有没有把「下一张卡」写进规格 |

**暂定 A**，但**这一条我最想要你的判断**。B 的诱惑是「一步到位」，可它要拆掉的那条守卫不是随手加的——它的注释写着「a hard-coded number of days would be a rule the SOP never stated」。观察时点落地之后那句话确实过期了，但**拆守卫和让守卫认识新的合法写法是两件事**，后者要花的心思多得多。如果你选 B，我会把守卫改成「时间比较必须读自设置，不得是字面量」而不是直接允许时间比较。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把「一周发几条」写下来 (Priority: P1)

小张这个品牌定的是小红书一周三条、公众号一周一条。他打开运营规则，给这两个渠道各填一个数。工作台以后就能对着这个数说「这周还差两条」——但**今天它只是被写下来了**，没有任何东西会因为没达标而提醒他，也不会有任何东西因此自动开始写。

**Why this priority**：§3.2 五项里的第一项。它是后面所有「节奏」类判断的唯一来源；没有它，「这周做够了没有」这个问题在产品里问不出来。

**Independent Test**：给一个渠道设一个目标条数，读回来不变；另一个渠道没设，读回来是「未设」而不是 0。渠道模板、审核规则、观察时点都不必存在。

**Acceptance Scenarios**：

1. **Given** 一个品牌，**When** 给小红书设「每周 3 条」，**Then** 存下来，读回来是 3。
2. **Given** 同一品牌，**When** 读一个没设过的渠道，**Then** 读回来是**「未设」**，不是 0——「这个渠道不发」和「还没想好」是两件事，而 0 会被后面的计算当成前者。
3. **Given** 某渠道目标设为 **0**，**When** 读回来，**Then** 是 0 且**可与「未设」区分**（这是 019 的 `hasStoredAutoPrecheck` 撞过的同一件事，本卡照抄）。
4. **Given** 已设好节奏，**When** 更新品牌名，**Then** 节奏**逐字节不变**——settings 是整体替换，改名不能抹掉它。
5. **Given** 节奏已设，**When** 检索代码，**Then** 不存在任何调度器、定时任务或提醒发送路径（§3.2：「排期用于提醒运营者手动处理，不触发平台发布」）。

### User Story 2 - 给每个渠道写一份「这里该怎么发」 (Priority: P2)

小红书的标题有字数限制，公众号要有摘要，视频号得先有封面。小张把这些写成每渠道一段说明，再填上账号名和主页链接，好让别人一眼看出这是哪个号。**他从头到尾没被要求输入任何平台密码**——界面上也写着系统不需要。

**Why this priority**：§3.2 的第二项，也是四条约束里占了三条的那一项（存名称或链接、不要凭据、模型上下文只收必要说明）。

**Independent Test**：给一个渠道写一段说明 + 一个主页链接，读回来两者都在；检索代码确认没有任何凭据字段。

**Acceptance Scenarios**：

1. **Given** 一个渠道，**When** 填写字段约束说明与主页链接，**Then** 两者都存下来，读回来不变。
2. **Given** 任意渠道模板，**When** 检索存储与接口，**Then** **不存在**任何密码、token、cookie、app_secret 之类的字段或参数（§3.2：「系统不需要平台登录凭据」）。界面上**写明**这一点。
3. **Given** 主页链接填的是一个 URL，**When** 提交，**Then** 只存字符串，**系统不去访问它**——检索用例确认没有任何外发请求，也不把它渲染成会自动取回的元素（照 028 的做法）。
4. **Given** 渠道模板要进模型上下文，**When** 组装上下文，**Then** 只带**渠道说明**，**不带**账号名、主页链接、目标条数或任何其它设置（§3.2：「模型上下文仅接收必要的渠道说明」）。
5. **Given** 一个模板配给了不能交付的渠道（按 Q2=A，八个平台里有四个今天不能交付），**When** 打开它，**Then** 界面**写明这个渠道今天不能交付**，不让人误以为配了模板就能发。

### User Story 3 - 说清楚谁来审 (Priority: P2)

小张一个人做这个品牌，所以审核规则那一栏写着「自己审核」，而且它本来就是这样——他没选过。旁边写着「团队复核以后再说」，是一行说明，不是一个灰着的下拉框假装将来会亮。

**Why this priority**：§3.2 原文「个人默认自己审核。后续团队模式可要求不同成员复核。」前半句是本卡要落地的默认值，后半句明写是「后续」。

**Independent Test**：读一个从没设过的品牌，审核规则是「自己审核」；把它显式设成「自己审核」，`hasStored` 能区分这两种情况。

**Acceptance Scenarios**：

1. **Given** 一个从没设过审核规则的品牌，**When** 读，**Then** 是**「自己审核」**，不是空值。
2. **Given** 同一品牌，**When** 问「存过没有」，**Then** 是否——与上一条是**两个不同的问题**，读得到值不等于选过。
3. **Given** 审核规则一栏，**When** 打开页面，**Then** 「团队复核」**写明是后续能力**，**不提供**任何形式的成员选择控件——一个灰着的控件是在承诺，而本卡不做它。
4. **Given** 已有的自动预检开关（019），**When** 打开运营规则，**Then** 它**在同一处可见**，不另起一个位置——两个开关都是「审核规则」，分在两页会让人以为是两件事。

### User Story 4 - 定下「发完多久去看数」 (Priority: P3)

小张定的是「发布后 14 天」去抄一次数。他把这个数填进去。**今天填完之后，工作台的「待补录」还是老样子**——它列的仍然是「发了且一条数都没录」的那些，不看时间。界面上写着这一点，不是让人以为填完就会有提醒。

**Why this priority**：§3.2 的第五项，也是 027 在规格里**点名留给本卡**的那一件事。优先级低于前三项是因为它今天没有消费方（见 Q3）。

**Independent Test**：设一个观察天数，读回来不变；派生函数对「发布时间 + N 天」是否已过给出答案。工作台不必改。

**Acceptance Scenarios**：

1. **Given** 一个品牌，**When** 设「发布后 14 天」，**Then** 存下来，读回来是 14。
2. **Given** 一条 `published_at` 是 20 天前的发布记录、观察时点 14 天，**When** 问派生函数，**Then** 答「已过」。
3. **Given** 一条 `published_at` 为**空**的发布记录（025 允许），**When** 问，**Then** 答**「无法判断」**，不是「已过」也不是「未到」——没有发布时间就没有起算点，猜一个方向都是在造事实。
4. **Given** 观察时点**没设过**，**When** 问，**Then** 答「无法判断」——本卡不发明默认天数（027 已经拒绝过一次同样的诱惑）。
5. **Given** 观察时点已设，**When** 打开今日工作台，**Then** 第五项的口径**与本卡之前一致**（按 Q3=A），且界面写明观察时点尚未接入该判定。

---

### Edge Cases

- **目标条数是 0**：合法，意思是「这个渠道这周不发」。它与「没设过」必须可区分——布尔的 `false` 和数字的 `0` 在这件事上是同一个坑，019 已经踩过。
- **观察天数是 0**：意思是「发完当天就去看」。同样合法，同样要与「没设过」区分。
- **观察天数是负数**：拒绝并点名字段。「发布前 3 天去看数」没有含义。
- **渠道模板配给了一个账号都没有的渠道**：合法。先定规则再建号是正常顺序，界面不拦。
- **同一渠道下有多个账号**（品牌在小红书有两个号）：模板是**渠道级**还是**账号级**？本规格按**渠道级**写（§3.2 说的是「渠道模板」），账号名与主页链接则天然是账号级的——这两件事在同一段原文里，但落点不同，界面要分开呈现。
- **主页链接不是一个合法 URL**：拒绝并点名字段，只放行 `http` / `https`（照 028 的 `isWebURL`）。
- **设置被并发修改**：settings 整体替换，后写的赢。本卡不引入版本号或乐观锁——量级不到，而且这是一个人在一个表单里填的东西。
- **品牌删除**：若 Q1=A（settings 键），设置随工作区一起消失，删除链不用改；若 Q1=B，新表要进删除清单与删除链。

## Assumptions

1. **本卡只存规则，不执行规则。** §3.2 原文「排期用于提醒运营者手动处理，不触发平台发布」——「提醒」本身今天也没有载体（没有通知系统），所以本卡连提醒都不做，只做「写下来」。
2. **观察时点按渠道设，可缺省到全局。** §3.2 没说粒度。按渠道是因为小红书和公众号的数据爬升速度不是一回事；可缺省到全局是因为多数品牌只想设一个数。**这是我补的**（见下）。
3. **审核规则首版只有一个值。** 一个「受控集」只有一项看起来很怪，但原文写的就是「个人默认自己审核，后续团队模式可要求不同成员复核」——把「后续」写成今天的一个选项，就是在承诺一件没做的事。
4. **不引入版本号或乐观锁。** settings 整体替换、后写赢。这是一个人在一个表单里填的东西，量级不到。
5. **主页链接只存不访问**，与 028 的素材链接同一条底线。
6. **本卡不碰时区。** LT-009 已经落地且被其它卡消费，本卡只是把它**显示在同一处**，不改键、不改默认、不改语义。
7. **不新增路由。** 设置挂在既有设置页（Q1 定具体位置）。

## Out of Scope

- **提醒与调度**：没有通知系统，本卡不发明一个。
- **团队复核**：§3.2 明写「后续」。
- **「这周做够了没有」的计算与展示**：属于工作台（026），本卡只提供目标值。
- **平台登录与自动发布**：§3.2 明写系统不需要凭据；自动发布违反 025 与 027 已经反复写死的底线。

## 我补的地方（原文没有，改起来都很便宜）

原文只给了五个名词，没给任何一个的形态。下面三条是我定的，都单独标出，因为它们是最可能被推翻的：

1. **每周节奏是「按渠道的目标条数」。** 原文只说「每周内容节奏」。也可以是「每周总条数」或「每个账号的条数」。选按渠道，是因为交付与发布记录都是按渠道组织的（025），按渠道能和它们对上。**若要按账号，那是把键的层级从工作区挪到账号，一天的活。**
2. **观察时点按渠道，可缺省到全局。** 见 Assumptions 2。**若要只有一个全局值，去掉按渠道那一层即可，更简单。**
3. **渠道模板的「字段约束说明」是一段自由文本，不是结构化字段。** 原文说「渠道模板」但没给形态。选自由文本，理由与 027 的 `window`（统计窗口）相同：小红书的约束是「标题 20 字内、首图 3:4」，公众号是「必须有摘要」，这两件事拆不成同一组字段，硬拆会逼人把不知道的格子填满。**若要结构化，那是每渠道一组字段 + 一张表，Q1 也要跟着变成 B。**
