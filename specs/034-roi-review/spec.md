## 需求原文

**下面是文档 14 的原句，不是转述。** 每个列名、受控集和「系统不做什么」都要能指回其中一句；指不回去的，是本规格补的，已在「本规格补的设计」一节单独标出。

**R-061**

> - 在品牌空间内手工登记或导入成本、线索、成交及退款/调整记录，可关联账号、作品、活动/项目和观察窗口；保存币种、金额、时间、录入者、来源证据及修订历史。
> - 成本可配置为策划、人工、拍摄、剪辑、投放等类别；人工时间须有用户设定单价才能折算金额。共享费用采用用户确认的分摊方式，保留原始总额，避免跨作品重复计入。
> - 线索记录可配置阶段、来源及关联标识，支持人工去重/合并并留痕；成交保留关联线索、订单标识、确认金额、退款及可用毛利依据。优先使用脱敏标识，AI 仅访问完成分析所需的授权字段，不要求收集无关客户个人信息。
> - 归因记录区分可确认来源、用户判断、多触点及来源不明；分析窗口和归因方法由人选择。多触点成交按确认规则分配，汇总不得重复计入整笔成交；AI 不自动把时间相关性认定为内容带来的成交。
> - 用户已确认线索来源按人工证据登记：平台关联内容、内容评论、客户自述、专属表单/二维码/口令分别标识依据类型；这些是可用证据，不要求工作台自动采集或生成追踪工具。评论与后续私信是否为同一客户由人工核对。
> - 来源字段允许仅知道平台/账号，作品为空；完全未知明确标记来源不明。来源记录与运营者归因判断分开保存，AI 不补猜具体作品。
> - 同一线索可记录多个内容触点及首次了解、预约前触点等角色，保留时间、证据、记录人；客户自述不伪装为平台直接证据。重复触点不得让品牌汇总重复计数；没有可靠作品来源时只做可支持的账号/品牌层面分析。
> - 金额与公式由服务端确定性计算，AI 负责解释、局限和行动建议。默认经营 ROI 口径为（归因毛利－内容及营销投入）÷内容及营销投入；毛利须扣除对应销售成本，投入与毛利不得重复扣同项成本。显示公式、包含项目、窗口、币种和归因依据。
> - 同时区分销售额/投入比与广告 ROAS（归因广告收入÷广告支出），不得标为利润 ROI。没有毛利依据时经营 ROI 显示不可计算，可以单独展示可计算的收入指标；分母为零、缺失或跨币种未换算时不输出伪造比率，真实负回报可正常呈现。
> - 报告显示投入、有效线索、成交、已知归因覆盖、可计算的转化率/单位成本及 ROI；转化分母与阶段须明确，不把不同窗口混算。原始观测、计算结果、AI 推断分开保存，后续调整产生新的报告输入版本。
> - AI 建议可经人工采用进入选题、预算待办或经营记忆；不自动调整投放预算、发起付款、联系客户或执行交易。本模块不是完整 CRM、财务账簿或投放平台。

**工作流与技术落点（第 8、9 条）**

> - 成本、线索、成交与分摊/归因由经营反馈领域拥有，复盘通过公开接口读取版本化汇总。金额使用精确十进制/最小货币单位，保存币种；公式与计算版本可追溯，禁止把模型生成的算术结果直接作为权威指标。
> - 共享成本分摊及多触点归因需事务一致性和重复导入幂等校验；操作审计与脱敏沿用现有诊断/授权规范。数据结构和迁移在所属任务实施前细拆。

**补充验收**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把花出去的钱记下来，共享的钱分清楚 (Priority: P1)

小张这个月给品牌花了三笔钱：一次拍摄 3000 元，三条视频共用；小红书薯条投放 800 元，投在一条笔记上；他自己剪辑花了 6 小时，他给自己定的单价是 150 元/小时。他逐笔登记：类别、金额、币种、发生日期、关联作品或账号、凭证说明。拍摄那笔他按 1:1:1 分到三条作品，系统显示 1000.00 + 1000.00 + 1000.00 = 3000.00，原始总额仍是 3000.00。剪辑那笔系统按 6 × 150 算出 900.00；如果他没填单价，这笔显示「金额不可计算：缺少工时单价」，不猜。

**Why this priority**：没有投入，就没有任何比率。R-061 第 1、2 条。

**Independent Test**：录一笔直接金额、一笔工时、一笔三方分摊的成本，读回来金额、币种、分摊份额与原额逐一对得上；再改其中一笔，旧修订仍在。

**Acceptance Scenarios**：

1. **Given** 一个品牌空间，**When** 登记一笔 `3000.00 CNY` 的拍摄成本，**Then** 存下 `amount_minor = 300000`、`currency = CNY`、录入人（服务端从会话取）、发生时间、凭证说明，修订号为 1。
2. **Given** 金额填 `3000.005` 且币种是 CNY，**When** 提交，**Then** 400 并点名 `amount`——小数位超过该币种的最小单位，系统不替人舍入。
3. **Given** 请求体里 `amount` 是 JSON 数字而不是字符串，**When** 提交，**Then** 400 并点名 `amount`——浮点在进服务端之前就可能已经不准了。
4. **Given** 一笔工时成本 360 分钟、单价 `150.00 CNY/小时`，**When** 提交，**Then** 金额为 `90000`；**Given** 同一笔没有单价，**Then** 照样能存下，但金额状态是「不可计算：缺少工时单价」，任何包含它的投入合计同样不可计算。
5. **Given** 一笔 `100.00` 的共享成本按 1:1:1 分给三条作品，**When** 保存分摊，**Then** 三份是 `3334 / 3333 / 3333`（最小单位），合计恰好 `10000`；余数去向按 FR-032 的规则，可复现。
6. **Given** 一笔已登记的成本，**When** 修改金额，**Then** 产生修订 2，修订 1 逐字节不变；已经生成的报告版本仍指向修订 1。
7. **Given** 成本属于 A 品牌，**When** B 品牌成员读它或给它加修订，**Then** 得到与「不存在」逐字节相同的拒绝（`trace_id` 除外）。

### User Story 2 - 线索从哪来：证据是证据，判断是判断 (Priority: P1)

一位客户私信说「看了你那条讲面料的视频来的」。小张登记一条线索，客户标识写「客户-0412」，不写名字和电话。他给这条线索加一个触点：平台抖音、账号「品牌主号」、作品「面料对比」、依据类型「客户自述」、角色「首次了解」。一周后同一位客户通过专属二维码预约了到店，他再加一个触点：依据类型「专属表单/二维码/口令」、角色「预约前」、作品为空（二维码印在门店海报上）。另一条线索只知道是从小红书账号来的，作品为空；第三条完全说不清来源，他标「来源不明」。

这些是**证据**。至于这笔成交算谁的，是他之后在成交上单独做的**判断**，两者分开存。

**Why this priority**：R-061 第 5～7 条、D14-V16。归因报告的可信度全部来自这里：一旦客户自述被存成「平台关联内容」，或者系统替人补了作品，后面所有数字都不可信，而且看不出来。

**Independent Test**：造五种来源（平台关联、客户自述、仅知账号、完全未知、多触点），读回来依据类型与作品字段原样；给其中一条加归因判断，触点逐字节不变。

**Acceptance Scenarios**：

1. **Given** 一条线索，**When** 加一个依据类型为「客户自述」、作品为空的触点，**Then** 存下，作品为空，依据类型仍是「客户自述」。
2. **Given** 依据类型为「平台关联内容」，**When** 作品与发布记录都为空，**Then** 400 并点名 `work_id`——这类证据本身就指向一条内容，缺了它证据不成立。
3. **Given** 依据类型为「仅知账号」，**When** 账号为空，**Then** 400 并点名 `account_id`；**When** 作品不为空，**Then** 400 并点名 `work_id`——知道作品就不是「仅知账号」。
4. **Given** 依据类型为「来源不明」，**When** 平台、账号或作品任一不为空，**Then** 400 并点名那一项。
5. **Given** 线索字段，**When** 检索迁移与 Go 结构，**Then** 不存在姓名、手机号、微信号、身份证、地址类的列；客户只有一个化名标识 `customer_ref`，界面写明「不要填真实姓名或联系方式」。
6. **Given** 两条线索其实是同一位客户，**When** 运营者把 B 合并进 A，**Then** B 产生一条带 `merged_into` 的新修订，审计记下是谁、何时、为什么；品牌线索数少一条；B 的触点在 A 名下可见，不丢，也不重复计数。
7. **Given** 一条线索的触点，**When** 任何代码路径试图根据时间先后自动补作品或改依据类型，**Then** 不存在这样的路径（守卫用例扫源码）。

### User Story 3 - 成交、退款、毛利依据 (Priority: P1)

客户下单 10000 元，小张登记成交：关联线索「客户-0412」、订单标识（他从店铺后台抄的单号）、确认金额 `10000.00 CNY`、毛利依据「按销售成本」、销售成本 `7000.00`。半个月后客户退了 1000 元，他登记一条退款，填退款金额 1000 与对应的毛利冲减 300。另一笔成交他不知道成本，毛利依据留「无」。

**Why this priority**：R-061 第 3 条；D14-V13 的缺毛利、退款两项。

**Acceptance Scenarios**：

1. **Given** 毛利依据为「按销售成本」，**When** 保存，**Then** 毛利 = 确认金额 − 销售成本，由服务端算；存下的是依据与两个输入，不是客户端算好的数。
2. **Given** 毛利依据为「直接填写毛利」，**When** 保存，**Then** 存下填写的毛利。

4. **Given** 一笔有毛利依据的成交，**When** 登记退款但没填毛利冲减，**Then** 这笔成交的毛利变为「不可计算：退款未给出毛利冲减」——系统不按比例猜（Q3 已裁定）。
5. **Given** 退款金额超过该成交当前净额，**When** 提交，**Then** 400 并点名 `amount`。
6. **Given** 两条成交的订单标识相同，**When** 手工登记第二条，**Then** 界面提示「疑似重复：与成交 X 的订单标识相同」，用户确认「不是重复」后才写入，确认动作进审计。

### User Story 4 - 一份算得清、说得出来历的复盘报告 (Priority: P1)

月底小张选了窗口「2026-09-01 至 2026-09-30（Asia/Shanghai）」、报告币种 CNY、归因方法「平均分配」，生成报告。报告第一屏是：内容及营销投入、有效线索、成交数、已知归因覆盖、经营 ROI、销售额/投入比、广告 ROAS。每个数旁边有公式、包含了哪些记录（可点开到原始记录的某一修订）、窗口、币种和归因依据。算不出来的写「不可计算」和原因，不是空白也不是 0。

**Why this priority**：R-061 第 8～10 条；D14-V12、V13。

**Independent Test**：固定样例——归因毛利 3000、投入 1000 → 经营 ROI 200.00%；同一窗口销售额 10000、投入 1000 → 销售额/投入比 10.00 倍，标签不含「ROI」「利润」。

**Acceptance Scenarios**：

1. **Given** 归因毛利 `300000`、投入 `100000`（CNY 分），**When** 计算，**Then** 经营 ROI = `(300000 − 100000) / 100000` = **200.00%**，公式 id `business_roi/1`，计算版本 `roi-calc/1`。
2. **Given** 归因销售净额 `1000000`、投入 `100000`，**When** 计算，**Then** 销售额/投入比 = **10.00 倍**，指标 id `revenue_to_spend`，界面标签「销售额/投入比」，**不出现**「ROI」「利润」字样。
3. **Given** 归因毛利 `50000`、投入 `100000`，**When** 计算，**Then** 经营 ROI = **−50.00%**，照实显示，不截成 0、不隐藏。
4. **Given** 投入为 0，**When** 计算，**Then** 三个以投入为分母的指标都是「不可计算：分母为零」，不输出无穷或 0。
5. **Given** 窗口内有一笔 USD 成本、报告币种 CNY、没有录入汇率，**When** 计算，**Then** 投入合计与所有依赖它的指标「不可计算：存在未换算的币种（USD）」，并列出那笔记录；**不静默排除它**。录入汇率 `USD→CNY 7.1234`（十进制字符串）后重新生成，才有数。
6. **Given** 一笔成交在窗口内、它的退款发生在窗口结束之后但在报告生成之前，**When** 计算，**Then** 按 FR-047 计入该成交，并在报告上写明规则。
7. **Given** 广告支出（标为投放的成本）为 0，或没有带投放标记的触点，**When** 计算广告 ROAS，**Then** 「不可计算」并写明是哪一种原因。
8. **Given** 报告上的任意一个数，**When** 点开，**Then** 能看到公式、计算版本、参与计算的每条记录的 id 与修订号及其金额。

### User Story 5 - 多触点与来源不明：不重复、不强补 (Priority: P2)

一次预约关联了两条作品（先看了 A 首次了解，再看了 B 后预约）。品牌层面：预约 1 次、成交 1 笔。作品层面：按「平均分配」A、B 各得 50% 的成交额；按「首次触点」A 得 100%。另有一笔来源不明的成交：它计入品牌成交总数和总销售额，但不分给任何作品或账号，报告单列「来源不明」这一行，并据此算出「已知归因覆盖」。

**Why this priority**：D14-V14、V16。重复计数是这类报告最常见的错误，而且一旦混进品牌合计就看不出来。

**Acceptance Scenarios**：

1. **Given** 一次预约的线索有两个作品触点，**When** 统计品牌预约数，**Then** 是 1。
2. **Given** 一笔 `10001` 分的成交按平均分配给两个触点，**When** 计算，**Then** 两份 `5001 / 5000`，合计 `10001`，不超过也不少于原额。
3. **Given** 各作品的「触达成交数」，**When** 显示，**Then** 标明「同一笔成交可能出现在多个作品下，不可相加」，且品牌合计不由它们相加得来。
4. **Given** 来源不明的成交，**When** 按任何归因方法计算，**Then** 分给作品与账号的份额都是 0，品牌总额里仍有它，覆盖率分母里仍有它。
5. **Given** 只知道账号、作品为空的触点，**When** 计算作品层面，**Then** 这部分进「账号层面（作品未知）」，不摊给该账号下的任何作品。
6. **Given** 运营者的归因判断把一笔成交标为「用户判断」并选定触点，**When** 计算，**Then** 报告对这笔的依据显示「用户判断」，与「可确认来源」分开计数。

### User Story 6 - 从表格导入，重复的认得出来 (Priority: P2)

小张把店铺后台导出的 40 行订单粘进来。系统先预览：37 行可写入、2 行与已有成交的订单标识相同（疑似重复，默认不写）、1 行币种填了 `RMB`（不在允许的取值里，点名第 23 行 `currency`）。他修好第 23 行，逐一核对 2 行疑似重复，其中 1 行其实是另一笔（勾「不是重复」），然后导入。网络断了他又点了一次，结果不变：没有多出一行。导入记录里写着：谁、什么时候、共几行、写入几行、跳过几行重复及原因。

**Why this priority**：D14-V11。

**Acceptance Scenarios**：

1. **Given** 一批里有一行校验不通过，**When** 提交，**Then** 整批不写，拒绝里点名第几行的哪一列（027 的全有或全无）。
2. **Given** 一批里有与已有记录去重键相同的行，**When** 提交且未确认，**Then** 这些行不写入，导入批次记录逐行写明「疑似重复：与 X 相同」；其余行写入。
3. **Given** 同一个 `Idempotency-Key`、同一份输入，**When** 重发，**Then** 返回原响应，各表行数不变。
4. **Given** 同一个 `Idempotency-Key`、不同输入，**When** 提交，**Then** 409，点名 `Idempotency-Key`。
5. **Given** 不同的 `Idempotency-Key`、与上一批完全相同的行，**When** 提交，**Then** 每一行都被识别为疑似重复（去重键相同），不写入，除非逐行确认。
6. **Given** 导入完成，**When** 查看导入批次，**Then** 能看到操作者、时间、行数、每行的结果与生成的记录 id；审计表有一条对应事件。

### User Story 7 - 改了记录，旧报告不变 (Priority: P2)

报告生成后，小张发现一笔成本记错了，改成新金额。旧报告版本打开仍是原来的数，页面提示「有 1 条输入在此版本之后被修改」。他点「用最新记录生成新版本」，得到版本 2，版本 1 不变，两版可以并排看。

**Acceptance Scenarios**：

1. **Given** 报告版本 1 引用了成本 C 的修订 1，**When** C 产生修订 2，**Then** 版本 1 的输入与结果逐字节不变。
2. **Given** 同上，**When** 打开版本 1，**Then** 显示「输入已有更新」的派生提示，列出是哪几条；这个提示不落存储。
3. **Given** 生成版本 2，**When** 对比，**Then** 两版各自保存参数、输入引用、计算版本和结果。
4. **Given** 用版本 1 保存的输入与计算版本重新计算，**When** 比较，**Then** 与版本 1 保存的结果逐字节相同。

### Edge Cases

- **同一笔钱既算投入又算销售成本**：成本记录只能是内容及营销投入；销售成本只存在于成交的毛利依据里。两者是不同实体，不存在一条记录同时进入两边的路径（R-061「投入与毛利不得重复扣同项成本」）。一条用例钉住：成本记录上没有「计入销售成本」这类字段。
- **成本跨窗口**（例如一笔季度投放费）：成本只有一个发生时间。想按月分开，用户先把它分摊到多个「期间」目标（FR-031）；系统不自动按天折算（Q6 已裁定）。
- **分摊权重都为 0**：拒绝，点名 `allocations`。
- **分摊到的作品后来被删除**：分摊仍在，报告里那一份显示「作品已不存在」，金额照计；无外键，也无级联删除。
- **一条线索没有任何触点**：合法，归为「来源未登记」，与「来源不明」（用户明确标了不知道）分开显示。
- **一笔成交没有关联线索**：合法（订单直接来），归因只能看成交自身的判断；品牌成交数照计。
- **成交关联的线索已被合并**：读取时沿 `merged_into` 找到合并后的线索取触点，原关联保留在修订历史里。
- **汇率**：只在报告参数里录入，随报告版本保存；同一对币种在一份报告里只能有一个汇率。十进制字符串，最多 12 位小数，不是浮点。
- **窗口与时区**：窗口按品牌时区（`loretide.timezone`）解释为 `[开始日 00:00, 结束日次日 00:00)`，存成带时区的时间点。
- **负毛利的成交**：合法，照实进入合计。
- **极大金额**：单条 `|amount_minor| ≤ 10^15`；合计用任意精度整数，不会溢出。
- **报告范围内一条记录都没有**：各指标显示「不可计算：没有数据」，不是 0。

## Requirements *(mandatory)*

### Functional Requirements

**金额与币种（D2）**

- **FR-001**：每条带金额的记录 MUST 保存整数 `amount_minor`（`bigint`）与 `currency`（ISO 4217 三位大写字母）。MUST NOT 有任何浮点类型的金额列或字段。
- **FR-002**：`currency` MUST 取自模块内一张「币种 → 小数位」表（Q1 已裁定：`CNY 2、HKD 2、TWD 2、USD 2、EUR 2、GBP 2、SGD 2、JPY 0、KRW 0`），不在表内即拒绝并点名 `currency`。
- **FR-003**：API 接收金额 MUST 是十进制**字符串**（如 `"3000.00"`）；JSON 数字 MUST 被拒绝并点名字段。小数位多于该币种的位数 MUST 被拒绝，MUST NOT 替用户舍入。
- **FR-004**：单条 `|amount_minor|` MUST ≤ `10^15`；所有合计与比率 MUST 用任意精度整数/有理数计算（Go `math/big`），MUST NOT 用 `float64`。一条守卫用例扫计算相关源文件，确认不出现 `float32` / `float64`。
- **FR-005**：舍入规则全模块只有一条：**四舍五入，远离零**（half away from zero），用于工时折算、汇率换算和比率显示（Q2 已裁定）。分摊与多触点分配 MUST NOT 用舍入，而用 FR-032 的余数规则。
- **FR-006**：跨币种运算 MUST 只在报告参数里有该币种对的用户录入汇率时进行；汇率是十进制字符串（最多 12 位小数），与录入人、录入时间、说明一起存进报告输入版本。没有汇率时，所有依赖该记录的合计与比率 MUST 为「不可计算」，原因码 `currency_unconverted`，并列出涉及的记录；MUST NOT 静默排除该记录。

**成本（R-061 第 1、2 条）**

- **FR-010**：成本记录 MUST 保存：类别（自由文本，Q5 已裁定）、计价方式（受控集 `amount` 直接金额 / `labor_time` 工时）、金额或（工时分钟数 + 单价 + 币种）、发生时间、是否为广告投放（`ad_spend` 布尔，广告 ROAS 的分母只取它）、关联账号（可空）、关联作品（可空）、活动/项目标签（自由文本，可空，Q4 已裁定）、凭证说明、录入人、修订号。
- **FR-011**：`labor_time` 成本的金额 MUST 由服务端按「分钟数 × 单价 ÷ 60」计算并按 FR-005 舍入；单价缺失时 MUST 仍可保存，金额状态为「不可计算」，原因码 `labor_rate_missing`。
- **FR-012**：成本记录 MUST NOT 有任何表示「计入销售成本」的字段；销售成本只存在于成交的毛利依据里。
- **FR-013**：修改 MUST 产生新修订（`revision` 递增），旧修订逐字节不变；「作废」也是一条修订（`voided = true`），MUST NOT 有 UPDATE 或 DELETE（工作区删除链除外）。提交修订时 MUST 带 `base_revision`，与当前最新不符 → 409，点名 `base_revision`。本条适用于本卡所有修订制记录。

**线索与触点（R-061 第 3、5、6、7 条；D4）**

- **FR-015**：线索记录 MUST 保存：化名客户标识 `customer_ref`（自由文本，短）、阶段（自由文本，Q5 已裁定）、是否有效线索（`qualified` 布尔）、首次登记时间、说明、录入人、修订号、`merged_into`（可空）。
- **FR-016**：线索、成交、触点 MUST NOT 有姓名、手机号、微信号、邮箱、身份证、地址类的列或字段。一条守卫用例扫迁移与 Go 结构的列名/字段名；界面在客户标识旁写明「请填化名或编号，不要填真实姓名或联系方式」。
- **FR-017**：触点 MUST 是独立记录，挂在一条线索上，保存：依据类型（受控集**恰好六项**，见 FR-018）、平台（可空，取 `ip-profile` 的八个平台）、账号（可空）、作品（可空）、发布记录（可空）、角色（受控集 `first_touch` 首次了解 / `pre_booking` 预约前 / `other` 其他，Q5 已裁定）、是否投放触点（`paid` 布尔）、发生时间、证据说明、录入人、修订号。
- **FR-018**：依据类型受控集 MUST 恰好是：`platform_linked_content`（平台关联内容）、`content_comment`（内容评论）、`customer_statement`（客户自述）、`dedicated_channel`（专属表单/二维码/口令）、`account_only`（仅知账号）、`unknown`（来源不明）。**MUST NOT 有「其它」**。
- **FR-019**：依据类型与字段的组合 MUST 按下表校验，不合法即 400 并点名字段：

  | 依据类型 | 作品 / 发布记录 | 账号 | 平台 |
  |---|---|---|---|
  | `platform_linked_content` | 至少一个必填 | 可空 | 必填 |
  | `content_comment` | 至少一个必填 | 可空 | 必填 |
  | `customer_statement` | 可空 | 可空 | 可空 |
  | `dedicated_channel` | 可空 | 可空 | 可空 |
  | `account_only` | **必须为空** | 必填 | 必填 |
  | `unknown` | **必须为空** | **必须为空** | **必须为空** |

- **FR-020**：归因判断 MUST 是挂在**成交**上的独立记录（另一张表），保存：判断类型（受控集 `confirmed` 可确认来源 / `operator_judgement` 用户判断 / `multi_touch` 多触点 / `unknown` 来源不明）、采信的触点 id 列表、可选的人工权重、说明、录入人、修订号。**触点记录 MUST NOT 因判断而改变**；判断 MUST NOT 写进触点表。
- **FR-021**：系统 MUST NOT 有任何根据时间先后、相似度或模型输出自动填写作品、依据类型或归因判断的路径。一条守卫用例扫源码；另一条确认模块不调用模型、不发外部请求。
- **FR-022**：线索合并 MUST 是被合并线索的一条新修订（`merged_into = 目标线索`），带原因说明并写审计；MUST NOT 删除或改写任何触点。合并后品牌层面按目标线索计 1 条；被合并线索的触点在目标线索下读取，按触点 id 去重。取消合并 = 再写一条 `merged_into = ''` 的修订。合并链 MUST NOT 成环（A→B→A 拒绝，点名 `merged_into`）。

**成交、退款与调整（R-061 第 3 条）**

- **FR-023**：成交记录 MUST 保存：关联线索（可空）、订单标识 `order_ref`（自由文本，可空）、确认金额、币种、成交时间、毛利依据（受控集 `none` / `stated_gross_profit` 直接填写毛利 / `cogs` 按销售成本）及对应输入、说明、录入人、修订号。
- **FR-024**：退款/调整 MUST 是挂在成交上的独立记录：类型（受控集 `refund` / `adjustment`）、销售额变动（退款为正数，表示减少）、毛利变动（可空）、币种（MUST 与成交相同）、发生时间、说明、录入人、修订号。退款使成交净额小于 0 时 MUST 拒绝并点名 `amount`。
- **FR-025**：成交的毛利 MUST 由服务端按依据确定性得出：`stated_gross_profit` 取填写值；`cogs` 取「确认金额 − 销售成本」；两者都再加上各有效调整记录的毛利变动。任一有效的退款/调整的毛利变动为空、而该成交的依据不是 `none` 时，这笔成交的毛利 MUST 为「不可计算」，原因码 `refund_without_gross_delta`（Q3 已裁定）。

**重复识别与导入（D5；D14-V11）**

- **FR-026**：成本、线索、成交各有一个由服务端从规范化字段算出的**去重键**（定义见合同 §4）。手工登记或导入时，与本工作区已有有效记录去重键相同的 MUST 被标为「疑似重复」，**默认不写入**；用户逐条确认「不是重复」后写入，确认 MUST 进审计。
- **FR-027**：导入 MUST 接收前端解析好的行（首版是粘贴 CSV 文本，沿用 027 `csv.ts` 的做法；文件上传等 W-03）。校验错误 MUST 全有或全无，并点名第几行的哪一列；疑似重复不是错误，按 FR-026 逐行处理。
- **FR-028**：导入请求 MUST 支持 `Idempotency-Key`（≤255 字节），幂等 MUST 完全在 `feedback-learning` 内实现，MUST NOT import `idempotency` 模块：本模块的占位表 `content_roi_import_claim`（contract §1.9）在导入的同一写事务内插入（工作区, 记录类型, 键, 请求指纹, 导入批次 id），唯一索引 `(workspace_id, record_kind, idempotency_key)` 挡住并发的第二个请求。同键同输入 MUST 重放原响应（由该批次行重建，逐字节相同）；同键异输入 MUST 409 点名 `Idempotency-Key`；首个请求回滚时占位随之消失，重试可正常执行。占位表只插不改。
- **FR-029**：每次导入 MUST 写一条导入批次记录：操作者、时间、记录类型、总行数、写入数、跳过数、每行结果（写入的记录 id / 疑似重复的对照记录 id / 用户确认不是重复），并在同一事务写审计。导入批次只插不改。

**分摊与多触点分配（D3；D14-V14、V16）**

- **FR-030**：共享成本 MUST 可以分摊到多个目标；分摊是该成本某一修订的附属记录，随修订一起版本化。成本原始总额 MUST 保持不变。
- **FR-031**：分摊目标类型 MUST 是受控集 `work` / `account` / `campaign_label` / `period`（期间，`YYYY-MM`）；分摊方式 MUST 是受控集 `weights`（正整数权重）/ `amounts`（直接填各份金额）。`amounts` 方式各份之和 MUST 恰好等于原额，否则 400 点名 `allocations`。
- **FR-032**：`weights` 方式的余数规则（最大余数法）：每份先取 `floor(|原额| × 权重 ÷ 权重和)`；剩余的最小单位按「小数部分从大到小，相同时按目标键（类型 + id）字典序从小到大」逐个 +1；原额为负时按绝对值计算后每份取回负号。结果 MUST 满足各份之和 = 原额，且同一输入永远得到同一结果。
- **FR-033**：多触点收入与毛利分配 MUST 用与 FR-032 相同的余数规则，并列时的排序键是触点的（发生时间，触点 id）。一笔成交分给各触点的总和 MUST 恰好等于该成交的分配基数，MUST NOT 超过。
- **FR-034**：报告的归因方法 MUST 由用户在报告参数里选择，受控集 `first_touch` / `last_touch`（取角色为 `pre_booking` 的最后一个，没有则取最后一个）/ `even_split` / `judgement_weights`（取归因判断里的人工权重；某笔成交没有人工权重时这笔按 `even_split`，并在报告上逐笔标出）。
- **FR-035**：只有被归因判断采信的触点参与分配；判断类型为 `unknown`、或成交没有归因判断、或采信触点为空的成交，分给作品与账号的份额 MUST 为 0，计入「来源不明 / 未判断」行。
- **FR-036**：作品为空的采信触点（`account_only`，或作品为空的 `customer_statement` / `dedicated_channel`），分到的份额 MUST 进「账号层面（作品未知）」；账号也为空的进「品牌层面（账号未知）」；MUST NOT 再摊给任何作品。
- **FR-037**：品牌层面的线索数、预约数（处于报告参数所选阶段的线索数）、成交数、成交额 MUST 按线索 id / 成交 id 去重计数，与触点数量无关；MUST NOT 由作品层面的数字相加得出。
- **FR-038**：作品层面的「触达成交数」若显示，MUST 标明「同一笔成交可能出现在多个作品下，不可相加」。

**确定性计算（D2；D14-V12、V13）**

- **FR-040**：所有指标 MUST 由服务端的纯函数计算，输入是一份冻结的「报告输入」（参数 + 记录修订快照），输出是结果对象。同一输入与同一计算版本 MUST 得到逐字节相同的输出。前端 MUST NOT 做任何指标算术，只显示服务端给的值与字符串。
- **FR-041**：计算版本 MUST 是常量字符串，首版 `roi-calc/1`；每个指标 MUST 带公式 id（如 `business_roi/1`）。改变任何公式或舍入 MUST 升版本号；旧报告版本 MUST 继续显示它当时的版本号与结果，MUST NOT 用新公式重算覆盖。
- **FR-042**：每个指标的结果 MUST 是二者之一：`{status: "ok", value, display, numerator, denominator, formula, records}` 或 `{status: "not_computable", reason, records}`。原因码受控集：`missing_gross_profit`、`zero_denominator`、`missing_denominator`、`currency_unconverted`、`labor_rate_missing`、`refund_without_gross_delta`、`no_data`。MUST NOT 用 0、空、无穷或 NaN 表示「不可计算」。
- **FR-043**：**经营 ROI**（`business_roi`）MUST = （归因毛利 − 内容及营销投入）÷ 内容及营销投入，显示为百分比，保留两位小数。**固定样例 MUST 是一条明写的用例**：归因毛利 `300000`、投入 `100000`（CNY 分）→ `200.00%`。
- **FR-044**：**销售额/投入比**（`revenue_to_spend`）MUST = 归因销售净额 ÷ 内容及营销投入，显示为「N.NN 倍」。**固定样例**：`1000000 / 100000` → `10.00 倍`。其标签与 id MUST NOT 含「ROI」「利润」「profit」。
- **FR-045**：**广告 ROAS**（`ad_roas`）MUST = 归因到 `paid = true` 触点的销售净额 ÷ `ad_spend = true` 的成本合计，显示为「N.NN 倍」，标签「广告 ROAS（收入÷广告支出）」，MUST NOT 称为利润或经营 ROI。
- **FR-046**：负回报 MUST 照实显示（如 `−50.00%`），MUST NOT 截断、取绝对值或隐藏。
- **FR-047**：窗口规则：成本按发生时间、线索按首次登记时间、成交按成交时间落入窗口；退款/调整**跟随它所属的成交**，只要它的发生时间不晚于报告版本的生成时间，就计入该成交（Q6 已裁定）。报告 MUST 在公式说明里写出这条规则。一份报告只有一个窗口，所有指标 MUST 用同一窗口。
- **FR-048**：转化率 MUST 明写分子阶段与分母阶段，二者来自同一批线索（分母 = 窗口内首次登记、到达过分母阶段的线索；分子 = 其中到达分子阶段的）；阶段由报告参数选择（Q5 已裁定）。单位成本（每有效线索成本、每成交成本）MUST 标明分母。
- **FR-048a**（Q5 裁决附加）：阶段是自由文本、没有先后顺序，转化率只能按「是否到达过某阶段」计算。报告的局限说明（结果对象的 `rules`，界面上的「计算规则与局限」）MUST 写明这一点：「阶段是自由文本，没有先后顺序；转化率只按线索是否到达过某阶段计算，不反映阶段之间的先后。」
- **FR-049**：已知归因覆盖 MUST 同时给出按笔数与按金额两个比例：判断类型不是 `unknown` 且采信触点非空的成交 ÷ 窗口内全部成交。
- **FR-050**：每个 `ok` 指标 MUST 附带参与计算的记录清单（记录类型、id、修订号、金额、币种、换算后金额）；报告界面 MUST 能从任一指标点到这些记录的原修订。
- **FR-051**：投入中任一成本「不可计算」（缺单价、未换算）时，投入合计及所有以它为分子或分母的指标 MUST 为「不可计算」，原因码取原因码表中排在最前的那个，`records` 列出全部涉及记录。
- **FR-052**：分子中任一归因成交的毛利「不可计算」时，经营 ROI MUST 为「不可计算」（`missing_gross_profit` 或 `refund_without_gross_delta`），而销售额/投入比与广告 ROAS 照常计算（R-061「可以单独展示可计算的收入指标」）。

**报告版本（D5；R-061 第 10 条）**

- **FR-053**：报告 MUST 由用户显式生成；每次生成 MUST 产生一条新的「报告输入版本」，保存：参数（窗口、时区、报告币种、汇率、归因方法、转化阶段、范围过滤）、参与记录的（id, 修订号）快照、计算版本、结果对象、生成人、生成时间。只插不改。
- **FR-054**：原始记录的任何新修订 MUST NOT 改变已生成的报告版本。
- **FR-055**：打开一个报告版本时，「输入已有更新」MUST 是读时派生的（比较快照里的修订号与当前最新修订号，以及窗口内是否出现新记录），MUST NOT 落存储。
- **FR-056**：「用最新记录生成新版本」MUST 以上一版参数为默认值生成版本号 +1 的新版本；上一版保留。
- **FR-057**：对任一已存版本，用其保存的输入与计算版本复算 MUST 得到与保存结果逐字节相同的输出；这是一条用例，不是界面功能。
- **FR-058**：报告 MUST 通过一个公开的 Go 读接口提供版本化汇总（给 BO-02 经营诊断等后续消费者），返回的结构 MUST NOT 含 `customer_ref`、`order_ref`、任何证据说明原文。

**AI 解释层（D1；只留位置，不建）**

- **FR-063**：本卡 MUST NOT 提供「采用建议」进选题、预算待办或经营记忆的任何路径；MUST NOT 有调整预算、付款、联系客户或交易的路径。

### Key Entities

- **成本修订（Cost Revision）**：一笔花出去的钱的某一版本。直接金额或工时×单价；可标为广告投放；可分摊。
- **成本分摊（Cost Allocation）**：某一成本修订分到各目标的份额，合计恰好等于原额。
- **线索修订（Lead Revision）**：一个化名客户的某一版本；可被合并进另一条。
- **触点修订（Touch Revision）**：一条证据：客户从哪里知道或到来，依据类型六选一，作品可空。**证据，不是判断。**
- **成交修订（Deal Revision）**：一笔确认的交易，带毛利依据。
- **退款/调整修订（Adjustment Revision）**：挂在成交上的销售额与毛利变动。
- **归因判断修订（Attribution Judgement Revision）**：运营者对一笔成交来源的判断与采信的触点。**判断，不是证据。**
- **导入批次（Import Batch）**：一次导入的审计记录，逐行结果。
- **导入占位（Import Claim）**：一个 `Idempotency-Key` 对应的请求指纹与导入批次 id，只插不改；本模块自建，不用 `idempotency` 模块。
- **报告输入版本（Report Version）**：冻结的参数、记录修订快照、计算版本与结果。
- **指标结果（Metric Result，值对象）**：`ok` 或 `not_computable`，带公式与记录清单。

## Success Criteria *(mandatory)*

- **SC-001**（D14-V12）：固定样例用例：归因毛利 `300000`、投入 `100000` → `business_roi` 为 `200.00%`；销售额 `1000000`、投入 `100000` → `revenue_to_spend` 为 `10.00 倍`，其标签与 id 不含「ROI」「利润」「profit」。一条 Go 用例 + 一条 core 显示用例。
- **SC-002**（D14-V13）：以下各一条用例，全部在计算器纯函数层：缺毛利 → `missing_gross_profit` 且收入指标仍 `ok`；零投入 → `zero_denominator`；退款缺毛利变动 → `refund_without_gross_delta`；负回报 → `−50.00%`；未换算币种 → `currency_unconverted` 且记录清单含那笔；录入汇率后 → `ok`；窗口外成交不计入、窗口内成交的晚到退款计入。
- **SC-003**（D14-V14）：分摊用例：`10000` 按 1:1:1 → `3334/3333/3333`；`100` 按七个 1 → 各份和为 `100`；`amounts` 方式和不等于原额 → 400。另一条性质用例：固定种子生成 1000 组输入，各份之和恒等于原额，且同一输入两次结果相同。
- **SC-004**（D14-V14）：多触点分配：`10001` 平均分两触点 → `5001/5000`；各触点份额之和恒等于成交分配基数（性质用例）；来源不明成交分给作品与账号的份额为 0。
- **SC-005**（D14-V16）：五种来源各一条用例（平台关联、客户自述、仅知账号、完全未知、多触点），作品可空的读回仍为空；给成交写归因判断后，触点表逐字节不变。
- **SC-006**（D14-V16）：一条线索、一次预约、两个作品触点 → 品牌预约数 1、成交数 1；两个作品的「触达成交数」各为 1，品牌合计仍为 1。
- **SC-007**（D14-V11）：导入：同键同输入重放、同键异输入 409、异键同行全部识别为疑似重复；一批有一行坏 → 一行都不写且点名行与列；导入批次记录与审计各一条。

## Assumptions

1. **数据都是人录的**。本卡不接任何店铺、广告或 CRM 接口，不生成追踪链接或二维码（R-061「不要求工作台自动采集或生成追踪工具」）。
2. **一个品牌 = 一个工作区**（D6）。品牌之间没有汇总。
3. **一份报告只有一种报告币种**。其他币种的记录要么录汇率换算，要么该份报告相应指标不可计算。
4. **窗口按品牌时区解释**，时区读自 `loretide.timezone`（LT-009）。
5. **工作区成员都可以录入和生成报告**；角色化权限没有既有实体可挂，与 027 相同。
6. **本模块不是 CRM、不是账簿、不是投放平台**：没有客户联系方式、没有凭证附件（等 W-03）、没有对账、没有预算控制。

## 本规格补的设计（原文没有直接给，改起来的代价写在后面）

1. **所有记录都是修订制（只插不改）**。原文要求「保存……修订历史」和「后续调整产生新的报告输入版本」；最直接的满足办法是每次修改写一行新修订，报告快照引用（id, 修订号）。若主控要「原地更新 + 历史表」，每张表多一张历史表，报告快照改为引用历史行。
2. **触点与归因判断是两张表**。原文「来源记录与运营者归因判断分开保存」；放在同一行的两列也算分开，但那样改判断会产生触点的新修订，看上去像证据变了。
3. **报告结果存下来，而不是每次打开重算**。原文「原始观测、计算结果、AI 推断分开保存」；另加 FR-057 的复算用例保证存的就是算的。
4. **余数用最大余数法**（FR-032）。原文只要求「合计与原额一致」；也可以「余数全给第一份」，更简单，但会一直偏向排在前面的目标。
5. **退款缺毛利变动时整笔毛利不可计算**（FR-025），而不是按收入比例冲减。见 Q3。
