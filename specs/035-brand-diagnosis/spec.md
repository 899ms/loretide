## 需求原文

**下面是文档 14 的原句，不是转述。** 每个受控集、每条「系统不做什么」都要能指回其中一句或主控的 D1–D9；指不回去的，在「本规格补的设计」一节单独列出。

**R-057**

> - 根据用户选择的品牌目标、账号配置、内容支柱、发布节奏、作品、人工指标和反馈生成诊断。支持账号报告及授权范围内的品牌汇总。
> - 诊断至少区分定位与表达一致性、内容覆盖、节奏、表现变化、受众反馈和执行流程问题；维度可配置，不预设行业运营角色。
> - 报告记录分析范围、时间窗口、数据完整性、原始依据、AI 判断、替代解释、局限和行动建议。未知数据保持未知，不伪造分数，不把相关性写成因果结论。
> - 无数据时显示可诊断范围与补录待办，允许定性分析；不能生成有数据支持的增长结论。不同平台指标不直接混合排名。
> - 建议可由人采用为账号配置修改、选题或待办；长期经营记忆仍须人工采纳。运营诊断与文档13的开发诊断面板分别建模和展示。

**工作流与技术落点（摘录）**

> 节点/监测发现 → 授权素材与候选选题 → 人工选择 → 已有研究/创作/审核链路 → 手工发布与数据录入 → 经营诊断/复盘 → 人工采纳建议。
>
> - 诊断由复盘领域拥有，复用人工观测、作品引用、AI 产物版本及采纳机制；品牌汇总先授权，再读取账号资料。
> - 数据库不新增外键/级联；必要关系由应用事务校验。新增索引遵守现有独立并发索引迁移约束。
> - 原生日历/选题页接入节点，研究/来源页接入监测，运营复盘页接入诊断；Skill 规定分析方法，服务端负责授权、状态与持久化。

**补充验收**

| 编号 | 验收要求 |
| --- | --- |
| D14-V01 | 两品牌同名节点互不泄漏；账号专属材料不因品牌汇总被越权读取 |
| D14-V04 | 诊断在缺数据、零值、不同平台口径下准确显示限制；不能凭空生成增长或因果结论 |
| D14-V05 | 诊断可追溯到输入版本/观察窗口；拒绝建议不改配置或记忆，采纳有动作记录 |
| D14-V08 | 浏览器用节点→候选→作品→手工反馈→诊断跑通闭环；模拟结果和真实联网分别标识、分别验收 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 给一个账号做一次诊断：看得出查了什么、缺了什么 (Priority: P1)

小张给品牌的小红书主号做月度诊断。他选账号「品牌主号」、窗口 `2026-09-01 至 2026-09-30`（品牌时区 Asia/Shanghai）、对比窗口 `2026-08-01 至 2026-08-31`，勾上「节奏」「表现变化」「受众反馈」三个维度，表现变化只看「曝光、收藏、私信」三个指标。生成后，报告第一屏是**分析范围**：哪个账号、哪两个窗口、用的是账号配置第几版、读到了几条发布记录、几条指标、几条摘录。然后每个维度一块：算出来的事实、这一维度的数据完整性、局限说明。算不出来的写「不可计算」和原因。

**Why this priority**：R-057 第 1、3 条；没有范围与完整性，后面的数字都没有来历。

**Independent Test**：构造一个账号、两条窗口内的发布记录（一条有指标、一条没有），生成报告，读回范围清单与完整性计数逐一对得上；窗口外的发布记录不在清单里。

**Acceptance Scenarios**：

1. **Given** 一个账号与所选维度，**When** 生成报告，**Then** 产生报告版本 1，保存参数、输入快照、计算版本 `opdiag-calc/1` 与结果；`result.scope` 列出账号、两个窗口（带时区）、账号配置 `revision_id`、每类输入的条数。
2. **Given** 窗口 `09-01 至 09-30`，**When** 一条发布记录的 `published_at` 是 `2026-09-30T23:30+08:00`，**Then** 它在窗口内；`2026-10-01T00:10+08:00` 的不在。
3. **Given** 一条发布记录 `published_at` 为空，**When** 生成，**Then** 它不落入任何窗口，出现在完整性缺口「发布时间未知」里。
4. **Given** 维度列表为空，**When** 生成，**Then** 仍然产生报告，只有 `scope` 与总体完整性（「只看范围」是合法的诊断）。
5. **Given** 参数里出现 `role`、`industry` 之类的字段，**When** 提交，**Then** 400 点名该字段——本卡不预设行业角色（R-057 第 2 条）。

### User Story 2 - 缺数据时，报告说「不知道」，并告诉我补什么 (Priority: P1)

新品牌只录了两条发布记录，一条指标都没有，经营规则也没设节奏。小张生成诊断：节奏维度显示实际每周篇数，但「目标：未设定」，不做达成判断；表现变化「不可计算：窗口内没有指标」；受众反馈「没有反馈摘录」。页面下方「补录待办」列出：去经营规则设定小红书节奏；给发布记录 A、B 补录指标；给账号配置确认「内容支柱」。他可以写一段**定性判断**，系统标明「定性判断：没有数据支持」。

**Why this priority**：R-057 第 3、4 条；D14-V04。

**Acceptance Scenarios**：

1. **Given** 经营规则里没有该渠道的节奏，**When** 算节奏维度，**Then** 目标为「未设定」，每周实际篇数照常列出，**不输出**「达成 / 未达成」。
2. **Given** 节奏设为 0（「这周这个渠道不发」），**When** 该周实际 0 篇，**Then** 显示「目标 0，实际 0」；**0 与未设定是两种状态**。
3. **Given** 窗口内一条人工指标值为 nil（平台不显示），**When** 计算，**Then** 它计入「未知」条数，不计入合计，不当作 0。
4. **Given** 窗口内一条指标值为 0（确认为零），**When** 计算，**Then** 它计入「有值」条数，合计加 0。
5. **Given** 任一维度，**When** 数据不全，**Then** `completeness` 给出 `expected` 与 `present` 两个计数和缺口清单；**不输出**百分制分数、等级或颜色评级。
6. **Given** 一条补录待办，**When** 查看，**Then** 写明缺什么、在哪条记录上、去哪一页补（链接到账号设置、经营规则、反馈录入页）。

### User Story 3 - 表现变化：两个明确窗口，按平台分开，不排名 (Priority: P1)

品牌有小红书与抖音两个账号。小张做品牌汇总，选「表现变化」、指标「曝光、点赞」。报告按平台分块：小红书一块、抖音一块，每块里每个指标两行（对比窗口、本窗口）：发布记录数、有值条数、未知条数、合计、每条均值，以及两窗口均值之差。**没有跨平台的合计，没有账号或平台排名**。某一块里指标的「统计窗口」文字不一致（「发布后 7 天」与「发布后 14 天」混在一起），这一块标出「统计口径不一致」并列出出现过的写法。

**Why this priority**：R-057 第 4 条「不同平台指标不直接混合排名」；D14-V04「不同平台口径」。

**Acceptance Scenarios**：

1. **Given** 两个平台的指标，**When** 计算，**Then** 结果按 `(platform, metric)` 分组；不存在任何把两个平台的值相加、相比或排序的字段。
2. **Given** 对比窗口里某组有值条数为 0，**When** 计算差值，**Then** 该组 `change` 为「不可计算：对比窗口没有数据」，本窗口的数字照常显示。
3. **Given** 一组里 `stat_window` 出现两种写法，**When** 计算，**Then** 该组带标记 `stat_window_mixed` 与写法清单，差值照算，但局限说明写明「两窗口的统计口径不一致，差值不可直接比较」。
4. **Given** 本窗口均值比对比窗口高，**When** 显示，**Then** 标签是「两窗口均值之差」，**不出现**「增长」「提升」「带来」「导致」一类的词；局限说明固定包含「差值只描述两个窗口的数字，不说明原因」。
5. **Given** 同一条发布记录同一指标有多次采样，**When** 计算，**Then** 取采样时间不晚于报告生成时刻的**最后一次**（相同时按 `created_at`、再按 id），同一条发布记录不重复计数（Q7）。

### User Story 4 - 一致性与覆盖：人勾的清单，机器只计数 (Priority: P2)

小张打开诊断页的「作品标注」区，逐条看窗口内的作品：给每条作品勾它属于哪个内容支柱（支柱清单是他这次在参数里写的「面料知识 / 穿搭 / 门店活动」）；再对照账号配置勾一致性检查清单：定位、表达风格、禁用表达，每项「符合 / 不符合 / 拿不准」。生成报告后，覆盖维度显示每个支柱几条、「未标注」几条；一致性维度显示每个检查项符合几条、不符合几条、拿不准几条、未检查几条，以及账号配置里哪些项还没确认。

**Why this priority**：R-057「定位与表达一致性」「内容覆盖」。一致性与支柱归属都是判断，机器在执行器禁用时做不了，只能计数人的标注（D1）。

3. **Given** 一条作品先标「穿搭」、后撤掉「穿搭」改标「面料知识」，**When** 算覆盖，**Then** 按每个（作品，支柱）的最新标注计，旧标注保留在记录里。
4. **Given** 参数里的支柱清单为空，**When** 选了覆盖维度，**Then** 该维度「不可计算：未指定内容支柱」，不从账号配置文字里切分出支柱。
5. **Given** 一致性标注记录了它对照的账号配置 `revision_id`，**When** 账号配置后来改到新版本，**Then** 旧标注仍计入，但报告在该维度的局限说明里写明「有 N 条标注对照的是旧版账号配置」。

### User Story 6 - 人写判断、替代解释与建议；采纳或拒绝都有记录 (Priority: P1)

看完报告版本 2，小张写下：判断「9 月收藏均值低于 8 月」（引用表现维度的那一组数字）；替代解释「9 月有两条是门店活动通知，本来就不以收藏为目标」；建议三条——(1) 做一期「面料对比」选题；(2) 待办「补齐 9 月所有抖音发布的指标」；(3) 把账号配置的「内容支柱」改成新写法。他采纳 (1)：系统建一张草稿选题卡并记下「由建议 S1 采纳，决定 D7」；采纳 (2)：出现一条待办；采纳 (3)：出现一份「账号配置修改提议」，**账号配置本身没变**，要他在提议上再点一次「确认修改」并看到修改前后对照，才产生账号配置的新版本。他拒绝了第四条建议：什么配置都没变，只多一条拒绝记录。

**Why this priority**：R-057 第 3、5 条；D3；D14-V05。

**Acceptance Scenarios**：

1. **Given** 一条判断，**When** 选「有数据依据」却没引用报告里的任何一项，**Then** 400 点名 `evidence_refs`；选「定性判断」则不需要引用，界面标明「定性判断：没有数据支持」（R-057「允许定性分析；不能生成有数据支持的增长结论」）。
2. **Given** 判断引用了 `performance/xiaohongshu/favorite`，**When** 这一项在该报告版本里不存在，**Then** 400 点名 `evidence_refs`。

5. **Given** 选题卡已经建好、但记效果时失败，**When** 重试，**Then** 凭这条建议的幂等键找到已建的那张卡并关联它，**不建第二张**；效果 `done` 指向那张卡（Q3 补充）。
6. **Given** 采纳一条目标为账号配置修改的建议，**When** 成功，**Then** 只产生一份提议（`proposed`），`ip-profile` 的版本数**不变**。

8. **Given** 拒绝一条建议，**When** 完成，**Then** 只多一条决定记录与一条审计；账号配置版本数、选题卡数、待办数、提议数、任何设置**全部不变**，也没有调用任何其他模块的写接口。

10. **Given** 任何建议或判断，**When** 查看，**Then** 标明「人工撰写」；本版不存在 AI 写的判断或建议（`author_kind` 只有 `human` 一个取值）。

### Edge Cases

- **账号关联不到**：作品没有选题卡（历史导入）或选题卡没有账号 → 该发布记录进「账号未知」一节，并进缺口清单；**不按** `platform_account` 自由文本去匹配账号（那是推断）。表现维度用指标自身的 `account_id`（人录的字段），与作品的账号无关（contract §5.1）。
- **账号的平台不在交付渠道里**（知乎、微博等）：节奏与发布记录相关的维度显示「该平台没有可登记的发布渠道」，不是 0。
- **窗口跨周**：节奏按品牌时区的 ISO 周（周一 00:00 起）计；窗口两端不完整的周标「不完整周」，不与目标对比。
- **一条发布记录多次改状态**：取它的最新状态（`review-delivery` 的读接口已这样返回）。
- **作品被删除 / 选题卡不存在**：无外键；适配器回答「不存在」时该项进缺口「引用的作品已不存在」，不中断整份报告。
- **账号在两次生成之间被删除**：新版本生成时，该账号与「不存在」同形拒绝；旧版本照常能读。
- **一条建议的目标账号后来被删除**：采纳为账号配置提议时 404 同形拒绝；采纳为选题卡时卡上不挂账号并在效果记录里写明。
- **标签写法不同**（「价格」与「 价格 」）：受众反馈按标注原文分组，只做 NFC 与首尾空白规范化，不做大小写折叠或同义合并。
- **ROI 报告被引用后又有新版本**：诊断引用的是 `(report_id, version_no)` 那一版的摘要副本，不跟着变。
- **报告范围内一条数据都没有**：除执行流程外每个维度「不可计算：没有数据」，不是 0；`scope` 照常列出空清单。

## Requirements *(mandatory)*

### Functional Requirements

**范围、窗口与参数**

- **FR-001**：诊断报告 MUST 由用户显式生成。参数 MUST 包括：范围（`account`：恰好一个账号；`brand`：用户勾选的一个或多个账号）、本窗口（起止日期）、所选维度及各维度参数；表现变化维度另需对比窗口。
- **FR-002**：窗口 MUST 按品牌时区（`loretide.timezone`）解释为 `[开始日 00:00, 结束日次日 00:00)`，时区随参数存进报告版本。结束早于开始 → 400 点名 `window`。
- **FR-003**：维度 MUST 是受控集**恰好六项**：`consistency`（定位与表达一致性）、`coverage`（内容覆盖）、`cadence`（节奏）、`performance`（表现变化）、`audience_feedback`（受众反馈）、`execution_flow`（执行流程）。用户可选任意子集（含空集）；每个维度的参数见 contract §4。
- **FR-004**：参数与结果 MUST NOT 有行业、岗位、运营角色类字段；请求体里出现 `role` / `industry` 之类未知字段 MUST 400 点名该字段（严格解码）。
- **FR-005**：`brand` 范围的账号清单 MUST 由用户给出，不许「空 = 全部」；空清单 400 点名 `scope.account_ids`。

**确定性计算（D1、D2）**

- **FR-010**：所有维度结果 MUST 由服务端纯函数 `CalculateDiagnosis(params, inputs) (Result, error)` 算出：不读库、不读时钟（生成时间由参数带入）、不调模型、不外发、不用 `float32` / `float64`（比率与均值用 `math/big.Rat`）。同一输入同一计算版本 MUST 逐字节相同，输入顺序打乱结果不变。
- **FR-011**：计算版本 MUST 是常量，首版 `opdiag-calc/1`。改变任何既有维度的算法、舍入或结果形状 MUST 升版本；**新增维度**不改变既有维度与 `scope` 的结果，不升版本（这一条让 PR 1 与 PR 2 之间生成的版本仍可复算，见 plan.md「PR 1」）。
- **FR-012**：每个维度的结果 MUST 是 `{status: "ok", facts, completeness, limits, records}` 或 `{status: "not_computable", reason, completeness, limits, records}`。原因码是受控集（contract §3），MUST NOT 用 0、空、NaN 或省略表示「不可计算」。
- **FR-013**：结果里 MUST NOT 出现任何分数、等级、评级、百分制、红黄绿之类的汇总字段；计数、合计、均值、差值是事实，都带上它们的分母或条数。
- **FR-014**：显示用的舍入 MUST 是「四舍五入，远离零」，两位小数（与 034 同一条规则）；存储的 `value` 是约分后的有理数串。
- **FR-015**：服务端产生的说明文字 MUST 只是**规则 id**（受控集，contract §3），由前端翻译；服务端 MUST NOT 生成自由文字的结论。

**各维度（contract §5 给出逐条算法）**

- **FR-020 一致性**：对所选账号，列出用户选定的检查项（账号配置十一项的子集）各自的 `status`；对窗口内每条作品，按最新的一致性标注计「符合 / 不符合 / 拿不准 / 未检查」四个计数。未确认的配置项与未检查的作品 MUST 进缺口。
- **FR-021 覆盖**：按参数里用户写的支柱清单，计窗口内作品按最新支柱标注的条数，另计「未标注」。一条作品可属于多个支柱；结果 MUST 标明「一条作品可属于多个支柱，各支柱条数不可相加」。支柱清单为空 → `not_computable`，原因 `missing_config`。MUST NOT 从账号配置文字或作品标题推断支柱。
- **FR-022 节奏**：按渠道、按品牌时区的 ISO 周计窗口内已发布（`reported_published` / `verified_published`）的发布记录条数；目标取经营规则的 `cadence[渠道]`。目标缺省 → 「未设定」，不对比；目标 0 与缺省 MUST 区分。不完整周 MUST 标出且不对比。`published_at` 为空的发布记录 MUST 进缺口，不落入任何周。
- **FR-023 表现变化**：按 `(platform, metric)` 分组，两个窗口各给：发布记录数、有值条数、未知条数、合计、均值（合计 ÷ 有值条数）；两窗口有值条数都 ≥ 1 时给均值之差，否则 `change` 为 `not_computable`。`stat_window` 写法不止一种 MUST 标 `stat_window_mixed`。MUST NOT 有跨平台合计、跨平台比较或任何排序字段。
- **FR-024 受众反馈**：窗口内（按 `occurred_at`）的反馈摘录，按 `source_type`（评论 / 私信 / 线索）与平台计数，再按人工标签计数（规范化见 contract §5.5），无标签的计「未标注」。MUST NOT 做情感判断、同义合并或关键词抽取；摘录原文与解读 MUST NOT 进入报告输入。
- **FR-025 执行流程**：以报告生成时间为准，列出并计数：`pending` 与 `changes_requested` 的审核（带等待整日数）、`decided_at` 落入窗口的 `rejected` 审核、`held` 的交付任务、`review-delivery` 派生 `due = true` 的交付任务、状态 `failed` / `unknown` / `removed` 的发布记录、已过观察时点却没有任何指标的发布记录（观察时点缺省 → 该项 `not_computable`）。MUST NOT 使用任何本卡自定的天数阈值。
- **FR-026 账号归属**：发布记录与作品的账号 = 作品所属选题卡的 `account_id`；审核用它自己的 `account_id`；指标用它自己的 `account_id`。都为空时进「账号未知」。MUST NOT 用 `platform_account` 等自由文本匹配账号。历史导入的作品没有选题卡，因此全部归「账号未知」（主控已接受，2026-09-25）；只要范围内有这类记录，结果的 `rules` MUST 含具名局限 `scope.historical_import_account_unknown`，并在「账号未知」一节每个维度的 `limits` 里列出（contract §5.9）。
- **FR-027 ROI 引用（Q6）**：参数可带一个可选的 `roi_report_ref {report_id, version_no}`；生成时经 034 的 `ReportSummary` 读出并**整份复制**进输入，结果里原样呈现为「经营结果（引用）」，MUST NOT 与任何维度相加、相比或参与计算。
- **FR-028 不下结论**：结果与服务端规则 id 里 MUST NOT 出现「增长」「提升」「下降」「带来」「导致」「因为」一类的因果或趋势结论；表现维度的 `limits` MUST 固定包含 `performance.difference_is_not_cause`。
- **FR-029 品牌汇总**：品牌汇总 = 每个所选账号一节 + 「账号未知」一节 + 品牌层面一节（节奏按渠道、执行流程计数）。账号节按 `display_name`、再按 `account_id` 排序，MUST NOT 按任何数值排序。

**数据完整性与补录待办（D1-b）**

- **FR-030**：每个维度 MUST 给 `completeness {expected, present, gaps[]}`；报告另给总体缺口清单（各维度缺口按 `gap_key` 去重）。
- **FR-031**：每个缺口 MUST 带：稳定键 `gap_key`（由维度、缺口类型与记录 id 确定性拼成）、缺口类型（受控集，contract §3）、指向的记录 `{kind, id}`、账号（可空）、去哪里补（前端路由 id，不是 URL）。
- **FR-032**：「补录待办」= 缺口清单的呈现，读报告版本即得，MUST NOT 另存一份；用户可以把某个缺口「加入待办」（PR 3，产生一条 `origin_kind = data_gap` 的待办）。
- **FR-033**：完整性 MUST NOT 被折算成分数显示；可以显示「20 条中 12 条有指标」这样的计数。

**报告版本（D1-c；D14-V05）**

- **FR-040**：每次生成 MUST 产生新的报告版本：`report_id` + `version_no`，保存 `params`、`inputs`（每项输入的必要字段副本与 `fingerprint`）、`calc_version`、`result`、生成人、生成时间。只插不改。
- **FR-041**：输入快照 MUST 记下每个外部输入的版本标识：账号配置 `revision_id`、经营规则内容副本（它没有版本号）、发布记录的最新状态、指标与摘录的 id、标注的 id、ROI 报告的 `(report_id, version_no)`。
- **FR-042**：输入 MUST 只含计算需要的字段（contract §6 逐项列出）；MUST NOT 含账号配置各项的文字内容、反馈摘录原文与解读、证据说明、`customer_ref` / `order_ref`。
- **FR-043**：打开一个版本时，`inputs_changed` MUST 读时派生（按同一参数重新收集当前输入，按 `fingerprint` 比较，列出新增、修改、消失的项），MUST NOT 落存储。
- **FR-044**：「用最新数据生成新版本」MUST 以上一版参数为默认值生成版本号 +1 的新版本；旧版本及挂在它上面的判断、建议、决定保持不变。
- **FR-045**：对任一已存版本，用其保存的 `params`、`inputs` 与 `calc_version` 复算 MUST 得到与保存结果逐字节相同的输出（一条用例，不是界面功能）。
- **FR-046**：报告 MUST 通过公开 Go 读接口 `DiagnosisSummary` 提供给后续消费者（AI 判断层等），字段只取 contract §8 的允许清单；一条反射用例扫字段名。

**人写判断、替代解释与建议（D1-d）**

- **FR-050**：判断记录 MUST 挂在一个报告版本上（`report_id`, `version_no`），修订制，类型受控集 `judgement`（判断）/ `alternative_explanation`（替代解释）/ `limitation`（局限）；替代解释 MAY 指向它所解释的那条判断。
- **FR-051**：每条判断 MUST 选依据 `evidence`（有数据依据：`evidence_refs` 非空且每一项在该版本的结果里存在）或 `qualitative`（定性：`evidence_refs` 必须为空）。界面 MUST 对 `qualitative` 显示「定性判断：没有数据支持」。
- **FR-052**：建议记录 MUST 挂在报告版本上，修订制，保存：文字、目标类型（受控集**恰好三项** `topic_card` / `todo` / `profile_proposal`）、目标参数（contract §7.3）、关联的判断 id、引用。
- **FR-053**：判断与建议的 `author_kind` MUST 是受控集，本版**恰好一项** `human`。AI 写的判断与建议是后续卡，届时加取值要一个迁移（改 `CHECK`）——这是有意的代价。
- **FR-054**：判断、建议的修改 MUST 产生新修订并带 `base_revision`，不符 → 409；作废也是一条修订。

**采纳与拒绝（D3；D14-V05）**

- **FR-060**：对建议的某一修订，用户 MUST 能做且只能做一次决定：`adopt` 或 `reject`，带可选说明。决定记录只插不改。同一修订已有决定 → 409 点名 `suggestion_id`。已作废的修订不能决定。
- **FR-061**：`reject` MUST 只写决定记录与审计；MUST NOT 调用任何其他模块的写接口，MUST NOT 写本模块的待办、提议、效果表。
- **FR-062**：`adopt` + `topic_card` 有两种方式（Q3）。`create`：先写决定记录（本模块事务），再经 `topic-planning` 公开接口 `CreateOnce` 建一张 `draft` 选题卡，带这条建议的幂等键 `opdiag-suggestion:<suggestion_id>`（账号取建议的目标账号；建议文字预填进 `ip_fit`，其余留空），再写效果记录 `done` 带 `topic_card_id`；建卡失败写效果 `failed` 带原因码。`link`：关联一张已有选题卡（经公开接口只读核实它存在且账号相符），决定与效果在同一事务写入。两种方式都 MUST NOT 启动选题、创作、审核或发布。
- **FR-063**：效果 `failed`、或还没有任何效果记录的采纳决定 MUST 可重试（`POST /decisions/{decisionId}/retry`，可改为 `link`）；已有 `done` 效果的决定 MUST NOT 再建卡（409 点名 `decision_id`）。
- **FR-063a**（Q3 补充，主控已裁定 2026-09-25）：建卡 MUST 带每条建议一个的幂等键 `opdiag-suggestion:<suggestion_id>`。`topic-planning` 按（工作区, 幂等键）至多建一张卡：同键再调用 MUST 返回已建的那张卡、不建新卡。「卡已建、效果未记」的窗口 MUST 经重试收敛：重试拿到已建的卡，写效果 `done` 指向它；无论重试几次、是否并发，一条建议最多对应一张选题卡。同一建议的新修订再采纳也用同一个键，仍指向同一张卡（contract §7.4）。
- **FR-064**：`adopt` + `todo`：在同一事务里写决定、待办（`open`）与效果 `done`。
- **FR-065**：`adopt` + `profile_proposal`：在同一事务里写决定、提议（`proposed`，记下目标账号当前配置的 `revision_id` 作 `base_revision_id`）与效果 `done`。**此时 MUST NOT 写 `ip-profile`。**
- **FR-066**：提议的确认 MUST 是另一个显式动作：界面显示每个被修改项的「当前值 → 提议值」；确认时当前 `revision_id` 仍等于 `base_revision_id` 才经 `ipprofile.Service.SetProfile` 写新版本（其余项沿用当前值，被修改项的状态置为 `confirmed`），然后提议写 `confirmed` 修订带新 `revision_id`；不相等 → 409 点名 `base_revision_id`。用户也可以「放弃」提议（`dismissed`），不写 `ip-profile`。
- **FR-067**：提议只能改账号配置的**八个文本项**（contract §7.3）；`persona_prompt`、渠道列表、每周时长、风格样本 MUST NOT 出现在提议里（400 点名字段）。
- **FR-068**：本卡 MUST NOT 有写「经营记忆 / 经营结论」的路径，也 MUST NOT 为它建表；守卫用例扫模块与迁移。
- **FR-069**：每个决定、效果、提议状态变化、待办状态变化 MUST 在同一事务写审计（`AuditTx`）；审计失败整体回滚。

**AI 判断层（D1：只留挂接）**

### Key Entities

- **报告版本（Report Version）**：冻结的参数、输入快照、计算版本与结果。只插。
- **作品标注（Work Mark）**：人对一条作品的一次标注——属于哪个支柱，或对照账号配置某一项是否一致。只插，最新的为准。
- **维度结果（Dimension Result，值对象）**：`ok` 或 `not_computable`，带事实、完整性、局限与记录清单。
- **缺口（Gap，值对象）**：一处缺数据，带稳定键与去哪里补。「补录待办」就是缺口清单。
- **判断修订（Judgement Revision）**：人写的判断、替代解释或局限，挂在报告版本上。
- **建议修订（Suggestion Revision）**：人写的行动建议，带目标类型与目标参数。
- **决定（Decision）**：对建议某一修订的采纳或拒绝。只插。
- **效果（Effect）**：采纳之后真正发生了什么（建了哪张卡、哪条待办、哪份提议），或失败原因。只插。
- **账号配置修改提议（Profile Proposal Revision）**：待确认的配置改动；确认后指向 `ip-profile` 的新版本。
- **待办修订（Todo Revision）**：经营诊断里的一条待办，来自建议或缺口；`open` / `done` / `dropped`。

## Success Criteria *(mandatory)*

- **SC-001**（D14-V04 缺数据）：计算器纯函数用例，各一条：无指标 → 表现 `not_computable/no_data`；nil 值计「未知」不计入合计；0 值计入「有值」；节奏目标缺省 → 不对比，目标 0 → 对比；支柱清单空 → `missing_config`；观察时点缺省 → 该项 `not_computable`；范围内零数据 → 除执行流程外每个维度 `no_data`，执行流程 `ok` 且清单为空（审核与交付是工作台自己的状态）。
- **SC-002**（D14-V04 平台口径）：两平台数据 → 结果按平台分组，反射扫结果类型确认不存在 `rank`、`score`、`grade`、`rating` 一类字段，也没有跨平台合计；`stat_window` 两种写法 → `stat_window_mixed` 与写法清单。
- **SC-003**（D14-V04 不下结论）：守卫：规则 id、core 显示映射、四语言文案中本页的键不含「增长 / 提升 / 下降 / 导致 / 带来 / 因为」及英文 `growth` / `caused` / `because`；表现维度的 `limits` 恒含 `performance.difference_is_not_cause`。
- **SC-004**（D14-V05 可追溯）：生成版本 1 → 补录一条指标 → 版本 1 逐字节不变，`inputs_changed` 列出那条；生成版本 2，两版并存；每个版本的 `inputs` 含账号配置 `revision_id` 与两个窗口。
- **SC-005**（FR-045）：每个计算器固定样例存成报告版本，从库读回复算，逐字节相同。
- **SC-006**（D14-V05 拒绝）：拒绝一条建议 → 除决定表与审计外，所有 `content_opdiag_*` 表行数不变，`ip-profile` 版本数、选题卡数不变；假适配器记录零次写调用。

- **SC-009**（D4 / D14-V01）：非成员与跨品牌账号 id 各一条：拒绝体与「不存在」逐字节相同，假适配器记录零次账号数据读取；守卫：模块与 handler 文件不引用 `source-inbox`、`knowledge-base`。
- **SC-010**（FR-042、FR-046）：反射用例：`inputs` 与 `DiagnosisSummary` 不含 `redacted_excerpt`、`interpretation`、`evidence_note`、`customer_ref`、`order_ref`、账号配置各项的 `value`、`recorded_by`。
- **SC-011**（FR-004、FR-013）：请求体带 `role` / `industry` → 400；反射扫结果类型无分数类字段。

## Assumptions

1. **数据都是人录的**。本卡不接平台接口、不抓数据、不调模型。
2. **一个品牌 = 一个工作区**（D4）。品牌之间没有汇总。
3. **工作区成员都可以生成诊断、写判断与建议、做决定**；角色化权限没有既有实体可挂，与 027、034 相同。
4. **账号数据的授权 = 品牌成员资格 + 账号属于本品牌**（Q5）。一旦 LT-016 开始存授权记录且覆盖账号数据，品牌汇总改走 `CanRead`（后续项）。
5. **规模**：一个品牌几个到十几个账号，每月几十到几百条发布记录与指标；生成时把窗口内输入读进内存即可。

## 本规格补的设计（原文没有直接给，改起来的代价写在后面）

1. **一致性与支柱归属靠人标注，机器只计数**（FR-020、FR-021）。执行器禁用时，「是否符合定位」「属于哪个支柱」都是判断；机器能做的只有核对配置项是否确认、数人标了什么。代价：没人标就全是「未检查 / 未标注」。
2. **表现维度取「报告生成前最后一次采样」**（Q7）。原文只说「表现变化」；指标是累计值的快照，同一条发布记录多次采样相加会重复。代价：老发布记录的采样通常比新的「更晚」，局限说明固定写出这一点（`performance.samples_taken_at_different_ages`）。
3. **采纳先记决定、再做动作、后记结果，建卡带幂等键**（Q3 与补充）。跨模块建卡没法与决定放进同一事务；先记决定保证「采纳有动作记录」（D14-V05）在任何失败下都成立；幂等键保证中途失败后重试不会多出一张卡。代价：`topic-planning` 多一个可空列、一个唯一索引和一个公开函数 `CreateOnce`（既有 `Create` 不变）。
4. **决定挂在建议的某一修订上，一次定终身**（FR-060）。改主意要先改建议（新修订），旧决定留在旧修订上，历史不被覆盖。
5. **补录待办不另存**（FR-032）。它就是报告版本里的缺口清单；只有用户主动「加入待办」才产生一条待办记录。
6. **服务端只输出规则 id，不输出句子**（FR-015）。四语言由前端翻译；也让「服务端不写因果结论」可以被守卫用例检查。
